# AGENTS.md — src/app/shell/

Sidebar, deck (home grid), command palette, and root layout. This is the "framework, not a tool list" part of DUDE (README's "Architecture" section, `DUDE_PRD.md` §9).

## The rule

**Nothing under this directory contains a hard-coded tool ID.** Every list here (sidebar entries, deck cards, command-palette results) is derived at runtime from `TOOL_DEFINITIONS` (`src/app/core/registry/tool-definitions.ts`) via `ToolRegistryService`. If you're editing a component here to special-case a specific tool by ID or route, stop — that's the exact failure mode the registry pattern exists to prevent, and it means the fix belongs in `tool-definitions.ts` or the registry service instead.

Adding, removing, or reordering a tool should never require touching this directory. If it does, treat it as a bug in the registry/shell contract, not a one-off exception — see `/ADDING_A_TOOL.md`.

## The deliberate exceptions: `pipelines/` and `smart-paste/`

`src/app/shell/pipelines/` (the Pipelines list/builder pages) and the "Pipelines" sidebar link in `sidebar.html` are new shell surface area sanctioned by `DUDE_PRD.md` §21 Phase 21 Item 2 — composing tools into a chained workflow changes what a `ToolDefinition` means, not just adds one, so this is one of the roadmap items explicitly allowed to add to `shell/`/`core/`. It still honors the rule's spirit: nothing in `pipelines/` hard-codes a specific tool id — a pipeline step's `toolId` is user-selected data, resolved generically through `ToolRegistryService`/`PipelineStepRegistryService`, the same way `ToolShell` resolves the current tool via `getByRoute()`. Pipelines are not a 278th tool: no category, no `TOOL_DEFINITIONS` entry, no `buildToolRoutes()` entry — see `src/app/core/pipeline/AGENTS.md`.

`src/app/shell/smart-paste/` (the Smart Paste page) and the "Smart Paste" sidebar link are the second such exception, sanctioned by `DUDE_PRD.md` §21 Phase 21 Item 3 for the same reason: recognizing pasted content and routing to the matching tool is cross-tool discovery infrastructure, not a 278th tool. `PASTE_DETECTORS` (`src/app/core/paste-detect/paste-detectors.ts`) is a hand-maintained array of `{toolId, test}` entries rather than a per-tool convention file — see `src/app/core/paste-detect/AGENTS.md` for why that differs from the Pipelines precedent. As with Pipelines, no category, no `TOOL_DEFINITIONS` entry, no `buildToolRoutes()` entry, and every tool it can navigate to is resolved generically through `ToolRegistryService.getById()` — a detector's `toolId` is just a string key into the registry, never a hard-coded branch.

`src/app/shell/workspace/` (tabs, resizable panels, and — from Milestone 292 — a scratchpad drawer) is the third such exception, sanctioned by `DUDE_PRD.md` §21 Phase 21 Item 4: a multi-tool tab strip and panel layout change what "the shell's content area" means, not a 278th tool. See `src/app/shell/workspace/AGENTS.md` for why it needed a new dynamic-mounting mechanism (`ToolHost` + `NgComponentOutlet`) instead of named router outlets, and `src/app/core/workspace/AGENTS.md` for the shared `<id>.workspace-step.ts` adapter convention it and Local History both build on.

`src/app/shell/history/` (the History feed) is the fourth such exception, sanctioned by `DUDE_PRD.md` §21 Phase 21 Item 5: a cross-tool history feed is discovery/recall infrastructure spanning every tool, not a 278th tool. See `src/app/shell/history/AGENTS.md` and `src/app/core/history/AGENTS.md` for the eligibility rule and storage design.

`src/app/shell/quick-run/` (the `/quick-run` route, "Quick Run" in the sidebar/command palette) is the fifth such exception, sanctioned by `DUDE_PRD.md` §21 Phase 24 Item 12 (the PRD's own "Quick Actions," renamed to avoid colliding with the already-shipped Electron feature of that name — see `electron/hotkey-bridge.ts`). Running a tool's transform without navigating into its full workspace is cross-tool execution infrastructure, not a 278th tool: no `TOOL_DEFINITIONS` entry, no category. It executes via the exact same `PipelineStep.run(input)` contract Pipelines already uses, scoped to text-accepting steps only — see `shell/quick-run/quick-run-list/quick-run-list.ts`'s own doc comment.

Two other Phase 24 shell surfaces are new *directories* but deliberately extend an already-sanctioned exception rather than adding a new one: `src/app/shell/workspace/template-gallery/` (Workspace Templates, Item 11) extends the `workspace/` exception above, and `src/app/shell/history/recents-tab/` (Unified Recents, Item 13) extends the `history/` exception above — see `core/workspace/AGENTS.md` and `core/recents/AGENTS.md` respectively. Neither gets its own numbered entry here.

Two further Phase 24 additions touch shell-adjacent files without any new exception at all, since neither adds a hard-coded tool id or a new top-level surface: `src/app/shell/deck/` (Deck, the home route) grew a paste/drop hero and Recently-Used/Favorites/Pinned-Pipelines rails above its existing category grid (Item 1, via `shared/components/paste-detect-panel/` and `shared/components/smart-file-drop-zone/` — both registry-driven, no hard-coded tool ids); and `src/app/shell/layout/shell-layout.ts` mounts `shared/components/ambient-paste-chip/` once, globally (Item 2) — a `shared/` component, not a `shell/`-owned one, following the exact same reasoning `OfflineBadge`/`UpdateBadge` already established for other globally-mounted, registry-agnostic UI.

`src/app/shell/projects/` is the sixth sanctioned exception, added in Phase 25 Item 1. A Project is a named reference bundle of workspace layout and pinned pipeline ids, not a tool or an IDE project. The gallery is a shell route because it manages these cross-tool references; it never hard-codes a tool id. See `src/app/core/project/AGENTS.md`.

`src/app/core/deep-link/` and its one `ShellLayout` mount form the seventh Phase 25 exception. Links resolve tool ids through `ToolRegistryService` and saved layouts/pipelines through their owning stores; the shell never contains a tool-specific route branch. Main-process protocol handling forwards raw strings only.

`src/app/shell/settings/` (the `/settings/:section` and `/settings/tools/:toolId` routes, pinned to the sidebar footer) is the eighth exception. Settings used to be a `developer`-category tool, which forced special cases everywhere (tool counts, README/SECURITY generators, pipeline coverage, hard-coded `getById('settings')` lookups in `core/`). App-wide preferences aren't a tool, so it is now a shell destination: core sections (`settings-sections.ts`, one component each under `sections/`) are hand-listed app-level panels, and the "Tools" group is generated from manifests' optional `settingsSection` declaration (`ToolRegistryService.settingsSections()`), so a tool contributes its own settings panel without touching this directory. Its secure-local/`local` storage keeps the legacy `'settings'` namespace (`core/persistence/app-settings.ts`) because `electron/llm-bridge.ts` reads `dude:v1:settings:llm*` directly — that string is a storage namespace, not a tool id.

`src/app/shell/browse-tools/` (the `/tools` route) is the ninth exception, sanctioned by `DUDE_PRD.md` §21 Phase 30A.1: the complete tool inventory needed a dedicated, searchable/filterable/sortable catalog surface once Deck stopped being allowed to treat the full registry as its default content (Phase 30's product rule). It still honors the rule's spirit — every row is resolved generically through `ToolRegistryService`/`FavoritesService`/`UsageService`, nothing hard-codes a tool id, and no `TOOL_DEFINITIONS` entry or `buildToolRoutes()` entry exists for it (`core/routing/app.routes.ts` wires it as a plain sibling route, the same way as the other eight exceptions). The pure filtering/sorting/ranking logic it depends on lives in `core/registry/browse-tools-*.ts`, not in this directory, so it stays independently unit-testable and reusable by Phase 30D/30G. Deck's own "Browse all tools" grid is intentionally left untouched by Phase 30A — see Phase 30D for when that changes.
