# AGENTS.md — apps/hub/

The self-hosted **DUDE Hub** (Phases 31C-31G, complete; 31D added synchronization, 31E the Hub-served shared-state web, trusted certificates and private-mode access, 31F Internet readiness behind an elevated public-mode gate, and 31G encrypted backup, restore and manual Hub transfer; 31J (complete, Milestones 787-815) added presence, notifications, read-only job status, live owner views and Hub-persisted collaboration, decisions PD-099 to PD-115 in the [Phase 31J plan](../../docs/delivery/PHASE31J_PLAN.md), evidence in [31J acceptance](../../docs/delivery/PHASE31J_ACCEPTANCE.md)): the user's own authoritative service for owner identity, the device registry, sessions, audit and a canonical SQLite skeleton. It runs independently of Electron, as a Windows service, a Docker container or a foreground process. DUDE never operates an instance. Decisions: PD-023 to PD-037 in the [decision log](../../docs/history/DECISION_LOG.md#phase-31c-implementation-decisions) (amended for PD-025 and PD-026); PD-038 to PD-049 (31D) and PD-050 to PD-062 (31E) PD-063 to PD-068 (31F) and PD-069 to PD-074 (31G, with the amendments recorded there) in the same log. Evidence: [Phase 31C acceptance](../../docs/delivery/PHASE31C_ACCEPTANCE.md), [31D](../../docs/delivery/PHASE31D_ACCEPTANCE.md), [31E](../../docs/delivery/PHASE31E_ACCEPTANCE.md), [31F](../../docs/delivery/PHASE31F_ACCEPTANCE.md) and [31G](../../docs/delivery/PHASE31G_ACCEPTANCE.md).

## The rules

- Plain TypeScript with its own `tsconfig.json`, compiled by `esbuild` to a CJS bundle and packaged as a Node 24 single-executable application. Never pulled into `tsconfig.app.json`.
- Never import `electron`, `@angular/*`, `apps/web`, `@dude/device-agent` or `@dude/desktop`. Shared code comes only from portable packages, plus the Node-only `@dude/sqlite-store`.
- `src/security/ip-block.ts` blocks an address (not loopback) after 25 failed credentials across kinds or 10 flood rejections in 15 minutes (15 min, 1 h, 6 h, 24 h by strike, forgotten after 7 days). It persists in `ip_blocks` (migration 0006), is audited (`security.ip-blocked`, `security.ip-unblocked`) and is cleared only by the elevated `dude-hub security blocks list|clear <address>` (admin methods `security.blocks.*`).
- Owner step-up: a cookie session is password-confirmed for 5 minutes after sign-in, recovery or `POST /auth/step-up`; pairing codes, recovery-code regeneration and revoke-all (preview and apply) return 403 `step-up-required` otherwise (bearer sessions always count as stepped up). Step-up and password change rotate the cookie session (`rotateSession`: new token/CSRF, old row kept 60 s via `rotated_to`; open sockets follow the successor). Clients must adopt the returned `csrfToken`.
- Audit and alerts: `throttle.locked` is written once per lockout start; `security/address-privacy.ts` masks stored client addresses when `dude-hub security audit-ips truncated` is set (meta `audit_ip_mode`; throttle and IP-block keys keep the real address; existing rows are not rewritten). `GET /api/v1/security/alerts` and `POST /api/v1/security/alerts/seen` expose a read model over security-relevant audit events (new-address sign-ins carry `newAddress`; the seen watermark is meta `alerts_seen_seq`).
- `src/cli/test-overrides.ts` reads TEST-ONLY env knobs in `run` (`DUDE_HUB_TEST_RELAX_RATE_LIMITS=1`, `DUDE_HUB_TEST_SYNC_RETENTION_DAYS`, `DUDE_HUB_TEST_SYNC_COMPACTION_MS`, and for the 31J collaboration e2e `DUDE_HUB_TEST_BACKUP_CHECK_MS`, `DUDE_HUB_TEST_COLLAB_SNAPSHOT_IDLE_MS`, `DUDE_HUB_TEST_COLLAB_SNAPSHOT_MIN_INTERVAL_MS`) for the two-Agent sync suite and the Hub e2e; never a CLI flag or config field. They are honoured only by the test bundle (`npm run hub:compile:test` -> `dist/hub-test/`, `__DUDE_HUB_TEST_BUILD__`); the release bundle (`hub:compile`, SEA, service, Docker) ignores them and public mode refuses to start if one is set (PD-068). Test harnesses (`hub-harness.ts`, `e2e/hub`, `measure-hub-web`) use the test bundle.
- The Hub process is the only writer of `data/dude.db`. CLI commands that need state go through the local admin named pipe while the service runs; they never open the database.
- Every route has a TypeBox schema (request and response), declares its credential type (none, setup token, owner cookie session, owner bearer session, device token), and writes an audit event. A device credential alone never grants owner rights.
- HTTPS only. No listener on a non-loopback address unless LAN mode is on (installer checkbox or elevated `dude-hub network lan on|off`) or container mode is set. Reverse-proxy mode listens on loopback only.
- Public (Internet) mode is released behind an elevated readiness gate (PD-066): `network mode public [--accept-unverified-reachability] --type "EXPOSE HUB TO THE INTERNET"` goes through the admin method `network.mode.set`, which builds the Hub's own diagnostics report as if public (the CLI adds the Windows-only firewall-rule inspection and native-listener audit), runs `diagnostics/readiness.ts` (`evaluatePublicReadiness`, pure) and refuses with the blocker list (error `detail`, each with its fix) unless there is none, then requires the exact phrase. Blockers: certificate not browser-trustable (needs `acme`, `imported` or reverse-proxy mode; self-signed and `local-ca` block), no public DNS name, certificate not covering the names or expiring within 7 days, no owner, missing or invalid Public firewall rule (Windows service), an Agent TCP listener, a loopback bind without proxy mode, and external reachability not verified within 7 days (a warning only with `--accept-unverified-reachability`, which is audited). Warnings: address stability, DNS resolution, HSTS. The gate needs a running Hub, so with none the CLI refuses; `private` is unrestricted. `run` refuses a public config only when the bind cannot accept inbound traffic (loopback without proxy mode) and never because of certificate state. Exposure changes (names, CA, import, proxy, mode) are elevated admin-pipe commands; no owner-session route may widen exposure.
- The built-in local CA key is DPAPI LocalMachine protected and may be unprotected only by the admin methods, the leaf issuer and the isolated renewal job; a spec in `src/tls/local-ca.spec.ts` enforces the import boundary. Request handlers never touch it.
- ACME (31F): certificate source `acme` via `dude-hub tls acme issue --name <dns> [--agree-tos] [--staging|--directory <url>] [--http-port <n>]` / `tls acme status` (admin methods `tls.acme.issue|status`, audit `tls.acme-issued|tls.acme-failed`, config `exposure.acme`). Issuance stages the certificate through the dual-pin rotation (the operator then runs `tls activate`); the Hub renews an ACTIVE `acme` certificate itself (`tls/acme/acme-renewal.ts`, 12 h timer, within 30 days, same leaf key so the pin is unchanged, 6 h retry back-off, `tls.renewed` with `source: acme`). The http-01 listener binds only during an order (never idle). The account key (`<tlsDir>/acme/`, own DPAPI entropy) may be unprotected only by `acme-issue.ts` (issuance method and renewal job); `local-ca.spec.ts` and `acme-issue.spec.ts` enforce the import boundary. ACME certificates count as browser-trustable for HSTS; chain verification against public roots is not implemented.
- Public-mode firewall and native ports (31F, PD-068): `service/firewall.ts` owns the `DUDE Hub (Public)` (profile any, program-scoped) and `DUDE Hub (ACME http-01)` rules, managed ONLY by the elevated CLI (`network firewall public|acme on|off|status`, `tls acme issue --open-firewall`, removed by `service uninstall`); the running Hub and owner routes never touch the firewall and never use UPnP. `service/listeners.ts` audits `netstat`/`tasklist`: ANY `dude-agent.exe` TCP listener is a violation (the Agent has no TCP port), a non-loopback `DUDE.exe` listener is info. `public-firewall-rule` and `native-ports-exposed` are gathered only by `dude-hub doctor`; `GET /api/v1/diagnostics` reports them not-checked.
- External reachability (31F, PD-065): `GET /api/v1/reachability/echo` (owner session or device token; a device token gains no owner rights elsewhere) returns the Hub's own observation of the request source (scope only, never the address). Verified only for a public source on a configured name (proxy mode: the `publicOrigin` host); it stores meta `reachability_last` and writes `network.reachability-verified` at most once per 24 h. `diagnostics/reachability.ts` owns `evaluateEcho`, `readReachability` and `reachabilityVerified` (7-day freshness); the `external-reachability` check reads it. No third-party probe, no client-reported result. The desktop's "Test from this device" is just another caller: its Device Agent makes this request through the public name with a device token (`hub.reachabilityEcho`), and the Hub still decides from the observed source.
- Dynamic addresses (31F, PD-064): detection only. `diagnostics/addresses.ts` inventories interface addresses and resolves configured DNS names (injectable resolver, 60 s cache on the owner route, no external IP lookup); `diagnostics/address-watch.ts` records `meta.hub_addresses` and writes one `network.address-changed` audit event per change (alert-listed; startup `addresses-changed` notice). The Hub never updates DNS and stores no DNS credential. This still holds for the 32-SS1 Cloudflare Tunnel (PD-142): the Hub stores no Cloudflare API token, only the owner-pasted tunnel connector token as a DPAPI-protected Hub secret.
- Revoked devices (31F): `resolveDeviceToken` re-resolves the token against the database on every request (revocation is effective on the next call). `commitCanonical` takes an `actor` (device + key, or browser session + browser row) and re-verifies it inside the commit transaction, throwing `DeviceInactiveError` (routes answer the standard 401) so a revocation racing a push writes nothing. `devices/revoked-attempts.ts` audits `device.revoked-attempt` (via `token|challenge|redeem|realtime`, once per hour per device and via, meta-throttled, failure path only; alert-listed with the device display name); responses must stay identical to an unknown token or id. `revocation-internet.spec.ts` is the scenario suite.
- Every certificate change (re-issue, renewal, import, proxy pin) goes through the dual-pin stage and activate rotation. Self-signed leaves omit `keyUsage` (BoringSSL).
- Never log or audit credentials, tokens, recovery codes, keys or request payloads.
- Destructive Hub actions (`purge`, owner reset, revoke-all, certificate rotation with `--force`) follow the Destructive-Action Contract with the server-side ConfirmationStore.
- Backup (31G, PD-069 to PD-074): `src/backup/` plus the portable `@dude/hub-backup` format library. A backup is one passphrase-encrypted `.dudebackup` file holding a scrubbed `VACUUM INTO` copy of the database (transient sessions, tokens, challenges, pairing codes, setup state and per-run meta removed; TLS keys and DPAPI material never included) and `hub.json`. `createBackupFile` writes `<name>.part`, re-opens and hash-verifies it, and only then renames it into place, so a failed run leaves nothing. `backup create` is two-step over the admin pipe (`backup.create.preview` writes nothing and reports the folder, file name, same-machine warning and passphrase warning; `backup.create.apply` needs the single-use ConfirmationStore token bound to folder, Hub instance and epoch; action `BACKUP_CREATE_ACTION`, classes `filesystem-write` and `secret-management`, boundary spec `backup/backup.confirmation-boundary.spec.ts`); no HTTP route, sync credential or web credential can issue or consume it, and a target inside the data, configuration or TLS directories is refused. `backup.list|verify|schedule.set|off|status` are admin methods too. A schedule (`hub.json` `backup.schedule`: folder, `intervalHours`, `retention`) is set only from the elevated CLI, stores a DPAPI-protected DERIVED key (`backup/schedule-key.ts`, only the schedule methods and `backup/scheduler.ts` may use it) and never the passphrase; the scheduler checks every 10 minutes, writes meta `backup_last`, prunes to the retention count only after its own run succeeded and verified, never after a failure, and never throws out of its timer. Audit events `backup.*` carry file names, sizes, counts and short error codes only. The passphrase travels only in admin-pipe params at apply time: never in audit detail, meta, logs, config or error messages. Restore (PD-072) is the OFFLINE command `dude-hub backup restore --file <abs> [--confirm <token>] [--replace "REPLACE HUB DATA"] [--old-hub-gone "THE OLD HUB IS GONE"]` (`service/restore.ts` over the library `backup/restore.ts`; it refuses, exit 2, while `isHubRunning` (shared with `purge` in `service/common.ts`) says a Hub is running, and needs elevation when a service is installed). It is purge-style staged: the preview writes only `run/restore-confirm.json` (a hashed single-use 60-second token bound to the file hash, manifest and target state); apply builds everything in `data/.restore-tmp`, moves an existing database, `hub.json` and TLS directory to `backups/replaced-<stamp>/` (never deleted) and renames the result in with rollback. The restored Hub has a NEW `hub_instance_id` and epoch + 1, every desktop device is `needs_re_pair` with its key revoked, transient state, device sync cursors and the TLS tables are cleared (certificates and keys are never in a backup), and `hub.json` keeps only port and names: loopback, private mode, no proxy, ACME or schedule. Re-pair (PD-072): `POST /pairing-codes` accepts `reattachDeviceId` (owner session, step-up as for any pairing code; 404 for an unknown or browser row, 409 for a row not awaiting re-pair) and stores it in `pairing_codes.reattach_device_id`; `enrollDevice` enrolls over an active `needs_re_pair` desktop row ONLY with a code bound to exactly that deviceId (any other code still yields `active-conflict`; a bound code with another deviceId or a row no longer awaiting re-pair is `code-rejected` without burning the code), clears the flag and adds a NEW key (the old keys stay revoked). `GET /api/v1/backup/status` (`routes/backup.ts`, owner cookie or bearer, read-only: no CSRF, no audit) is the read model for the UI: authority epoch and state, `lastBackup` (file NAME only), the schedule (folder, interval, retention, key presence supplied by `run`, never the key), the default backups folder and `devicesNeedingRePair`; transferred Hubs answer 503 through the fence. Typed phrases are compared exactly; a missing phrase refuses without spending the token. Transfer: `backup create --for-transfer` (admin `backup.create.preview|apply` with `forTransfer: true`) retires the Hub after the verified write (authority state `transferred`: it answers hello and status but fences sign-in, sync, web records and pairing) and `backup reactivate` (elevated, two-step, admin `backup.reactivate.preview|apply`) returns it to service at a new epoch.
- Job status (31J, PD-112): `src/jobs/job-status.ts` is a read-only registry the timers report into (`createJobRegistry`, decorated as `app.hubJobs`; `track`/`report` observe a run without changing the timer, `run` registers the four timers it starts, `create-server` the audit prune and sync compaction, and `run` the queue's `queue-runner`, `blobs-verify` and `blobs-staging-sweep` only when `savesphere.db` exists). `GET /api/v1/jobs` (`routes/jobs.ts`, owner cookie or bearer, `no-store`, no audit) lists `HUB_JOB_IDS` in order with last run, outcome, a short credential-free summary, next due time and running state; the last run is meta `job_last:<id>` (scrubbed from backups) and every change calls `notifyOwnerView('jobs')`. As built through 31J there is no run-now, queue or job framework; 32-SS1 adds a durable queue for Hub-internal work only (PD-147, Milestone 834), and `GET /api/v1/jobs` stays read-only. `GET /api/v1/queue` (`routes/queue.ts`, owner cookie or bearer, `no-store`, no audit) is the queue's read model: counts by state and kind, the oldest waiting job and recent failures with redacted notes, never a payload or result; there is no route that enqueues, cancels, retries or runs a job.
- Notifications (31J, PD-109/PD-110): `src/notifications/` keeps owner notifications in the `notifications` table (migration 0009, deduplicated by `source_key`, 30-day dismissed / 90-day / 500-row retention, scrubbed from backups and cleared on restore) fed ONLY by `producers.ts` (audit observer rows, failed `leaf-renewal` and `sync-compaction` jobs through `jobs.onFinish`, and the backup scheduler's overdue check; an address change is one notification, never also a security alert); `GET /api/v1/notifications`, `POST /read` and `POST /:id/dismiss` (`routes/notifications.ts`, owner session or a device token whose active desktop row holds `devices.notifications_access`, no audit) are the only routes the owner-set, step-up-gated, audited `PUT /devices/:id/notifications-access` grant opens to a device, and it also gates the protocol-3 `notification` and `notifications` view events to that device's sockets.
- Schema changes are new numbered migrations only; a shipped migration is never edited, and `minReaderVersion` makes older Hubs refuse a newer database.

## Layout

- `src/main.ts` entry; `src/cli/` the hand-parsed `dude-hub` CLI (`run`, `setup-token`, `owner reset`, `tls`, `self-test`; the service, network, doctor, purge, backup and provision commands live in `src/service/`).
- `src/server/` Fastify app (`create-server.ts`), `routes/` (hello, bootstrap, auth, sessions, devices, device-auth, device-recovery, tls-audit, sync, web-records, backup, diagnostics, reachability, security-alerts, and from 31J presence, jobs, notifications, collab-rooms with kept documents, collab-history and the shared `collab-caller` credential resolution), static/SPA hosting (never rewrites `/api/*`), error mapping, pin handling. Route specs and the `api-client-parity.spec.ts` live beside it.
- `src/security/` headers and CSP, Host guard, request (Origin, Fetch-Metadata, CSRF) guard, cookies, rate limit, persisted throttle, audit log and the single-use ConfirmationStore.
- `src/auth/` owner password (Argon2id), recovery codes, setup token, cookie and bearer sessions, device-token resolution, the `requireOwner` resolver, hub events.
- `src/devices/` pairing codes, Ed25519 keys, device tokens, the registry.
- `src/realtime/` the authenticated WebSocket at `/api/v1/realtime` and the shared WebSocket host and upgrade authentication (`ws-host.ts`, `ws-auth.ts`); `@fastify/websocket` is registered once there for every socket route. Also `presence.ts` (online counts and opt-in activity, memory only), `owner-views.ts` (audit notices to contentless `owner-view-changed` topics, coalesced per topic) and `ws-contract-parity.spec.ts`. 31J events go only to sockets whose hello declared protocol 3 or later.
- `src/collab/` Phase 31J collaboration: the `/api/v1/collab` socket (`collab-socket.ts`, consent per PD-103 in `collab-consent.ts`, Hub-rewritten awareness), the persistent document store, registry and materializer (`doc-store.ts`, `doc-registry.ts`, `materializer.ts`) for the PD-099 surfaces, the PD-102 push merge (`record-merge.ts`), history snapshots and the `collab-history-prune` job (`history.ts`), the `collab-maintenance` job (`maintenance.ts`) and the in-memory Markdown rooms (`rooms.ts`). Rooms are never persisted except through an explicit, audited keep.
- `src/workers/worker-mode.ts` (32-SS1, Milestone 830) the internal worker spawn contract: a worker is the Hub executable re-spawned with `--internal-worker <kind>` (`sea.isSea()` chooses exe or `node <bundle>`), hooked first in `main.ts`. Milestone 834 adds the `job` kind: `job-protocol.ts` (one `run` line in, `progress` lines and one `result` line out, redacted errors), `job-worker-host.ts` (the worker side; exits when stdin closes) and `worker-pool.ts` (the Hub side: one child per job, at most `size` (default 2) at once, an allowlisted environment (`WORKER_ENV_ALLOWLIST`; no Hub secret, `PATH` or `NODE_OPTIONS` inherited) plus `NODE_OPTIONS=--max-old-space-size`, a per-job scratch working directory under `storage/workers/`, a wall-clock kill (and `taskkill /T` on Windows), out-of-memory detection from the child's stderr, crash back-off, shutdown that kills every child). `worker-job-handlers.ts` is the empty production map of worker-side code; `test-worker-*.ts` serve the specs only and are never imported by `main.ts`. A heap ceiling bounds V8 memory only, and without a Windows Job Object a Hub killed without its shutdown relies on stdin closing; `src/db/sqlite-vec.ts` the hash-pinned optional vector library probe (`unavailable` is a state, never a failure). `npm run check:hub-capabilities` runs the built Hub's `self-test` and asserts FTS5, vector and worker re-spawn.
- `src/secrets/` (32-SS1, Milestone 831) the machine-bound secret store: closed `HUB_SECRET_PURPOSES`, per-purpose DPAPI entropy and file under `<configDir>/secrets/` (mode-0600 file on Linux), presence-only `status()`, never in a backup or diagnostics; importers are an explicit allowlist in `secrets.spec.ts` and never request handlers.
- `src/savesphere-db/` (32-SS1, Milestone 832) the SaveSphere content store `data/savesphere.db`: `openSaveSphereDb(paths)` (own numbered `migrations/`, 0001-platform, 0002-blobs, 0003-queue, quick-check, pre-migration copies in `data/pre-migration/savesphere`, reader fence, extension loading off by default) and `audit-outbox.ts` (`appendAuditOutbox` inside the content transaction, `drainAuditOutbox` into `dude.db` audit after commit and at start, deduped). Never `ATTACH`ed to `dude.db`. `backup/snapshot.ts` classifies every table of both databases as scrubbed or kept (`backup/classification.spec.ts`).
- `src/blobs/` (32-SS1, Milestone 833) the content-addressed `BlobStore` (`blob-store.ts` interface, `local-blob-store.ts` writing `storage/blobs/<aa>/<bb>/<sha256>` through `storage/staging/*.part`, streaming only, strict hex hashes), the `savesphere.db` catalogue and reference counts (`registry.ts`, migration 0002), the `gc`/`backup` blob lease (`lease.ts`), `verifyBlobBatch` and the two-step mark-and-sweep GC (`blob-gc.ts`, ConfirmationStore, `blob-gc.confirmation-boundary.spec.ts`). Only GC deletes a blob; the queue runs `blobs.verify` and `blobs.staging-sweep` on a schedule (Milestone 834) and the admin methods register the GC job later.
- `src/queue/` (32-SS1, Milestone 834, PD-147) the durable job queue over `savesphere.db` `jobs` (migration 0003, scrubbed from backups): `job-queue.ts` (`enqueue` with an optional idempotency key unique among queued or running jobs, atomic lease `claim`, `heartbeat`, `complete`, `fail` with exponential backoff to `dead`, `release`, `recoverExpired`, `prune`, `status`; every holder-side change names the lease owner so a stale worker cannot touch a recovered job; a claim counts as an attempt, so a crash mid-job retries and eventually dead-letters; `failed` is the non-retryable end state), `job-kinds.ts` (the closed `JOB_KINDS` list and the handler declarations, `inline` or `worker` with a timeout and, for workers, a memory limit; later phases add their kind and handler here), `handlers.ts` (`noop.echo`, `blobs.verify`, `blobs.staging-sweep`, all inline), `queue-runner.ts` (poll, concurrency, lease heartbeat, recovery at start and every 60 s, scheduled enqueues, reports into the job registry through each handler's `hubJobId`) and `queue-runtime.ts` (assembled by `run` only when `savesphere.db` exists). Payloads never hold a credential-looking key and `last_error` is redacted and cut to 300 characters (`redact.ts`).
- `src/provisioning/` (32-SS1, Milestone 835, PD-118, PD-153) the idempotent provisioning engine behind `dude-hub provision`, the admin methods `provision.run` and `provision.status` (`admin/provisioning-methods.ts`, admin pipe only, no confirmation token because a run is additive, audited as `provisioning.run` through the `audit_outbox` in the same transaction as the run record in `savesphere.db` meta) and `GET /api/v1/provisioning` (`routes/provisioning.ts`, owner cookie or bearer, read-only, `no-store`, no audit; a request handler gets only the service's `status()`, never the secret store). `provision(paths, options)` is single-flight per data directory and `checkProvisioning` never creates `savesphere.db`. A component is `{id, core?, provision?, check}` (`types.ts`) registered with `registerProvisioningComponent` from `components/index.ts`; ids are the closed `HUB_PROVISIONING_COMPONENT_IDS` (`tunnel`, `oidc`, `power` and `backup` are reserved and absent until their milestones, never faked). Built in: `content-store`, `fts`, `vector` (`unavailable` is by design, never an error), `blob-store` (round trip in a throwaway scratch store, no residue), `cache` (`HubPaths.cacheDir` = `storage/cache`, bounded by `DEFAULT_CACHE_MAX_BYTES`, swept oldest-first), `queue` (a `noop.echo` job against an in-memory copy of the migrations, never the live `jobs` table), `workers` and `secrets` (presence only; the expected purposes are kept in the content store's `meta`, which backups keep, while the secrets themselves never travel, so a restore shows `needsReentry`). `deriveOverall` (`state.ts`) gives `not-provisioned`, `needs-provisioning` (no run recorded, another Hub identity, a required directory gone or a secret to re-enter), `needs-attention`, `degraded` or `ready`. Details and next actions are redacted, capped sentences with no absolute path; `dude-hub provision status` exits 0 for ready or degraded, 1 otherwise, 2 for usage or a Hub that is not running. The CLI sends no secret in argv; the wizard's secrets (Milestones 837 and 853) will arrive as an optional `secrets` parameter read from standard input.
- `src/supervisor/` (32-SS1, Milestone 836) the generic supervisor for long-lived child processes (`createSupervisor`; nothing in it knows about Cloudflare). `prepare()` builds the whole command before EVERY launch (command, args, cwd, the COMPLETE child environment, the secret values to scrub, an optional readiness probe), so secrets are re-read and pins re-verified on each automatic restart; a refused `prepare` is `failed`, never retried. Spawned `shell:false`, `windowsHide`, stdin ignored. Crash policy mirrors `apps/desktop/device-store/agent-host.ts`: restart after 500, 2000, 8000 ms, `failed` on the 4th crash within 2 minutes (`crashed-repeatedly`), only an explicit `start()` clears it. A readiness probe polls (default every 1 s); a launch not ready within the start timeout is killed and counted as a crash; a child that stops answering after being ready turns `ready` false without a restart. `stop()` sends the polite signal, waits the grace period, then `taskkill /T /F`. Output goes to a bounded in-memory ring (`log-buffer.ts`: 200 lines, 64 KiB, 2048 characters a line) and every line is redacted before it is stored (`redact.ts`: the literal secret values, `TUNNEL_TOKEN=`/`--token` forms and the `eyJ...` connector-token shape; lines are stored only once complete so a split token is still caught; a cut line drops a dangling token start); `status()` and `logs()` carry no env, no argv and no path. Children outliving the Hub: Node cannot create a Windows Job Object without a native addon, so the chosen approach is a pid file (`pidFile`, written on spawn, removed on exit) plus an orphan sweep at `start()` that kills the recorded pid ONLY when its image path (CIM through PowerShell on Windows, `/proc` on Linux) equals `expectedImagePath`, so a reused pid is never touched; `killNow()` is the synchronous last resort for a process `exit` handler. Limit: a Hub killed outright leaves the child running until the next Hub start (or the WinSW service stop kills the process tree); there is no kill-on-close guarantee. Nothing is wired into `run.ts` yet.
- `src/tunnel/` (32-SS1, Milestone 836, PD-142) `cloudflared.ts` builds the supervised connector: `tunnel --no-autoupdate --metrics 127.0.0.1:<free port> run`, the connector token (secret purpose `tunnel.connectorToken`) ONLY as `TUNNEL_TOKEN` in an allowlisted environment (`CLOUDFLARED_ENV_ALLOWLIST`; Windows itself still adds its baseline variables such as `PATH` to any child), the executable hashed against `CLOUDFLARED_SHA256` before every start (`binary-hash-mismatch` refuses, before the secret is even read), readiness from `GET /ready` on the metrics port, pid file `run/cloudflared.pid`, working directory `run/`. Windows only (`unsupported-platform` elsewhere, PD-141). ## Adding or changing a route

1. Add TypeBox schemas to `@dude/contracts/hub` and register the route with them; declare its credential type and audit event (the audit event list is closed; add to it deliberately).
2. Add the matching method to `@dude/api-client`; `api-client-parity.spec.ts` must pass.
3. Mutating routes get Origin/Fetch-Metadata/CSRF handling by credential type; destructive or authority-changing routes use the ConfirmationStore and need a confirmation-boundary spec registered in the high-consequence gate.
4. Sync routes (Phase 31D) live in `src/server/routes/sync.ts`. They use device credentials (the owner session only for `summary` and the environment clear), enforce `SYNC_POLICIES` and the setting-key scope check on every operation, and never put payloads in audit events. The environment clear uses the ConfirmationStore and needs a confirmation-boundary spec. Still no other public record endpoint or import path.

5. Web routes (Phase 31E) live in `src/server/routes/web-records.ts` under `/api/v1/web` (attach, snapshot, changes, push, state, access). They are cookie-session only (bearer and device credentials get 401), carry CSRF and Origin checks, reuse the sync contracts and `commitCanonical` with the browser device row as the acting device, enforce per-category web access, and never put payloads in audit events. A browser row is attribution, never a credential: it must not be able to obtain a device token, enroll, be recovery-trusted or block pin rotation.
6. Static and sandbox serving: `/sandbox/*` pages carry their own CSP and `frame-ancestors 'self'`, and those headers must also be sent on 304 responses (a 304's headers merge into the cached response, so the app's `X-Frame-Options: DENY` would otherwise block the frame). The page CSP never contains `'unsafe-eval'`. Only `/assets/vendor/pyodide/*` is CORS-readable. The static handler never rewrites `/api/*`.
