# AGENTS.md — apps/web/src/app/core/

This directory is the tool-agnostic framework: `registry/` (metadata, search, route generation), `persistence/` (per-tool storage policy), `workers/` (Worker request/result/cancel contract), `connectivity/` (online/offline + update-available signal), and `routing/` (the one root route table). Phase 30I added `home-layout/` (the user-designed Home's grid engine, layout store and panel-manifest helpers; see its own `AGENTS.md` — like everything here it names no panel kind or tool id). Phase 30K added `appearance/` (the pure appearance model and sanitizer, `AppearanceService` — `local`, live across tabs, one `data-*` attribute per axis on `<html>`, the `theme-color` meta, the desktop native-theme sync and the `revision` signal color-reading code re-reads on — the standalone `*.dude-theme.json` file, and the generated `appearance-axes.generated.ts`; the inline pre-paint script in `apps/web/src/index.html` mirrors its resolution, and `appearance-prepaint.spec.ts` keeps the two in sync). Phase 26 added `offline/` (cache readiness/repair), `share/` (URL input handoff), `backup/` (portable bundles), `pwa/` (install), and `parity/` (registry-wide tests). Keep all of these registry-driven; per-tool exceptions and fixtures live beside the tool, not in core.

## The rule

**No file in this directory should ever know a specific tool by name or ID.** Every tool interacts with `core/` only through `TOOL_DEFINITIONS` (`registry/tool-definitions.ts`) and the generic services here (`PersistenceService.signal(...)`, `WorkerClientService.run(...)`). If adding or modifying a tool seems to require editing something in `core/`, that's an architecture gap, not something to work around — see `/ADDING_A_TOOL.md`'s opening note.

## Persistence (Phase 31B)

`persistence/` is no longer just localStorage: `PersistenceService` keeps synchronous signals over an in-memory cache and resolves each key's data scope on write (`resolveKvScope` in `@dude/persistence`: a manifest `settingScopes` override, indexed once from the generated registry in `persistence.service.ts`, else `SETTING_DEFINITIONS`, else the policy rule). `main.ts` awaits a **boot snapshot** (`device-store/boot-snapshot.ts`) before `bootstrapApplication` (not an app initializer: those run concurrently and would race `AppearanceService`); the desktop backend (`device-store/device-kv-backend.ts`) debounces key/value writes 1 s, commits journaled settings immediately and answers main's flush request, while the web backend is browser storage. `local-backend-registry.ts` lets `createStorageBackend('local')` find the active backend lazily. Entity collections (favorites, pipelines, user scripts, projects, workspace templates) go through the `ENTITY_STORE` token (`entities/`): saves are async, optimistic with rollback, and journaled ones commit the row and its outbox op together in the desktop store; the store, not the renderer, decides what journals. History and network runs are repositories (`history/history.service.ts`, `platform/network-run-history.service.ts`). `device/` holds `DeviceIdentityService` (web installation ID, skipped by Clear all data), the store-health service behind the degraded banner and the reset service. Secrets go through `SecretsService` by purpose and are never readable. Do not add `storageMigrations`, `moveLocalValue` or `migrateX`: shapes evolve through `@dude/persistence` codecs. `sync/` (Phase 31D) holds the `SYNC_PORT` contract, its desktop adapter, `SyncStatusService` (an app initializer feeding the shell indicator and Settings › Sync) and `RemoteChangesService`, which applies records the Agent has already merged into the entity collections and key/value backend (`applyRemote`); the renderer never merges, pushes or holds a Hub credential. `hub-web/` (Phase 31E, `hostKind === 'hub-web'` only, never imported by Pages or desktop code paths; the api-client stays out of those bundles) holds the Hub web boot (attach and snapshot before `bootstrapApplication`), the Hub kv backend and entity collections that replace the browser backend for synced categories, the realtime client, the browser `SyncPort` adapter and the sign-out wipe. Rules: shared writes are online-only (refused and rolled back with a notice while the Hub is unreachable; any 5xx counts as unreachable), a real merge conflict opens the Keep Hub / Keep mine / Keep both dialog (there is no outbox), nothing private is written to browser storage or the service worker cache, and sign-out wipes the origin through `@dude/persistence`'s origin wipe except the public service worker caches.

## Changes here are framework-layer, not tool-layer

A change in `core/` affects every tool at once. Treat it with more scrutiny than a tool addition:
- It gets its own git milestone/commit, separate from any tool commit (see `/AGENTS.md`'s git convention).
- Run the full test suite (`npm test` + `npm run test:e2e`), not just the affected tool's spec — `tool-search.spec.ts` and `tool-registry.service.spec.ts` iterate the real `TOOL_DEFINITIONS` array and will catch a lot, but a `core/` behavior change can break tools that never touch the modified file directly (e.g. a `PersistenceService` policy change affects every tool using `session`/`local`).
