# AGENTS.md — apps/web/src/app/shell/

Sidebar, deck (Home), command palette, and root layout. This is the "framework, not a tool list" part of DUDE (README's "Architecture" section, `DUDE_PRD.md` §9).

Home vs Browse Tools vs Sidebar vs Command Palette responsibilities, the panel-kind contract, layout persistence and dashboard/chart/table rules: see `deck/AGENTS.md` ("Home / Workbench shell contract").

## The rule

**Nothing under this directory contains a hard-coded tool ID.** Every list here (sidebar entries, deck cards, command-palette results) is derived at runtime from `TOOL_DEFINITIONS` (`apps/web/src/app/core/registry/tool-definitions.ts`) via `ToolRegistryService`. If you're editing a component here to special-case a specific tool by ID or route, stop — that's the exact failure mode the registry pattern exists to prevent, and it means the fix belongs in `tool-definitions.ts` or the registry service instead.

Adding, removing, or reordering a tool should never require touching this directory. If it does, treat it as a bug in the registry/shell contract, not a one-off exception — see `/ADDING_A_TOOL.md`.

## The deliberate exceptions: `pipelines/` and `smart-paste/`

`apps/web/src/app/shell/pipelines/` (the Pipelines list/builder pages) and the "Pipelines" sidebar link in `sidebar.html` are new shell surface area sanctioned by `DUDE_PRD.md` §21 Phase 21 Item 2 — composing tools into a chained workflow changes what a `ToolDefinition` means, not just adds one, so this is one of the roadmap items explicitly allowed to add to `shell/`/`core/`. It still honors the rule's spirit: nothing in `pipelines/` hard-codes a specific tool id — a pipeline step's `toolId` is user-selected data, resolved generically through `ToolRegistryService`/`PipelineStepRegistryService`, the same way `ToolShell` resolves the current tool via `getByRoute()`. Pipelines are not a 278th tool: no category, no `TOOL_DEFINITIONS` entry, no `buildToolRoutes()` entry — see `apps/web/src/app/core/pipeline/AGENTS.md`.

`apps/web/src/app/shell/smart-paste/` (the Smart Paste page) and the "Smart Paste" sidebar link are the second such exception, sanctioned by `DUDE_PRD.md` §21 Phase 21 Item 3 for the same reason: recognizing pasted content and routing to the matching tool is cross-tool discovery infrastructure, not a 278th tool. `PASTE_DETECTORS` (`packages/tool-engine/src/core/paste-detect/paste-detectors.ts`) is a hand-maintained array of `{toolId, test}` entries rather than a per-tool convention file — see `apps/web/src/app/core/paste-detect/AGENTS.md` for why that differs from the Pipelines precedent. As with Pipelines, no category, no `TOOL_DEFINITIONS` entry, no `buildToolRoutes()` entry, and every tool it can navigate to is resolved generically through `ToolRegistryService.getById()` — a detector's `toolId` is just a string key into the registry, never a hard-coded branch.

`apps/web/src/app/shell/workspace/` (tabs, resizable panels, and — from Milestone 292 — a scratchpad drawer) is the third such exception, sanctioned by `DUDE_PRD.md` §21 Phase 21 Item 4: a multi-tool tab strip and panel layout change what "the shell's content area" means, not a 278th tool. See `apps/web/src/app/shell/workspace/AGENTS.md` for why it needed a new dynamic-mounting mechanism (`ToolHost` + `NgComponentOutlet`) instead of named router outlets, and `apps/web/src/app/core/workspace/AGENTS.md` for the shared `<id>.workspace-step.ts` adapter convention it and Local History both build on.

`apps/web/src/app/shell/history/` (the History feed) is the fourth such exception, sanctioned by `DUDE_PRD.md` §21 Phase 21 Item 5: a cross-tool history feed is discovery/recall infrastructure spanning every tool, not a 278th tool. See `apps/web/src/app/shell/history/AGENTS.md` and `apps/web/src/app/core/history/AGENTS.md` for the eligibility rule and storage design.

`apps/web/src/app/shell/quick-run/` (the `/quick-run` route, "Quick Run" in the sidebar/command palette) is the fifth such exception, sanctioned by `DUDE_PRD.md` §21 Phase 24 Item 12 (the PRD's own "Quick Actions," renamed to avoid colliding with the already-shipped Electron feature of that name — see `apps/desktop/hotkey-bridge.ts`). Running a tool's transform without navigating into its full workspace is cross-tool execution infrastructure, not a 278th tool: no `TOOL_DEFINITIONS` entry, no category. It executes via the exact same `PipelineStep.run(input)` contract Pipelines already uses, scoped to text-accepting steps only — see `shell/quick-run/quick-run-list/quick-run-list.ts`'s own doc comment.

Two other Phase 24 shell surfaces are new *directories* but deliberately extend an already-sanctioned exception rather than adding a new one: `apps/web/src/app/shell/workspace/template-gallery/` (Workspace Templates, Item 11) extends the `workspace/` exception above, and `apps/web/src/app/shell/history/recents-tab/` (Unified Recents, Item 13) extends the `history/` exception above — see `core/workspace/AGENTS.md` and `core/recents/AGENTS.md` respectively. Neither gets its own numbered entry here.

Two further Phase 24 additions touch shell-adjacent files without any new exception at all, since neither adds a hard-coded tool id or a new top-level surface: `apps/web/src/app/shell/deck/` (Deck, the home route) grew a paste/drop hero and Recently-Used/Favorites/Pinned-Pipelines rails above its existing category grid (Item 1, via `shared/components/paste-detect-panel/` and `shared/components/smart-file-drop-zone/` — both registry-driven, no hard-coded tool ids); and `apps/web/src/app/shell/layout/shell-layout.ts` mounts `shared/components/ambient-paste-chip/` once, globally (Item 2) — a `shared/` component, not a `shell/`-owned one, following the exact same reasoning `OfflineBadge`/`UpdateBadge` already established for other globally-mounted, registry-agnostic UI.

`apps/web/src/app/shell/projects/` is the sixth sanctioned exception, added in Phase 25 Item 1. A Project is a named reference bundle of workspace layout and pinned pipeline ids, not a tool or an IDE project. The gallery is a shell route because it manages these cross-tool references; it never hard-codes a tool id. See `apps/web/src/app/core/project/AGENTS.md`.

`apps/web/src/app/core/deep-link/` and its one `ShellLayout` mount form the seventh Phase 25 exception. Links resolve tool ids through `ToolRegistryService` and saved layouts/pipelines through their owning stores; the shell never contains a tool-specific route branch. Main-process protocol handling forwards raw strings only.

`apps/web/src/app/shell/settings/` (the `/settings/:section` and `/settings/tools/:toolId` routes, pinned to the sidebar footer) is the eighth exception. Settings used to be a `developer`-category tool, which forced special cases everywhere (tool counts, README/SECURITY generators, pipeline coverage, hard-coded `getById('settings')` lookups in `core/`). App-wide preferences aren't a tool, so it is now a shell destination: core sections (`settings-sections.ts`, one component each under `sections/`) are hand-listed app-level panels, and the "Tools" group is generated from manifests' optional `settingsSection` declaration (`ToolRegistryService.settingsSections()`), so a tool contributes its own settings panel without touching this directory. Its secure-local/`local` storage keeps the legacy `'settings'` namespace (`core/persistence/app-settings.ts`) because `apps/desktop/llm-bridge.ts` reads `dude:v1:settings:llm*` directly — that string is a storage namespace, not a tool id.

Settings › Appearance (`sections/appearance-settings.*`, `/settings/appearance`, Phase 30K) is one of those hand-listed core sections, inside the eighth exception rather than a new one. It renders its rows from `APPEARANCE_AXES` (`core/appearance/appearance.model.ts`, fed by the generated `appearance-axes.generated.ts`) and writes only through `AppearanceService`; it also hosts theme-file Export/Import (preview, then Apply). The Onboarding wizard (`onboarding/`) has an Appearance page (theme, density, contrast) right after Welcome; its steps are page ids, not indices, so pages can be added without renumbering. These two are the only appearance entry points by design (`DUDE_PRD.md` Phase 30K): don't add palette commands or a sidebar toggle. Everything under this directory must stay token-only in every theme; `scripts/check-design-tokens.mjs` runs its full rule set here, and see `apps/web/src/app/shared/AGENTS.md`'s appearance rules.

`apps/web/src/app/shell/browse-tools/` (the `/tools` route) is the ninth exception, sanctioned by `DUDE_PRD.md` §21 Phase 30A.1: the complete tool inventory needed a dedicated, searchable/filterable/sortable catalog surface once Deck stopped being allowed to treat the full registry as its default content (Phase 30's product rule). It still honors the rule's spirit — every row is resolved generically through `ToolRegistryService`/`FavoritesService`/`UsageService`, nothing hard-codes a tool id, and no `TOOL_DEFINITIONS` entry or `buildToolRoutes()` entry exists for it (`core/routing/app.routes.ts` wires it as a plain sibling route, the same way as the other eight exceptions). The pure filtering/sorting/ranking logic it depends on lives in `core/registry/browse-tools-*.ts`, not in this directory, so it stays independently unit-testable and reusable by Phase 30D/30G. Deck's own "Browse all tools" grid is intentionally left untouched by Phase 30A — see Phase 30D for when that changes.

`apps/web/src/app/shell/insights/` (the `/insights` route, "Insights" in the sidebar and as a palette "Go to" destination) is the tenth exception, sanctioned by `DUDE_PRD.md` §21 Phase 30H: a dense, local-only view of the user's own usage (7-day trend, category ranking, Top Tools, Recent Activity) is workbench infrastructure spanning every tool, not a 278th tool — no `TOOL_DEFINITIONS` entry, no category, no `buildToolRoutes()` entry (`core/routing/app.routes.ts` wires it as a plain sibling route). It honors the rule's spirit: every row resolves through `ToolRegistryService`/`FavoritesService`/`UsageService`/`UnifiedRecentsService`, and nothing hard-codes a tool id. `InsightsSection` is one composition rendered in full here and in `compact` mode on Home. It is a read-only view: `UsageService` remains the only recorder, and `UnifiedRecentsService.activityEntries` (not `entries`) feeds Recent Activity so a workspace tab's synthetic "now" timestamp never appears as activity. See `core/usage/AGENTS.md` for the daily-bucket schema and privacy contract.

`apps/web/src/app/shell/settings/sections/home-layout-settings.*` (the `/settings/home-layout` section) with `apps/web/src/app/shell/deck/home-canvas/` (the Home renderer) is the eleventh exception, sanctioned by `DUDE_PRD.md` §21 Phase 30I: a user-designed Home is presentation infrastructure spanning every feature, not a 278th tool — no `TOOL_DEFINITIONS` entry, no category, no `buildToolRoutes()` entry. It honors the rule's spirit twice over: neither `HomeCanvas` nor the editor names a panel kind. Panels are declared by feature-owned `<kind-id>.panel-manifest.ts` files assembled into `core/registry/panel-definitions.ts` (generated), so a later feature (Git status, running processes, …) contributes a panel through its own manifest without touching Home, Settings, or any other shell component; registering a tool never creates a panel on its own. See `core/home-layout/AGENTS.md` for the store, grid engine, and safety rules.

`apps/web/src/app/shell/hub/` (the `/hub/setup`, `/hub/sign-in` and `/hub/recover` routes) with `core/hub/` (the `HUB_ADMIN` port, its desktop/hub-web/unavailable adapters and `hubSessionGuard`) is the twelfth exception, sanctioned by `DUDE_PRD.md` Phase 31C and decision PD-035. Bootstrapping a Hub, signing in as its owner and recovering a lost password are environment-administration entry points, not tools: no `TOOL_DEFINITIONS` entry, no category, no `buildToolRoutes()` entry, and nothing here names a tool id. They exist only in the Hub-served web build (`hostKind === 'hub-web'`, chosen at build time by `core/platform/host-flag.ts` and the `hub` angular.json configuration): `hubWebOnlyMatch` (a `canMatch`) keeps the routes out of the Pages and desktop builds, and `hubSessionGuard` on the shell root redirects an unauthenticated Hub visitor to them while letting every other host straight through. The Environment & Hub, Devices, Security & Sessions and (Phase 31E) Endpoint & Exposure Settings sections are ordinary hand-listed core sections inside exception #8, filtered by `CoreSettingsSection.hosts`; Endpoint & Exposure is view-only (it renders the Hub diagnostics report and copyable elevated commands, never changes exposure). Backup & Transfer (Phase 31G) is likewise a view-only core Settings section within exception #8 (desktop and hub-web): it renders the Hub's backup status and copyable elevated `dude-hub backup` commands, and never creates, restores or transfers a Hub itself. On `hub-web`, sign-in, setup and recovery do a full page load so the Hub web boot runs signed in.

`apps/web/src/app/shell/sync-indicator/` (one `ShellLayout` mount, in the top-right badge stack beside the offline/update badges) with `core/sync/` (`SYNC_PORT`, the desktop adapter, `SyncStatusService`) and the Settings › Sync section (`settings/sections/sync-settings.*` plus `sections/sync/`, an ordinary hand-listed core section inside exception #8) is the thirteenth exception, sanctioned by `DUDE_PRD.md` Phase 31D and the 31D Settings/indicator decision in the Phase 31D plan: showing whether this device is in step with its Hub (synced / syncing / pending / offline / paused / conflicts / needs first sync / revoked) is environment infrastructure, not a tool. No `TOOL_DEFINITIONS` entry, no category, no `buildToolRoutes()` entry, and nothing names a tool id. The indicator renders on desktop once the device is enrolled and, from Phase 31E, on `hub-web` through the browser `SyncPort` (Live, Hub unreachable, Session expired, Reload needed); it links to `/settings/sync`; its text label is the accessible name and the only motion (a pulse while syncing) is `motion-safe:`. `SyncStatusService` is constructed by an app initializer in `app.config.ts` so the Agent's `onApplied` stream feeds `RemoteChangesService.apply` even if Settings is never opened. Conflict, quarantine and first-sync flows are preview-then-confirm (Destructive-Action Contract).

## Sidebar (`sidebar.ts`/`sidebar.html`) is framework, not a new exception

Phase 30B.1 rewrote the sidebar's tool list from an always-expanded wall of every tool under all 8 categories into a collapsed category index: one row per category showing its live `computeCatalogCounts()` count (reused from Browse Tools' `core/registry/browse-tools-counts.ts`, never a second count derivation), which both links into Browse Tools filtered to that category and independently caret-expands the old per-tool list inline (expand state started session-only; the *keep open* half persists since Phase 30I.3, see below). This is not a new sanctioned exception — the sidebar has always been part of the shell framework covered by this file's top-level rule — it's a UI/behavior change to an existing surface, still 100% registry-driven (no hard-coded tool id was added or removed). Phase 30I.3 later made the *keep open* half of expand state persistent (`'__sidebar__'`, read defensively): a category the user opened stays open next session, while the default stays collapsed and the active route's category still auto-expands. Phase 30L capped an expanded category at `SIDEBAR_CATEGORY_LIMIT` (15) tools plus the active tool, followed by an "All N … tools" link into Browse Tools, so the sidebar stays bounded as the registry grows (`shell/registry-scale.spec.ts` checks it at 500 and 1,000 synthetic tools). The compact Favorites/Recents sections above the category index are plain read-only views over `FavoritesService`/`UnifiedRecentsService`, the same services Deck's own rails already use, not a new store.
