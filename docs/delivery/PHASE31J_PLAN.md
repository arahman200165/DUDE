# Phase 31J implementation decisions

Status: in progress. Decisions PD-099–PD-115 were recorded at Milestone 787 and govern the Hub collaboration and realtime-depth work through the close-out (planned as 814). The [ROADMAP 31J entry](ROADMAP.md#phase-31j) sets the scope (presence, selected Yjs collaboration, realtime document updates, notifications/job status) and the exit gate (authorization, content consent and retention; privileged job execution stays in Phase 88). The Hub keeps a single owner and a single environment (PD-027), so "collaboration" here means the owner's own desktops, browsers and phone. Named participants, read-only participants, guest permissions and richer collaborative surfaces remain Phase 53.

- **PD-099 — Collaborative surfaces.** Yjs is used only for three surfaces: scratchpad snippets (each snippet's title and body), the `body` of a user script, and Markdown Workspace **Hub rooms**. Home text panels, pipeline definitions, projects, layouts, settings and favorites stay on the existing record policies (PD-041); Yjs never becomes a generic replication protocol. Every other synced entity keeps its current conflict policy.
- **PD-100 — Collaboration transport and protocol 3.** Collaboration uses a separate WebSocket, `/api/v1/collab`. It authenticates with the same credential classes as `/api/v1/realtime` (owner cookie, owner bearer, device token) before the upgrade, negotiates the same hello/welcome, and reuses the realtime close codes. JSON control frames (hello, subscribe, unsubscribe, heartbeat; welcome, subscribed, doc-error) travel next to binary frames laid out as `[channel][kind: 0 sync | 1 awareness][y-protocols payload]`, each with its own size and rate limits. `/api/v1/realtime` stays JSON-only and nudge-only (PD-034, PD-039). Both routes share one `@fastify/websocket` registration, because the plugin attaches to the server's single `upgrade` listener. `HUB_PROTOCOL_VERSION` becomes 3, and events introduced in 31J are sent only to sockets whose hello negotiated protocol 3 or later. Shipped Android builds reject any event outside their contract, so they are protected by this gate.
- **PD-101 — Persistence and materialization.** For each collaborative document the Hub keeps a compacted Y.Doc state plus a short tail of updates (migration 0010: `collab_docs`, `collab_updates`, `collab_snapshots`, `collab_bases`), and only the Hub seeds a document's initial content. A debounced materializer (2 s after the last edit, at most every 10 s) writes the plain JSON through `commitCanonical`, so the change feed, snapshots, consent filtering and every non-Yjs client (Android, an offline Agent outbox, older builds) keep working unchanged. Materialization enforces the 128 KiB record cap, and the Hub refuses a Yjs update that would push a document over it. Migration 0010 raises the reader floor, so a pre-31J Hub refuses the database rather than writing around the Y.Doc. Deleting or tombstoning the record deletes its collaborative state, and so does clearing the environment.
- **PD-102 — Merging non-Yjs edits.** A record write that changes a collaborative text field is merged three ways on the Hub: the base is the materialization stored for the writer's `basedOnRevision` (`collab_bases`), "theirs" is the live Y text, and "ours" is the incoming text (`mergeText3` in `@dude/sync`, built on diff-match-patch, with identical edits on both sides collapsed). The difference between the live text and the merged result is then applied to the Y.Text as an ordinary Yjs edit, so an edit that arrives both as a Yjs frame and as an outbox write is not duplicated. The push result gains `merged` (`{status, revision, current}`), which the Hub returns only to clients that declare `accept: ['merged']`; older clients still receive `conflict`. merge3 gains a `text` rule and a keyed-list rule (snippets keyed by `id`, with text merge on title and body), and `user-script.updatedAt` resolves as `max-iso`, so devices and the web conflict path merge the same way without Yjs.
- **PD-103 — Consent and authorization.** Collaboration on a document requires the same consent as syncing it. Scratchpad and user-script collaboration need the `scratchpad` or `pipelines` category to be enabled: on a device, through its reported category map and a completed first sync; on Hub web, through the environment web-access toggle. A new `collab-documents` category, off by default, gates persisted Markdown documents; it is optional in the state contracts, so a client that omits it reads as off. Only the owner's principals can subscribe; a device credential never gains owner rights. Revoking consent ends the subscription with `doc-error`, revoking a device or session closes the socket with 4003, and a transferred Hub closes it with 4004. The Hub rewrites the identity in each awareness update from the authenticated principal, so a client cannot claim to be another device.
- **PD-104 — Markdown Hub rooms.** Hub rooms are a third Markdown Workspace mode next to the LAN server and the BYO relay; both of those remain unchanged, and the relay stays ephemeral and separate (ROADMAP Phase 53). A room lives in Hub memory only, with at most 8 concurrent rooms of 8 participants each, and closes 5 minutes after its last participant leaves. "Keep on Hub" persists a room as a `markdown-doc` record, but only after a disclosure that names the destination and the retention and only while `collab-documents` is on. A kept document never expires automatically; it lives until the owner deletes it, like any other synced record.
- **PD-105 — History and retention.** A snapshot is taken when a document goes idle (2 minutes without edits) or its last session ends, at most once every 10 minutes and at most 200 per document, under an 8 MiB per-document cap, and snapshots are pruned after 30 days. The owner can preview a snapshot and restore it; a restore is applied as a new forward edit (the CRDT is never rewound), the current state is snapshotted first, and the restore is audited (`collab.history-restored`). The update tail compacts into the state, and `collab_bases` are pruned below the sync floor, always keeping the newest. All collaborative tables are included in backups and transfers.
- **PD-106 — Desktop relay.** In the desktop renderer, the Y.Doc and CodeMirror binding live in the renderer. The resident Device Agent opens the pinned collab socket with its device token and relays opaque frames over IPC (`dude:collab-hub:*`, sender-checked and byte-capped), so the Agent depends on neither Yjs nor `@dude/collab-doc`. The Agent opens a collab socket only when the device is online, has completed its first sync, has no reconcile or authority-changed flag, and the authority check holds. After a 10-second disconnect grace, the editor falls back to a local journaled save that syncs through the outbox; a fresh Y.Doc loads after the outbox drains.
- **PD-107 — Editor dependency.** CodeMirror 6 and `y-codemirror.next` replace the textareas of the three surfaces on every host, including GitHub Pages, and the LAN/relay Markdown client moves to the same binding. The editor is a lazily loaded shared component in `apps/web` only (never in a portable package), so the shell-mounted scratchpad drawer stays inside the PWA prefetch and Angular budgets. It is themed only through token CSS variables and re-reads them on `AppearanceService.revision()`. Collaborator colors come from palette tokens. Tab can always escape the editor. Yjs, y-protocols and lib0 become direct `apps/web` dependencies.
- **PD-108 — Presence.** The Hub counts every principal as online, including the browser rows of owner cookie sessions, and pushes `presence-changed` to owner views. Android needs no new code because it already counts as a device. Per-document awareness (participants, cursors, selections) is ephemeral and never persisted. Active-tool presence (which tool or shell destination a device is showing) is opt-in per device through the local-only setting `__device__:presenceShareActivity`, off by default; it uses a closed vocabulary of registry tool IDs and shell destinations, is held in Hub memory only, and is never audited.
- **PD-109 — Notifications model.** The Hub keeps notifications in a `notifications` table (migration 0009) fed by a closed list of producers: scheduled backups (failed, recovered, overdue), leaf and ACME renewals (renewed, failed), sync compaction failure, address changes, and the 31F security alerts through an audit observer. Each notification is deduplicated by a source key, so an address change produces one notification, not two. Read and dismiss state is stored per notification and, as with marking alerts seen, is not audited. Dismissed notifications are kept 30 days and every notification at most 90 days, with a cap of 500. Notifications are pushed as `notification` events, removed from backup snapshots, and carry no record content.
- **PD-110 — Notification reader grant.** A desktop can receive notifications without an owner session through a per-device "notification reader" grant (`devices.notifications_access`). The grant is set by the owner with step-up, audited (`device.notifications-access-changed`), revocable, and allows only listing, reading and dismissing notifications plus receiving notification and job-status events. OS notifications on the desktop are opt-in per type (default off), raised by the main process from the device-local desktop preferences, and keep working while the window is closed to the tray.
- **PD-111 — Shell bell.** A notification bell with a panel becomes shell exception #14, shown on desktop and Hub web whenever an environment exposes notifications and absent on standalone and Pages hosts. It is themed only with tokens and is reachable by keyboard and screen reader. Settings › Environment & Hub gains a read-only "Hub jobs" card.
- **PD-112 — Read-only job status.** A closed `HUB_JOB_IDS` list (leaf renewal, ACME renewal, backup schedule, sync compaction, address watch, audit prune, plus the collaboration maintenance jobs) reports each job's last run, outcome, next due time and running state through `GET /api/v1/jobs`, with live `job-status` events. Per-job state is kept in meta `job_last:<id>` and scrubbed from backups. There is no "Run now", no queue and no job framework; owner- or device-initiated job execution stays in Phase 88.
- **PD-113 — Live views.** Clean remote merges are applied live in open editors (pipeline builder, script-editor fields other than the collaborative body, projects, home-layout editor), and conflicts still go to the inbox or dialog. Owner admin pages (Devices, Sync, Backup, Security alerts, Diagnostics, Jobs) refetch on a contentless `owner-view-changed {topic}` event, which goes to owner sockets and to protocol-3 desktop device sockets. `/api/v1/realtime` never carries record content (PD-039 stands).
- **PD-114 — Hub collaboration is environment infrastructure.** Hub collaboration sits behind a `HUB_COLLAB` port with desktop, Hub web and unavailable adapters, like sync, rather than being a platform capability. Tool manifests and the capability catalog (`collab-relay` keeps covering the LAN and BYO relay) are unchanged, and Pages reports Hub collaboration as unavailable.
- **PD-115 — Gate.** The exit gate is proved by `npm run test:hub` suites for collaboration authorization, consent, retention, history pruning, notification retention, the job-status contract and the WebSocket contract parity; `e2e/hub/60-collab.spec.ts` (two browsers co-edit the scratchpad, a script and a room, with presence, history restore, and the bell receiving a backup-failed notification); and `e2e/sync/30-collab.spec.ts` (a desktop through the Agent relay co-editing with a browser, then an offline edit merged on reconnect without an inbox entry or duplication). No `measure:collab` is required. Physical and installed passes owed at the close-out: two PCs co-editing over LAN and in public mode, the installed SEA/WinSW Hub and the Docker image, a real scheduled-backup failure reaching the bell and a Windows toast while signed out, NVDA on the editor and bell, cursor colors across themes and contrast modes, a real offline desktop edit and reconnect, restoring collaborative documents onto a second machine, a multi-hour Hub memory watch, and the phone shown as online.

## Deviations and implementation notes

### 2026-10-24, Milestone 803: editor dependencies (PD-107)

New direct `apps/web` dependencies (also listed in the root `package.json`, like the other application libraries). Editor packages are exact-pinned and were each published at least two weeks before this milestone; `yjs`, `y-protocols` and `lib0` keep the root's ranges and the installed versions.

| Package | Version | Why |
|---|---|---|
| `@codemirror/state` | 6.7.6 | Editor state, compartments, transactions |
| `@codemirror/view` | 6.43.14 | The editor view, theming, keymaps (6.43.15 is newer but only five days old) |
| `@codemirror/commands` | 6.11.1 | Default keymap and history (Tab is deliberately not bound) |
| `@codemirror/language` | 6.13.1 | Syntax highlighting |
| `@codemirror/search` | 6.7.2 | Find and replace in all three editors |
| `@codemirror/lang-markdown` | 6.5.2 | Markdown (GFM) highlighting; loaded only for Markdown editors |
| `@codemirror/lang-javascript` | 6.2.5 | User-script body; loaded only for script editors |
| `@lezer/highlight` | 1.2.5 | Highlight tags for the token-colored highlight style (already a transitive dependency; the boundary check requires a direct declaration for a direct import) |
| `y-codemirror.next` | 0.3.6 | Yjs binding: sync, remote cursors, undo manager |
| `yjs` / `y-protocols` / `lib0` | ^13.6.32 / ^1.0.7 / ^0.2.117 | Types and runtime the editor binding and the Markdown collaboration client share |

Transitive additions from `lang-markdown`/`lang-javascript` are the `@lezer/*` parsers, `@codemirror/lang-html`, `lang-css`, `autocomplete` and `lint`, `crelt`, `style-mod` and `w3c-keyname` (all MIT).

Implementation notes:

- `<app-code-editor>` (`shared/components/code-editor/`) is a thin component; `code-editor.engine.ts` is the only module that imports CodeMirror and is loaded through one dynamic `import()` in `code-editor.loader.ts`. A textarea renders first and is the permanent fallback if the chunk cannot load (offline first visit). In the production build the main bundle is 246.7 kB (raw) and the editor adds no code to it or to the shell chunk beyond a 5.6 kB component chunk. The lazy chunks are the engine (329.8 kB raw, 106.8 kB gzip), `lang-markdown` with its HTML/CSS parsers (102.0 kB, 38.4 kB gzip), and `lang-javascript` with `autocomplete` (120.4 kB, 44.3 kB gzip). They sit in the lazy `tool-chunks` cache group, so the 800 kB prefetch budget is unchanged (452.0 kB web, 444.1 kB hub-web).
- `valueChange` fires synchronously on every edit rather than debounced: the Markdown preview already rendered per keystroke, and a debounce would let the drawer and script forms lag behind the document.
- The Markdown LAN and relay client no longer needs a textarea-diff on typing: `MarkdownCollabClient` exposes `ytext` and `awareness`, calls `onInitialSync` once after the first sync message and the host seed, and the workspace binds the editor then. `computeTextDelta` stays for whole-text writes that do not come from the bound editor (opened file, Clear, plugin output, the textarea fallback). Remote edits no longer move the local cursor.
- Remote cursor colors are palette tokens: a peer sends a `colorSlot` (0-7) and each viewer maps it to a category token through its own theme; the engine hands `y-codemirror.next` a guarded awareness view that rebuilds every peer's `user` (name truncated, color from the slot), because the library writes `user.color` straight into a style attribute. Slots are picked from the client id, so two peers can collide (1 in 8). The name label uses `--dude-bg` text on the category fill (there is no `on-cat` token); the contrast of that pair is covered by the owed "cursor colors across themes and contrast modes" pass.
- The editor shows a focus outline of the theme's focus width, wraps lines, and never binds Tab or Shift+Tab; `Ctrl+F` opens the CodeMirror search panel inside the editor.
