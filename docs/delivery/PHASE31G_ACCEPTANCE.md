# Phase 31G implementation and acceptance evidence

Phase 31G (Milestones 700–719) delivers encrypted backup, restore and manual transfer for the self-hosted Hub: a passphrase-encrypted, verified `.dudebackup` file (manual or scheduled), an offline staged restore that gives the restored Hub a new identity and a higher authority epoch, a fence that retires the old Hub, re-attach pairing codes, a device reconnect that keeps local data and pending edits and ends in the first-sync preview, a rebase that never deletes history the Hub regressed past, a Hub web authority gate and a view-only Settings › Backup & Transfer. Decisions are PD-069 to PD-074 in the [decision log](../history/DECISION_LOG.md#phase-31g-implementation-decisions), with amendments recorded under PD-071, PD-072, PD-073 and PD-074; the milestone map and gotchas are in [Delivery History](../history/DELIVERY_HISTORY.md#phase-31g). The contracts are the "As built in Phase 31G" sections of [System](../architecture/SYSTEM_ARCHITECTURE.md#as-built-in-phase-31g-backup-restore-and-transfer), [Security](../architecture/SECURITY_ARCHITECTURE.md#as-built-in-phase-31g-backup-restore-and-transfer) and [Data and synchronization](../architecture/DATA_SYNC_ARCHITECTURE.md#as-built-in-phase-31g-backup-restore-and-transfer). A 31G desktop and Hub preview does **not** complete DUDE 2.0: the Android-inclusive release gate is Phase 31I.

## Implemented scope

- **Format and Hub backup (700–702, 704, 706–707)**: `@dude/hub-backup` is the portable `.dudebackup` format (a plaintext reader header, XChaCha20-Poly1305 over 64 KiB chunks with the nonce built from a stream id and counter and the header hash plus a final-chunk flag as associated data, the manifest inside the encryption, an NFKC-normalized passphrase, an injected KDF, random source and clock, a 512 MiB plaintext and 32-file ceiling). The Hub takes a `VACUUM INTO` snapshot, scrubs transient state from the copy (sessions, device tokens, challenges, pairing codes, setup state and per-run meta), writes `<name>.part`, re-opens and hash-verifies it and only then renames it into place; keys are Node Argon2id (64 MiB, 3 passes, 1 lane). Retention never deletes the newest file and does not run after a failed verification. `backup.create.preview|apply`, `list`, `verify` and `schedule.set|off|status` are admin-pipe methods behind the elevated `dude-hub backup create|list|verify|schedule`; a schedule keeps its folder, interval and retention in `hub.json` and a DPAPI-protected **derived** key (never the passphrase) on the Hub machine. The passphrase comes from `DUDE_HUB_BACKUP_PASSPHRASE`, standard input or a no-echo prompt, never a flag, and is never stored, logged or audited; nine `backup.*` events join the closed audit list.
- **Restore, transfer and fencing (701, 708–711)**: the Hub reports `authority_epoch` and `authority_state` (default 1 and active, no migration) as optional fields in `hello`, the device token response, the realtime welcome and sync responses (no protocol bump). `dude-hub backup restore` is offline and two-step (a hashed single-use token bound to the file; the phrases `REPLACE HUB DATA` and `THE OLD HUB IS GONE` compared exactly), moves replaced data to `backups/replaced-<stamp>/`, and writes a restored Hub with a new `hub_instance_id`, epoch = source + 1, every desktop device marked `needs_re_pair` with its key revoked (Hub migration 0008), transient state, `device_sync_state` and the TLS tables cleared and a sanitized `hub.json` (port and names kept; private mode, loopback, no proxy, ACME, schedule or `webRoot`). `backup create --for-transfer` retires the Hub: it answers `GET /api/v1/hello` and static assets only and everything else is 503 `hub-transferred` from the first request hook, with sockets closed 4004; `backup reactivate` returns it to service at epoch + 1. `POST /pairing-codes {reattachDeviceId}` creates a code only that device id can use; `GET /api/v1/backup/status` is the owner's read-only status.
- **Devices and browsers (703, 705, 712–713, 717)**: the device store keeps `hub_enrollment.authority_epoch` (migration 0005). The Agent checks `hello` at the start of every connect and in refresh, token, welcome and revoke confirmation: a different instance id, a transferred Hub or a lower epoch moves the connection to `authority-changed` and sync to `needs-reconcile` before any traffic, and a changed Hub is never read as a revoked device. A persisted `sync_reconcile_required` flag (`cursor-ahead`, `epoch-lower`, `history-regressed`) blocks sync the same way, and the rebase refuses to delete or move the cursor when an acknowledged local entity is newer than the snapshot. One recovery snapshot is taken per changed authority (prefixes `authority-changed`, `sync-reconcile`, `rebase`, `reconnect`). `hub.reconnect` (`{pairingString, acknowledged: true}`) replaces the enrollment, resets only sync bookkeeping and leaves entities and the outbox alone; the first-sync preview (Merge, Use Hub, Keep local) decides. It is allowed from `offline`, `connecting`, `authority-changed`, `untrusted-tls`, `revoked` and `incompatible`, never from `online` or standalone. Hub web boot judges the Hub against the local-only `__device__:hubAuthority` record, shows a blocking notice for a transferred or older Hub and locks on 503 `hub-transferred` or realtime close 4004.
- **UI (712, 714, 717)**: Settings › Backup & Transfer is view-only on desktop and Hub web (authority, last backup, schedule, default folder with a same-machine disclosure, devices needing re-pair, copyable elevated commands, the unrecoverable-passphrase warning); Settings › Devices shows a "Needs re-pair" badge and a "Create re-pair code" action; Settings › Environment & Hub has the reconnect panel, collapsed under "The Hub moved to a new address?" when the Hub is unreachable. Nothing in any window creates, schedules or restores a backup.
- **End-to-end and measurement (715–716, 718)**: `e2e/hub/50-backup-transfer.spec.ts` (six serial real-process tests), `e2e/sync/20-restore-reconnect.spec.ts` (eleven tests with two real desktops) and `npm run measure:backup`.

## Measurements

`npm run measure:backup` runs the release Hub bundle and the real `dude-hub` CLI (not the test bundle, so the rate limits are the production ones). Machine: Ryzen 9 5900X (24 logical processors), 31.9 GiB, Windows 11 Pro 10.0.26200, Node 24.21.0. These are a development-machine record, not guarantees. Argon2id 64 MiB, 3 passes, 1 lane: median 127.7 ms (123 to 134, five runs).

| Database | small | medium | large |
|---|---|---|---|
| Content | small fixture | 10,000 records, 5,000 audit events (17.8 MiB) | 100,000 records, 20,000 audit events (170.1 MiB) |
| `backup create` apply | 548 ms | 1,130 ms | 7,394 ms |
| `backup create` preview | about 200 ms | about 200 ms | about 200 ms |
| Backup size | 0.2 MiB | 17.7 MiB | 168.4 MiB (ratio 0.99: not compressed) |
| `backup verify` | 318 ms | 611 ms | 3,021 ms |
| `backup restore` preview plus apply | 788 ms | 1,297 ms | 5,747 ms |
| Restored Hub answers `hello` after start | 637 ms | 703 ms | 835 ms |
| Hub working set, idle | 91 to 93 MiB | 91 to 93 MiB | 91 to 93 MiB |
| Hub peak during create | 157.5 MiB | 218.5 MiB | 950.5 MiB |
| Hub peak during verify | 158.7 MiB | 183.4 MiB | 1,104.3 MiB |
| Restore CLI peak | 130 MiB | 166 MiB | 748 MiB |

Event loop on the large database (a `hello` request every 20 ms): idle p50 3.0 ms, p95 4.0 ms, max 4.4 ms; during `backup create` apply p50 3.6 ms, p95 2,512 ms, max 2,661 ms; during `backup verify` max 2,528 ms. The pause is mostly synchronous seal and open work plus a pair of `VACUUM INTO` calls of about 1.6 seconds, not only the vacuum. The medium size was not loop-tested.

**Limit, stated plainly.** The whole-buffer design (PD-069) costs about five times the database in Hub memory (950 MiB for a 170 MiB database; this extrapolates to roughly 2.7 GiB at the 512 MiB plaintext ceiling), and a live Hub stalls for about 2.5 seconds during a backup or a verify at 170 MiB. That is fine for typical Hub sizes and a scheduled backup can run at a quiet hour, but a streaming design is a later improvement.

## Known limitations and owed manual passes

- **Real second-machine pass** owed: restore on another owned physical machine with real devices re-pairing over the LAN. The e2e drills use a second data directory on one machine (the transfer drill runbook below is this pass).
- **Installed-service and elevated runs** owed: `backup restore` and `backup reactivate` against a real Windows service and the NSIS installer, `backup create` against a real service, and the DPAPI-protected schedule key on a real account (the specs use a foreground Hub, the admin pipe and an injected protector).
- **A real device pointed at a restored Hub across machines with a new certificate** owed: the reconnect flow also handles the resulting `untrusted-tls`, but it was exercised only on one machine.
- **First CI runs** owed for the new suites: `e2e/hub/50-backup-transfer.spec.ts`, `e2e/sync/20-restore-reconnect.spec.ts` (a local Windows gate, not in CI), `@dude/hub-backup` in `check:portable` and the Dockerfile `COPY` lines for `packages/hub-backup`. The Docker images were not built locally (no Docker daemon in this environment); `check-dockerfiles` passes.
- **Epoch-lower refusal against the OLD Hub** is covered by unit and in-process specs only: in the real-process drill the instance-changed check outranks it.
- **A same-instance rollback by file copy** (an operator replaces the database file with an older copy) can still receive one push batch before a device detects the regression; a restored Hub cannot, because its device keys are revoked.
- The e2e drill **reuses the old TLS directory** for the second Hub so it can observe `authority-changed` at the old address. A fresh certificate at the old address makes devices report `untrusted-tls` until re-paired, which the reconnect flow also handles.
- **Scheduled backups keep a DPAPI-protected derived key on the Hub machine** (never the passphrase). This is a deliberate deviation from "the secret is never stored" (PD-074), as strong as DPAPI LocalMachine protection, and the same machine as the data: it protects against a leaked backup file, not against a compromised Hub host.
- **Whole-buffer backups** cost about five times the database in Hub memory and stall a live Hub for about 2.5 seconds at 170 MiB (see Measurements). Streaming and compression are not implemented.
- **No automatic failover**, election or standby replication; transfer is manual. No UI creates, schedules or restores a backup. No recovery-key file: losing the passphrase makes a backup unrecoverable. Certificates, the local CA and ACME account keys are never in a backup, so a restore always needs LAN, proxy and public exposure re-enabled with the usual elevated commands.
- `hub-integration.spec.ts` has a pre-existing flake when a random confirm token starts with `-` (parsed as a flag), the web build prints an unrelated NG8113 warning, and `npx tsc -p e2e/tsconfig.json` has pre-existing errors; none was introduced by Phase 31G.
- The remaining owed [31B](PHASE31B_ACCEPTANCE.md), [31C](PHASE31C_ACCEPTANCE.md), [31D](PHASE31D_ACCEPTANCE.md), [31E](PHASE31E_ACCEPTANCE.md) and [31F](PHASE31F_ACCEPTANCE.md) passes remain owed.

## Transfer drill runbook

This is the owed real second-machine pass. Use two machines you own, the old Hub machine (OLD) and the new one (NEW), and at least one real enrolled desktop. Run the elevated steps from an elevated prompt.

1. **On OLD**, make the transfer backup: `dude-hub backup create --for-transfer --folder <folder>`. Run it once to see the preview (nothing is written), then re-run with the same `--for-transfer` and `--folder` plus `--confirm <token>` within 60 seconds and enter the passphrase twice. After the verified write OLD is retired.
2. **Carry the file and the passphrase separately** to NEW (the file may travel by any medium; never put the passphrase beside it). Without the passphrase the file is unrecoverable.
3. **On NEW**, stop any Hub (`dude-hub service stop`) and install the same or a newer Hub version.
4. **On NEW**, restore in two steps: `dude-hub backup restore --file <path>` (preview, nothing changes), then repeat with `--confirm <token>`. A non-empty data directory also needs `--replace "REPLACE HUB DATA"`. A backup made with `--for-transfer` needs no `THE OLD HUB IS GONE`.
5. **Start the Hub on NEW** and sign in with the **old owner password** (the owner credentials are restored). Note the new authority epoch in Settings › Backup & Transfer.
6. **Re-enable exposure on NEW** with the usual elevated commands: `dude-hub network lan on`, `network proxy on` or `network mode public` (the readiness gate runs again). Restore keeps only the port and names, and certificates are newly issued.
7. **For each device**: in the Hub web, Settings › Devices, press **Create re-pair code** on the row marked **Needs re-pair**; then on the device open Settings › Environment & Hub, expand **Reconnect** (shown under "The Hub moved to a new address?" when the old Hub is unreachable), paste the pairing string and acknowledge. The device keeps its data and pending edits.
8. **In the first-sync preview** on each device, choose **Merge** (it keeps the union of the device's and the Hub's edits).
9. **Verify OLD**: its Hub web shows the "This Hub was moved" notice, sign-in and sync are refused (503 `hub-transferred`) and a device pointed at it reports `authority-changed`.
10. **Verify NEW**: every device syncs live, edits made on one reach the others, and Settings › Backup & Transfer shows the new epoch and no device needing re-pair.
11. **Rollback**, only before step 4 has restored anything: on OLD run `dude-hub backup reactivate` (two steps) to return OLD to service at a higher epoch. After a restore has happened, NEW is the authority and OLD must not be reactivated.
