# Phase 32-SS1 implementation decisions

Status: in progress, started 2026-10-27 at Milestone 829. Decisions PD-141–PD-154 were recorded at Milestone 829 and govern the Hub platform work for SaveSphere (Milestones 829–857). They refine the program decisions PD-118–PD-124 ([SaveSphere program decisions](PHASE32SS_PLAN.md)) after owner Q&A and a feasibility review of the as-built Hub; where the two differ, the refinement wins, and the program decisions were reworded at the same milestone so no stale rationale remains (see [Deviations](#deviations-and-implementation-notes)). The [ROADMAP 32-SS1 entry](ROADMAP.md#phase-32-ss1) sets the scope and exit gate. Nothing here is an as-built claim until a milestone's evidence says so. The Hub keeps a single owner and a single environment (PD-027); guests arrive in 32-SS6.

A Phase 32-SS1 acceptance document (`PHASE32SS1_ACCEPTANCE.md`, Milestone 855) will record the automated exit gate and the owed live passes as a guided script, following the 31E–31J convention.

- **PD-141 — Windows first; the Docker image keeps working with a documented subset.** The tunnel, the power policy check and vector search are Windows-only. The Docker image keeps running the embedded stores, the blob store, the job queue, resumable uploads and backup v2 to local and S3-compatible destinations, and reports tunnel, power policy and vector search as "not available in this deployment" in the Docker section of the Hub documentation. `sea.isSea()` selects the worker spawn mode, so a Node-process Hub (Docker, foreground) and the single-executable Hub use the same worker code. `sqlite-vec` has no musl build, so the Alpine-based image reports "vector unavailable". No new workspace packages are added (the Dockerfile copy rules stay untouched); new Hub code lives under `apps/hub/src/`, format code under `packages/hub-backup`, and `jose` is declared in `apps/hub/package.json`.
- **PD-142 — The tunnel credential is an owner-pasted connector token; there is no Cloudflare API token.** The owner creates a remotely managed tunnel in the Cloudflare dashboard and pastes its connector token into the provisioning wizard (or the elevated `provision` run, over stdin, never argv). The token is stored DPAPI-protected in a new Hub `secrets/` module that generalizes `tls/ca-key-protector.ts` and `backup/schedule-key.ts` (per-secret entropy, an importer-boundary spec like `local-ca.spec.ts`). `cloudflared` is fetched by a hash-pinned script like WinSW, run with `TUNNEL_TOKEN` in its environment (never argv) and `--no-autoupdate`. Because the tunnel is remotely managed, its ingress rules and `originRequest` settings live in the Cloudflare dashboard, not on the Hub; the wizard shows the exact hostname and origin values the owner must enter, and the Hub cannot change them. PD-064 stands unchanged: the Hub stores no DNS-provider credential and no Cloudflare API token, and DNS routing for the tunnel hostname is the owner's dashboard action. The wording "proxy pins" in PD-120 is corrected accordingly (PD-143).
- **PD-143 — Tunnel trust: public-CA mode for the tunnel domain, a pinned loopback hop and tunnel-aware readiness.** Cloudflare terminates TLS at its edge with a certificate it rotates, so DUDE does not pin it. In tunnel mode devices (the Device Agent, the desktop and the Android Kotlin Hub client) verify the tunnel domain with the **public CA chain**, a new "public-CA trust" mode beside SPKI pinning, scoped to the configured tunnel domain and refusing any other host; the Hub's loopback hop is the only pinned connection (`cloudflared` verifies the Hub's loopback certificate against the Hub's local CA). Enrollment against the tunnel domain probes the trust mode instead of asking for an SPKI pin. A tunnel-aware readiness check set (the tunnel's `/ready` connected and healthy, no inbound port) replaces `public-firewall-rule` and `inbound-bind` in tunnel mode and leaves every other blocker unchanged. Turning the tunnel on is an elevated admin-pipe command (`network tunnel on|off`) that puts the Hub in the existing reverse-proxy mode (loopback hop, `publicOrigin`) behind the same typed-phrase gate and a confirmation-boundary spec, with the Cloudflare edge-TLS and terms disclosure. `www.<domain>` redirects to the bare domain in the Host guard. A forged `X-Forwarded-For` check runs against the stub `cloudflared`. Android ships the same trust mode in 32-SS1, with emulator acceptance.
- **PD-144 — The gating rule (PD-122 reworded): static assets are public; every API, websocket and admin route is gated.** The static web build (sign-in page, service worker, the precached offline shell, the Hub-offline page) stays public, because it must load before a session can exist and holds no owner data. Every API, websocket and admin route requires a session (owner cookie or bearer, device token, or from 32-SS6 a guest session) except a documented allowlist: sign-in and recovery, the OIDC callback, the Hub's existing unauthenticated `hello` endpoint, the token-only ingest path and, from 32-SS6, public share links. The SPA `hubSessionGuard` keeps every tool page behind sign-in, so the developer tools stay behind the session even though their code is a public asset. An enumerate-and-probe spec walks every registered route against a committed allowlist fixture and fails on any ungated route. The OIDC callback is a narrow GET exemption in `security/request-guard.ts` (the owner cookie is `SameSite=Strict`, so the session-less callback leaves a same-site follow-up that completes the sign-in or link). The Hub-offline page is a precached public asset used as the service worker's navigation fallback.
- **PD-145 — Sign-in: Google primary, the password can never be disabled.** The OIDC authorization-code flow with PKCE runs on `jose`, with `state`, `nonce`, a cached JWKS and verification of issuer, audience, expiry, nonce and signature. A Google identity binds by `sub` only after a signed-in round-trip; several of the owner's accounts can be linked, linking and unlinking need step-up, and the last linked account cannot be unlinked (`linked_identities`, migration 0011). Password and recovery sign-in sit under "Other ways" and can never be disabled by any setting or route. Failed callbacks count into `ip-block.ts`. Google unreachable shows an explanatory fallback to the password path. Link and unlink have confirmation-boundary specs, and the new audit events extend the closed list.
- **PD-146 — A separate `savesphere.db` with its own migrations, no `ATTACH`, and an audit outbox.** The SaveSphere content store is its own SQLite file with its own migration runner. `ATTACH` is not used, because a transaction across two WAL files is not atomic. Where an action must write both a SaveSphere row and an audit row, the audit event is written to an `audit_outbox` row in the same `savesphere.db` transaction and drained into `dude.db` on commit and at start (at-least-once, deduplicated by a key). Every table in both databases is classified scrubbed or kept for backups by a spec, with `SAVESPHERE_SCRUBBED_TABLES` beside `backup/snapshot.ts`. The Hub process is still the only writer of both files.
- **PD-147 — The queue runs Hub-internal work only; workers are isolated; vector search is proved, not built.** The durable queue (in `savesphere.db`) and its isolated workers run only Hub-internal work: blob verification, garbage collection, upload expiry, the restore drill, backup runs and later SaveSphere processors. Owner- or device-initiated privileged execution, a run-now for arbitrary jobs and a user-visible job framework remain Phase 88; `HUB_JOB_IDS` is extended with the internal jobs and stays read-only to clients. Workers are the Hub executable re-spawned in an internal worker mode (the single-executable application cannot run workers from a path), with a Node-process fallback chosen by `sea.isSea()`. SS1 provisions the schema slot for a vector index and proves that a pinned, hash-verified `sqlite-vec` library loads through `node:sqlite` `loadExtension` inside the single-executable application (an `allowExtension` option on `packages/sqlite-store/src/open.ts`); if it does not, or on Docker, the provisioning status reports "vector unavailable". FTS5 availability is proved in the same milestone. Milestone 830 is a go/no-go for both, and a failed proof is recorded here rather than worked around silently.
- **PD-148 — Blobs and uploads.** The local `BlobStore` is content-addressed by SHA-256 with refcounts, a verify job and mark-and-sweep garbage collection with a grace period; pruning or collecting unreferenced blobs is a two-step confirm (a `ConsequenceClass`-tagged preview and a single-use apply, with a confirmation-boundary spec). Uploads are a resumable route family with its own non-JSON body parser (the 64 KiB `HUB_BODY_LIMIT` is untouched elsewhere): sessions in `savesphere.db`, idempotent 8 MiB chunks by offset (below Cloudflare's request-body limit), a SHA-256 check before commit, no fixed size cap, a free-disk guard and an expiry job. An S3 blob mirror or tier is **deferred** (open item of PD-118 stays open after SS1); S3 is a backup destination only.
- **PD-149 — Ingest is a scaffold only.** SS1 adds `/api/v1/ingest/*` with the scoped, hashed ingest-token class (resolver, rate-limit bucket, audit events, gate-allowlist entry) and one `ping` route. Real capture channels are 32-SS3. Ingest tokens are **scrubbed on restore and must be reissued**, which resolves the open question recorded in the SaveSphere architecture ("whether ingest tokens survive a restore") now: a restored Hub never carries a capture credential from before the restore.
- **PD-150 — Backup v2: destinations, sequencing, retention and verification.** `@dude/hub-backup` gains a v2 format: a repository header with a wrapped master key (a passphrase change does not re-encrypt), an encrypted pack stream, a manifest, an HMAC-of-blob-hash dedupe key, `formatVersion` and `minReader` in the header and every manifest, and v1 files still restore. The engine snapshots both databases (with the scrub lists) first and takes the blob set from that snapshot under a GC lease; every backup is verified when written (verify-on-write) and counts only after that. Retention defaults to **7 daily, 4 weekly and 6 monthly**, pruned only by a two-step confirm, with mark-and-sweep blob garbage collection afterwards. A restore drill runs **monthly** as a job; a backup is **overdue at 2x its interval**, and overdue, failed and drill-failed backups raise notifications through the closed producer list (PD-109). Destinations are built in this order behind one streaming interface: local, S3-compatible (minimal SigV4 and multipart, tested against MinIO), warm standby (PD-151), then Google Drive and OneDrive (owner-supplied OAuth clients, separate `drive.file` consent). **The cut line:** the first three plus the interface close the 32-SS1 gate; Google Drive (Milestone 856) and OneDrive (Milestone 857) may slip to a named follow-up without blocking the gate and without renumbering earlier milestones. Restore stays the offline elevated command under the 31G rules and also restores the databases and blobs.
- **PD-151 — Warm standby is a pull, behind a per-device grant.** A paired desktop device pulls encrypted backup chunks over a device-token streaming route; the Hub never pushes to a device. The route is open only to a device holding a per-device, owner-set, step-up-gated, audited standby grant (the `notifications_access` pattern, with its own audit event and confirmation-boundary spec), revocable at any time. The puller lives in desktop main. Promotion with the old Hub dead uses the offline restore with `--old-hub-gone` and the 31G transfer rules; a promotion guide documents it. The standby holds only ciphertext it cannot decrypt without the backup passphrase.
- **PD-152 — Power policy: detect, then a two-step elevated change.** The Hub detects the sleep and hibernate settings of the active power plan with `powercfg` and reports them in provisioning status. Changing them is an elevated admin-pipe action with a preview, a single-use confirm, a `ConsequenceClass`, a confirmation-boundary spec registered in the high-consequence gate and a printed revert command. The Hub re-checks on start and raises a notification when the policy regresses. No owner-session route changes power settings.
- **PD-153 — Provisioning: an idempotent engine, a desktop wizard and a read-only Hub-web status.** An idempotent `dude-hub provision` engine (CLI and admin-pipe methods) creates and verifies each component and answers `GET /api/v1/provisioning` with per-component status, including "needs re-provision" and "secrets re-entry" after a restore. The Electron desktop wizard is chained after `setupLocalHub` and drives that engine; the token and passphrase reach one elevated `provision` run over stdin, never argv, never logs. Hub-web Settings shows per-component status and copyable commands only; it cannot create or change a backup, a schedule, the tunnel, the power policy or any exposure. Backup creation and scheduling therefore stay on the elevated admin pipe, and the owner UI on the Hub web stays view-only for backups.
- **PD-154 — Closure: an automated gate, a guided owner script and owed passes.** The exit gate is automated: a fake OIDC identity provider, a stub `cloudflared`, a generated backup larger than 512 MiB that streams with bounded memory and restores under the 31G rules, and MinIO for S3 in CI, plus the route-gating enumerate-and-probe spec, crash-injection suites (mid-commit, mid-blob-rename, mid-lease), upload resume, duplicate, wrong-hash and disk-full cases, and fake-IdP wrong `sub`, `nonce`, `aud` and `exp` cases. Live checks are a guided owner script in `PHASE32SS1_ACCEPTANCE.md` (real Cloudflare tunnel, Google sign-in including Google unreachable, direct Public mode, a second-machine restore, standby promotion, Drive and OneDrive). SS1 is declared complete with those passes owed, as 31E–31J were; 32-SS2 is not gated on them. Android is part of SS1: the public-CA trust mode ships in the Kotlin Hub client with emulator acceptance on the sharded Android CI.

## Deviations and implementation notes

### 2026-10-27, Milestone 829: decisions recorded and program wording amended

This milestone changes documentation only. The program decisions were reworded in place where the SS1 decisions above make their earlier wording wrong, and the dated scope entry required by PD-140 was added to the [program decisions](PHASE32SS_PLAN.md#dated-scope-entries-pd-140) and the [decision log](../history/DECISION_LOG.md#phase-32-ss1-implementation-decisions):

- **PD-064** still stands; the clarification is that the Hub holds no Cloudflare API token, only the tunnel connector token (PD-142).
- **PD-120** no longer says the tunnel uses "proxy pins": the tunnel is remotely managed, devices trust the public CA chain for the tunnel domain and only the loopback hop is pinned (PD-142, PD-143).
- **PD-122** is restated as the gating rule of PD-144 (static assets public; API, websocket and admin gated; the SPA guard keeps tool pages behind sign-in).
- **PD-123** now says the power policy change is a two-step elevated action (PD-152) and the standby device pulls backups (PD-151).
- **PD-124** gains the retention defaults, verify-on-write, the monthly drill, the 2x overdue rule, the standby pull and the Google Drive and OneDrive cut line (PD-150).
- The as-built constraints that 32-SS1 resolves (job queue, backup ceilings, tunnel readiness and pinning, the secret store, the upload parser) now cite the resolving decision, and the "ingest tokens across a restore" question is closed (PD-149).
- The [Hub scope ceilings](../../apps/hub/AGENTS.md) that said "no job queue", "no streaming backups", "no standby replication" and "no UI that creates or schedules a backup" are reworded to the 32-SS1 allowance and its boundaries: the queue runs Hub-internal work only, the standby is a device pull behind a grant, backup v2 streams, and the Hub-web backup UI stays view-only with creation and scheduling on the elevated admin pipe.

Planner judgment calls made at this milestone and reversible only by a dated amendment here: tunnel mode skips Cloudflare edge-certificate pins (PD-143); `savesphere.db` is separate with no `ATTACH` and an outbox (PD-146); an S3 blob tier is deferred (PD-148); the OIDC callback is a narrow GET exemption (PD-144); no new workspace packages (PD-141).

### 2026-10-27, Milestone 830: feasibility go/no-go (GO on all three)

Evidence from `npm run check:hub-capabilities` (`scripts/check-hub-sea-capabilities.mjs`) against the real single-executable Hub built with `npm run hub:compile` and `npm run hub:sea` (Node 24.21.0, SQLite 3.53.4, Windows 11 x64), and again against the CJS bundle under `node`:

- **FTS5: GO.** The `node:sqlite` build inside the SEA creates an `fts5` virtual table with the `porter unicode61` tokenizer and answers `MATCH` with `rank` ordering.
- **sqlite-vec: GO on Windows x64.** `scripts/fetch-sqlite-vec.mjs` (`npm run hub:sqlite-vec`) downloads sqlite-vec 0.1.9 `loadable-windows-x86_64` from the official release, pins the archive (`51581189...8165983`, equal to the release's own `checksums.txt`) and the extracted `vec0.dll` (`fcf98662...76476e6`) and writes it atomically to `build/vendor/sqlite-vec/` (untracked). The SEA verifies the DLL against the same pin (constants kept equal by `db/sqlite-vec.spec.ts`), opens an in-memory database with the new `allowExtension` option of `@dude/sqlite-store`, calls `loadExtension`, locks extension loading again (`lockExtensionLoading`) and reads `vec_version()` (`v0.1.9`). The default entry point works for `vec0.dll`. Extension loading stays off for every other connection.
- **Worker re-spawn: GO.** `apps/hub/src/workers/worker-mode.ts` re-spawns `process.execPath` with `--internal-worker <kind>` in the SEA and `node <bundle> --internal-worker <kind>` otherwise (`sea.isSea()` picks), one JSON line each way over stdio; `main.ts` runs the worker hook before the CLI. The SEA exchanged a message with a child process of itself.

Limitations and decisions recorded rather than worked around:

- The Hub only loads `vec0.dll` found beside the executable (SEA) or in `build/vendor/sqlite-vec/` (Node process), never from `PATH` or an unverified location. A missing, mismatching or unloadable library, a non-Windows or non-x64 host and the Alpine (musl) Docker image report `sqlite-vec` as **unavailable** (`state: 'unavailable'` with a reason, `ok` stays true) in `self-test`; the capability script fails on that only with `--require-vector`. `hub:stage` and the installer do not ship `vec0.dll` yet (a later milestone adds it to the copy list with provisioning status); until then a staged Hub reports vector search unavailable.
- The load is hash-check then `loadExtension` on the same path (no copy), so a local attacker who can write to the Hub's install directory could race it; that directory is already the trust root for the executable itself.
- `dude-hub run` keeps its fail-fast self-test but skips the vector and worker probes (`runSelfTest({ capabilities: false })`) so a start never spawns a child or reads the DLL; `dude-hub self-test` runs them all.
- FTS5 and worker re-spawn are hard requirements of the self-test (failure fails it); vector search is the only optional capability.
- The queue, the worker host and any non-`ping` worker kind are Milestone 834.

### 2026-10-27, Milestone 831: Hub secrets module

`apps/hub/src/secrets/` adds the `SecretStore` (closed `HUB_SECRET_PURPOSES`, one DPAPI entropy and one file per purpose under `<configDir>/secrets/`, `status()` presence only). Notes:

- It reuses `createDpapiProtector` and `createFileProtector` from `tls/ca-key-protector.ts` unchanged instead of extracting a `secrets/dpapi.ts`, so the CA, ACME and backup-schedule protectors and their specs are untouched.
- Limitation: the Linux/Docker fallback is a mode-0600 file in a mode-0700 directory (file-permission protection only), as for the CA and ACME keys.
- `HubPaths.secretsDir` was added; `ensureLayout` does not create it (the store creates it on first `put`). Backups hold only `dude.db` and `hub.json`, so the directory is never included (asserted in `secrets.spec.ts`); after a restore onto another machine DPAPI blobs are unreadable and every purpose needs re-entry. `status({ expected })` reports `needsReentry`; which purposes are expected comes from the provisioning config, which arrives at Milestone 835.
- The importer allowlist in `secrets.spec.ts` is empty until the first consumer (Milestone 832 onwards) adds itself.


### 2026-10-27, Milestone 832: `savesphere.db` content store foundation

`apps/hub/src/savesphere-db/` adds `openSaveSphereDb(paths, options?)`, its own migration sequence (`SAVESPHERE_MIGRATIONS`, `0001-platform`: `meta`, `schema_migrations`, `audit_outbox` only) and `audit-outbox.ts` (`appendAuditOutbox`, `drainAuditOutbox`, `drainAuditOutboxAtStart`). Notes:

- `HubPaths` gains `saveSphereDbPath` (`data/savesphere.db`) and `saveSpherePreMigrationDir` (`data/pre-migration/savesphere`, a subdirectory because the runner's backup pruning keeps the newest three `pre-v*.db` files of a directory and would otherwise count both databases together). `ensureLayout` does not create either; only `openSaveSphereDb` does, and nothing calls it yet except the start-up drain (provisioning is Milestone 835).
- The start-up drain in `cli/run.ts` runs only when `savesphere.db` already exists, opens it, drains and closes it, and swallows errors, so a Hub that never provisioned SaveSphere gets no file and an unreadable store never blocks start. The audit writer is the existing `audit()`; `HUB_AUDIT_EVENTS` is not widened (no first producer yet), so the specs use an existing event.
- Idempotence: the drain writes the row's `dedupe_key` into the audit detail as `outboxRef` and looks for it before writing, so a crash between the audit write and `drained_at` never duplicates the event. `appendAuditOutbox` refuses to run outside a transaction (`db.isTransaction`) and validates the event and detail (the Hub audit sanitizer) at append time so a bad event rolls the content back. Drained rows are pruned after 30 days.
- `backup/snapshot.ts` exports `HUB_KEPT_TABLES`, `SAVESPHERE_SCRUBBED_TABLES` (`audit_outbox`) and `SAVESPHERE_KEPT_TABLES`; `backup/classification.spec.ts` opens both real databases and fails on any unclassified table. Backup v1 behaviour is unchanged; the engine integrates `savesphere.db` at Milestone 847.
- `allowExtension` stays off unless the vector component asks; `SaveSphereDb.lockExtensions()` re-locks it.

### 2026-10-27, Milestone 833: content-addressed `BlobStore`

`apps/hub/src/blobs/` adds the `BlobStore` interface (`blob-store.ts`), the local-disk implementation (`local-blob-store.ts`), the catalogue and reference counts (`registry.ts`, migration `savesphere.db` 0002-blobs: `blobs`, `blob_refs`), the blob lease (`lease.ts`), `verifyBlobBatch` (`verify.ts`) and mark-and-sweep GC (`blob-gc.ts`, with `blob-gc.confirmation-boundary.spec.ts`, which the high-consequence gate's `confirmation-boundary` Hub filter already picks up). No job runner and no admin methods are registered: the queue arrives at Milestone 834 and the admin wiring at 835/847. Deviations from the architecture sketch:

- **Interface names and types.** `open` replaces the sketch's `get`, it returns a Node `Readable` (the Hub's stream type), and `put` accepts a buffer or any async-iterable of bytes (Node `Readable` or web `ReadableStream`). `has` and an optional `expectedSha256`/`maxBytes` on `put` were added; `list`, `delete`, `verify` and `stat` follow the sketch. `LocalBlobStore` also exposes `sweepStaging(maxAgeMs)`.
- **No overwrite without `rename`.** `put` hard-links the fsynced staging file to its final name and unlinks the staging name (`EEXIST` is the dedupe hit); `rename` is used only on a filesystem without hard links. `HubPaths` gains `blobsDir` (`storage/blobs`) and `stagingDir` (`storage/staging`); `ensureLayout` does not create them. `storage/staging/` is shared with the later import staging (PD-132): the sweeper only touches `*.part` files.
- **`blobs.unreferenced_since`** was added beside the sketched columns (`sha256`, `size`, `created_at`, `verified_at`, `state`) so the grace period counts from when the last reference went, not from the upload: it is set on record and on the last `removeBlobRef`, cleared by `addBlobRef`, and restarted by re-storing identical content. `state` is `ok`, `corrupt`, `missing` or `deleting`. `blob_refs` is `(blob_sha256, owner_kind, owner_id)` with the three as primary key and a foreign key to `blobs`. The migration floors the reader at 2.
- **GC.** `planBlobGc` is read-only (capped at 10 000 candidates, `truncated` flag); `previewBlobGc` stages a single-use 60-second token bound to the SHA-256 of the grace period and the exact candidate list (and the `cli` binding); `applyBlobGc` takes the `gc` lease first (a refused apply keeps the token), spends the token against the digest recomputed from the plan presented, then per blob re-checks references and the grace period in a transaction, marks `deleting`, removes the file, then the row. A failed file delete leaves the `deleting` row for the next GC. The grace period must be at least one hour (default seven days). Preview audits nothing (it must write nothing); apply appends one `blobs.gc-applied` outbox event.
- **Lease.** `meta` keys `blob_lease:gc` and `blob_lease:backup` (JSON `expiresAt`, 15-minute TTL, renewable) are mutually exclusive between holders; the backup engine (Milestone 847) takes `backup` while it reads the blob set from its snapshot. The keys are transient: Milestone 847 decides whether the snapshot scrubs them (a restored stale lease only expires on its own).
- **Audit events.** `HUB_AUDIT_EVENTS` gains `blobs.verify-failed` and `blobs.gc-applied` (written only through the outbox). `SAVESPHERE_KEPT_TABLES` gains `blobs` and `blob_refs`; the blob bytes are backup v2's concern. `0001-platform.spec.ts` now pins its own one-migration sequence instead of the full list.
- **Known narrow window.** If a re-upload of old unreferenced content dedupes against a file in the instant between GC's claim and its row delete, `recordBlob` refuses a `deleting` row and the caller re-puts; if GC finished completely in that gap the row would be recorded for a missing file, which the verify job flags as `missing`. The upload commit (Milestone 845) re-checks `has` after recording.

### 2026-10-27, Milestone 834: durable job queue and isolated workers

`apps/hub/src/queue/` and `apps/hub/src/workers/` add the queue, the runner and the worker host; `GET /api/v1/queue`, `HUB_JOB_IDS` growth and the `@dude/api-client` `queueStatus` method surface them. Deviations from the architecture sketch and decisions made here:

- **States.** `queued`, `running`, `succeeded`, `failed`, `dead` (not the sketch's `leased` and `canceled`; cancellation is not built, and there is no owner cancel or retry, which stays a later and separately decided scope). A failed retryable attempt returns to `queued` with a later `run_after`; `failed` is the terminal non-retryable state (a handler `PermanentJobError`, a worker out-of-memory abort, a kind with no handler) and `dead` means every attempt was used. Times are integer epoch milliseconds, unlike the ISO text of the older tables. `savesphere.db` migration 0003 floors the reader at 3; `jobs` is `SAVESPHERE_SCRUBBED_TABLES` (a restored Hub starts with an empty queue; the `queue_schedule:*` meta keys are kept and only make a schedule due early).
- **Idempotency** is unique among ACTIVE jobs (`queued` or `running`) through a partial unique index, so a scheduled job that is still waiting is never queued twice while a finished one can run again. Durable idempotency on (source hash, processor, version), which the processing pipeline needs, is that phase's check against content state.
- **Crash safety.** A claim counts as an attempt; a lease (60 s, renewed every third of it) that expires is recovered at runner start and every minute, with the same backoff as a failure and dead-lettering after `max_attempts` (default 5). A graceful stop `release`s running jobs without costing an attempt. Every holder-side change names the lease owner, so a stale holder gets `lost` instead of touching a re-claimed job.
- **Payload and error hygiene.** `enqueue` refuses a credential-looking key at any depth and a payload over 64 KiB; `last_error` is passed through `redactJobError` (paths, bearer tokens, secret-looking `key=value` pairs and long token-like runs removed, 300 characters) before it is stored, and the status route redacts again on read.
- **Handlers.** `JOB_KINDS` is `noop.echo`, `blobs.verify`, `blobs.staging-sweep`, all `inline` because each needs the Hub's own database or blob store. `worker` isolation is built and tested but has no production kind yet; the extension point is `JOB_KINDS` plus the handler map (`queue/handlers.ts`) plus `workers/worker-job-handlers.ts` (empty), and a spec fails if a declared worker kind has no implementation. An inline handler is only signalled on timeout (keep it short); a worker is killed.
- **Worker host.** One child per job (the Hub executable re-spawned as `--internal-worker job`), at most `size` (default 2) at once, a per-job scratch directory under `storage/workers/` (`HubPaths.workersDir`, emptied at pool start) as the child's working directory and temp location, `NODE_OPTIONS=--max-old-space-size=<mb>` for the heap ceiling (the same route works for the single-executable application, whose `execArgvExtension` defaults to the environment; not yet exercised inside a built SEA, an owed check), an allowlisted environment (`SystemRoot`, `windir`, `TZ`, `LANG`, `LC_ALL`; nothing else of the Hub's, no `PATH`; Windows itself still adds its own baseline variables to any child), a wall-clock kill with `taskkill /T` on Windows, out-of-memory detected from the child's stderr, and a crash back-off before the next spawn. The child exits when its stdin closes. Limits recorded: the heap ceiling does not bound native allocations, Windows Job Objects are not reachable from Node, and an event loop blocked inside a worker cannot notice a dead Hub until it yields. The pool size is an option of `createWorkerPool` and `createQueueRuntime`, not yet a `hub.json` field (provisioning, Milestone 835, decides the surface).
- **Wiring.** `run` creates the runtime only when `savesphere.db` already exists (a Hub that never provisioned gets no runner, pool or file), starts it after the other timers and stops it first at shutdown. `HUB_JOB_IDS` gains `queue-runner` (recovery, pruning and scheduling; reported only when it changed something, plus once at start), `blobs-verify` (every 6 h, 25 blobs) and `blobs-staging-sweep` (every 24 h, files older than 24 h); both are scheduled by the runner through idempotent enqueues and tracked in the job registry around each attempt, and a verify that finds a corrupt or missing blob shows as failed there. On a Hub without `savesphere.db` the three ids show as never run with no timer, so the bundle spec asserts a zero interval for them. The web Hub-jobs panel gained their display names (a type-checked map, not a behaviour change).
- **Read route.** `GET /api/v1/queue` is owner cookie or bearer, read-only (no CSRF, no audit, like `GET /api/v1/jobs`), `available: false` with zero counts when there is no store. There is no enqueue route.
- **Not done here.** Progress is passed to the pool's `onProgress` but not persisted or shown; no per-kind concurrency caps, cancellation or priority aging; the GC and upload-expiry jobs are registered by their own milestones; no real worker kind exists to prove SEA execution of a worker job beyond the M830 `ping` proof.

### 2026-10-27, Milestone 835: provisioning engine

`apps/hub/src/provisioning/` adds the engine (`engine.ts`: `provision`, `checkProvisioning`), the component registry (`registry.ts`, `registerProvisioningComponent`), the eight built-in components (`components/`), the cache helper (`cache.ts`) and a status service (`service.ts`); `dude-hub provision [status] [--json]` (`service/provision.ts`), the admin methods `provision.run` and `provision.status` (`admin/provisioning-methods.ts`), `GET /api/v1/provisioning` with `HubProvisioningResponse` in `@dude/contracts/hub`, `provisioningStatus` in `@dude/api-client` and the `provisioning.run` audit event. Deviations from the architecture sketch and decisions made here:

- **Statuses.** Components report `ready`, `degraded`, `unavailable`, `not-configured` or `needs-attention` (not the sketch's `not provisioned`/`failed`); `unavailable` is a by-design answer (vector search on Docker) and never lowers the overall state. The overall state is `not-provisioned`, `needs-provisioning`, `needs-attention`, `degraded` or `ready` (`deriveOverall`). A component that is not built (`tunnel` 836-837, `backup` 847 on, `oidc` 841, `power` 851) is absent from the report; its id is already reserved in the closed `HUB_PROVISIONING_COMPONENT_IDS`, so adding it edits only its own module and one line in `components/index.ts`.
- **Needs re-provision after a restore** is derived, not stored as a flag: no recorded run, a run recorded by another Hub identity (a restore creates a new one; the run record lives in `savesphere.db` `meta`, a kept table), a core directory missing, or a secret expected but absent. The expected secret purposes are also a `meta` key (`provisioning_expected_secrets`, names only), recorded by a provision run for every purpose present, so a restored Hub (machine-bound secrets never travel) reports `needsReentry` per purpose. Later milestones record a purpose with `setSecretExpected` when the owner stores a secret. A restored `hub.json` that keeps only the port and names holds no provisioning state, so the spec simulates the restore by copying `savesphere.db` into an otherwise empty data directory with a reduced `hub.json`.
- **No confirmation token.** A run only creates what is missing, so it is not destructive; it is still an owner-intent state change and writes `provisioning.run` through the outbox in the same `savesphere.db` transaction as the run record (credential class: the elevated admin pipe). It is single-flight per data directory (a concurrent caller joins the running run).
- **Cache location.** `HubPaths.cacheDir` is `storage/cache`, not the sketch's top-level `cache/`: `purge` already removes `storage/` (so the Destructive-Action Contract and its confirmation-boundary spec are untouched) and backups never hold it. The bound is the constant `DEFAULT_CACHE_MAX_BYTES` (1 GiB), swept oldest-first by every provision run; a `hub.json` field is later work.
- **Probes touch no live data.** The queue check runs a `noop.echo` job through the real queue and handler code against an in-memory database with the real migrations (a probe row in the live `jobs` table would race the runner and leave residue); the blob round trip uses a throwaway store under `storage/staging/.probe-*` and removes it. The FTS5 and worker re-spawn probes are the Milestone 830 code, now exported from `cli/self-test.ts`. The vector probe's reason (which names a path) is mapped to fixed sentences.
- **No `vec0` table yet.** SS1's "schema slot" for the vector index is the availability record only; a table that needs the extension at every open (and survives `VACUUM INTO` and the scrub) is SS5's decision.
- **A running Hub that started without `savesphere.db`** has no queue runner. A run that creates the store there returns `restartRequired` and the queue component reports `needs-attention` ("restart the Hub service") until it does; `run` passes `queueRunning` to the engine, the CLI engine and specs leave it unknown.
- **Wiring.** `run` creates one `ProvisioningService` (60 s cached read model for the route, invalidated after a run) and, only when `savesphere.db` exists, runs a read-only check after listening that logs the overall state and per-state counts, never a detail sentence. The route is owner cookie or bearer, `no-store`, no audit, and reports `not-provisioned` with the commands when no read model is wired or the check throws; the secret store is imported only by `provisioning/components/secrets.ts` (added to the `secrets.spec.ts` allowlist), never by a request handler.
- **CLI.** `dude-hub provision` needs the elevated terminal when the service is installed and the Hub running (it never opens a database itself; a stopped Hub exits 2); `provision status` is read-only. Exit codes: 0 ready or degraded, 1 needs attention, needs provisioning or a failed call, 2 usage or Hub not running. `provision.run` takes no parameters today and refuses any (the wizard's `secrets` parameter over standard input is Milestones 837 and 853, not built here).
- **Owed.** A real Windows service pass (elevated `dude-hub provision` against the installed Hub, the worker probe inside the SEA, `vec0.dll` beside the executable) belongs to the acceptance script; Docker is covered by the Linux secret-file fallback in the specs only.

### 2026-10-27, Milestone 836: pinned `cloudflared` and the process supervisor

`scripts/fetch-cloudflared.mjs` (`npm run hub:cloudflared`, part of `hub:stage`) pins **cloudflared 2026.10.4**, asset `cloudflared-windows-amd64.exe`, SHA-256 `411b16d40c8d872243efeb52c550053d00af0a8a97fbb32e730fb8aba429eaa8`. The value was computed from a real download and equals both the checksum in the release notes and the GitHub asset digest; the binary runs (`--version` reports 2026.10.4). It is written atomically to the gitignored `build/vendor/cloudflared/cloudflared.exe`, staged by `stage-hub.mjs` as `cloudflared.exe` (with its `SHA256SUMS` line), copied beside `dude-hub.exe` by `service install|update` (`CLOUDFLARED_EXE`, optional in a source directory so an older stage still installs), removed by `service uninstall` and the installer's uninstaller, and required by `build-hub-installer.mjs` and `check-hub-service.mjs` (which also asserts the update installed the staged copy). The installer's `File /r` payload and the CI `hub:stage` steps needed no edit. The Docker image does not run `hub:stage`, so it is unchanged. `apps/hub/src/supervisor/` and `apps/hub/src/tunnel/` are described in `apps/hub/AGENTS.md`. Deviations and notes:

- **No Job Object.** Node has no Windows Job Object API without a native addon, and a PowerShell holder process (create the job, assign the child, exit when stdin closes) was judged more fragile than the problem. The approach is a pid file plus an orphan sweep at the next `start()` that kills only a process whose image path equals the pinned executable, and a synchronous `killNow()` for an exit handler. The limit is recorded: a Hub killed outright leaves cloudflared running until the next Hub start (WinSW's stop also terminates the process tree, not yet verified with a running tunnel). The image lookup uses CIM through PowerShell (about a second, only when a pid file exists).
- **Polite stop on Windows.** There is no console control event for a window-less child, so `SIGTERM` is a hard terminate there; the grace period and `taskkill /T /F` still apply (and matter for Linux stubs and any future child that does handle the signal).
- **Hash then spawn.** The hash check runs before every start but is not atomic with the spawn; the install directory is administrator-writable only, so this defends against a corrupt or substituted file at rest, not against an administrator (stated in `tunnel/cloudflared.ts`).
- **The token read is injected.** `createCloudflaredSupervisor` takes `secrets: Pick<SecretStore, 'getText'>`; `tunnel/cloudflared.ts` joined the importer allowlist in `secrets.spec.ts`. The metrics port is a fresh free loopback port per launch.
- **No diagnostics entry.** A `supervisor` status in `GET /api/v1/jobs` or the diagnostics report was not trivial (the job registry is timer-shaped and read-only), so it is Milestone 837 together with the `tunnel` provisioning component and `network tunnel on|off`.
- **Owed.** A real run of `cloudflared.exe` against a Cloudflare tunnel (the readiness probe's `/ready` contract is the documented one and is exercised only against the stub), the installed-service orphan sweep after a killed Hub, and `hub:stage`/`check:hub-service` inside the elevated CI job (staging was run locally; the service check needs elevation).
