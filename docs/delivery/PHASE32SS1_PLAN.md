# Phase 32-SS1 implementation decisions

Status: in progress, started 2026-10-27 at Milestone 829. Decisions PD-141–PD-154 were recorded at Milestone 829 and govern the Hub platform work for SaveSphere (Milestones 829–857). They refine the program decisions PD-118–PD-124 ([SaveSphere program decisions](PHASE32SS_PLAN.md)) after owner Q&A and a feasibility review of the as-built Hub; where the two differ, the refinement wins, and the program decisions were reworded at the same milestone so no stale rationale remains (see [Deviations](#deviations-and-implementation-notes)). The [ROADMAP 32-SS1 entry](ROADMAP.md#phase-32-ss1) sets the scope and exit gate. Nothing here is an as-built claim until a milestone's evidence says so. The Hub keeps a single owner and a single environment (PD-027); guests arrive in 32-SS6.

A Phase 32-SS1 acceptance document (`PHASE32SS1_ACCEPTANCE.md`, Milestone 855) will record the automated exit gate and the owed live passes as a guided script, following the 31E–31J convention.

- **PD-141 — Windows first; the Docker image keeps working with a documented subset.** The tunnel, the power policy check and vector search are Windows-only. The Docker image keeps running the embedded stores, the blob store, the job queue, resumable uploads and backup v2 to local and S3-compatible destinations, and reports tunnel, power policy and vector search as "not available in this deployment" in the Docker section of the Hub documentation. `sea.isSea()` selects the worker spawn mode, so a Node-process Hub (Docker, foreground) and the single-executable Hub use the same worker code. `sqlite-vec` has no musl build, so the Alpine-based image reports "vector unavailable". No new workspace packages are added (the Dockerfile copy rules stay untouched); new Hub code lives under `apps/hub/src/`, format code under `packages/hub-backup`, and `jose` is declared in `apps/hub/package.json`.
- **PD-142 — The tunnel credential is an owner-pasted connector token; there is no Cloudflare API token.** The owner creates a remotely managed tunnel in the Cloudflare dashboard and pastes its connector token into the provisioning wizard (or the elevated `provision` run, over stdin, never argv). The token is stored DPAPI-protected in a new Hub `secrets/` module that generalizes `tls/ca-key-protector.ts` and `backup/schedule-key.ts` (per-secret entropy, an importer-boundary spec like `local-ca.spec.ts`). `cloudflared` is fetched by a hash-pinned script like WinSW, run with `TUNNEL_TOKEN` in its environment (never argv) and `--no-autoupdate`. Because the tunnel is remotely managed, its ingress rules and `originRequest` settings live in the Cloudflare dashboard, not on the Hub; the wizard shows the exact hostname and origin values the owner must enter, and the Hub cannot change them. PD-064 stands unchanged: the Hub stores no DNS-provider credential and no Cloudflare API token, and DNS routing for the tunnel hostname is the owner's dashboard action. The wording "proxy pins" in PD-120 is corrected accordingly (PD-143).
- **PD-143 — Tunnel trust: public-CA mode for the tunnel domain, a pinned loopback hop and tunnel-aware readiness.** Cloudflare terminates TLS at its edge with a certificate it rotates, so DUDE does not pin it. In tunnel mode devices (the Device Agent, the desktop and the Android Kotlin Hub client) verify the tunnel domain with the **public CA chain**, a new "public-CA trust" mode beside SPKI pinning, scoped to the configured tunnel domain and refusing any other host; the Hub's loopback hop is the only pinned connection (`cloudflared` verifies the Hub's loopback certificate against the Hub's local CA). Enrollment against the tunnel domain probes the trust mode instead of asking for an SPKI pin. A tunnel-aware readiness check set (the tunnel's `/ready` connected and healthy, no inbound port) replaces `public-firewall-rule` and `inbound-bind` in tunnel mode and leaves every other blocker unchanged. Turning the tunnel on is an elevated admin-pipe command (`network tunnel on|off`) that puts the Hub in the existing reverse-proxy mode (loopback hop, `publicOrigin`) behind the same typed-phrase gate and a confirmation-boundary spec, with the Cloudflare edge-TLS and terms disclosure. `www.<domain>` redirects to the bare domain in the Host guard. A forged `X-Forwarded-For` check runs against the stub `cloudflared`. Android ships the same trust mode in 32-SS1, with emulator acceptance.
- **PD-144 — The gating rule (PD-122 reworded): static assets are public; every API, websocket and admin route is gated.** The static web build (sign-in page, service worker, the precached offline shell, the Hub-offline page) stays public, because it must load before a session can exist and holds no owner data. Every API, websocket and admin route requires a session (owner cookie or bearer, device token, or from 32-SS6 a guest session) except a documented allowlist: sign-in and recovery, the OIDC callback, the Hub's existing unauthenticated `hello` endpoint, the token-only ingest path and, from 32-SS6, public share links. The SPA `hubSessionGuard` keeps every tool page behind sign-in, so the developer tools stay behind the session even though their code is a public asset. An enumerate-and-probe spec walks every registered route against a committed allowlist fixture and fails on any ungated route. The OIDC callback is a narrow GET exemption in `security/request-guard.ts` (the owner cookie is `SameSite=Strict`, so the session-less callback leaves a same-site follow-up that completes the sign-in or link). The Hub-offline page is a precached public asset used as the service worker's navigation fallback.
- **PD-145 — Sign-in: Google primary, the password can never be disabled.** The OIDC authorization-code flow with PKCE runs on `jose`, with `state`, `nonce`, a cached JWKS and verification of issuer, audience, expiry, nonce and signature. A Google identity binds by `sub` only after a signed-in round-trip; several of the owner's accounts can be linked, linking and unlinking need step-up, and the last linked account cannot be unlinked (`linked_identities`, migration 0011). Password and recovery sign-in sit under "Other ways" and can never be disabled by any setting or route. Failed callbacks count into `ip-block.ts`. Google unreachable shows an explanatory fallback to the password path. Link and unlink have confirmation-boundary specs, and the new audit events extend the closed list.
- **PD-146 — A separate `savesphere.db` with its own migrations, no `ATTACH`, and an audit outbox.** The SaveSphere content store is its own SQLite file with its own migration runner. `ATTACH` is not used, because a transaction across two WAL files is not atomic. Where an action must write both a SaveSphere row and an audit row, the audit event is written to an `audit_outbox` row in the same `savesphere.db` transaction and drained into `dude.db` on commit and at start (at-least-once, deduplicated by a key). Every table in both databases is classified scrubbed or kept for backups by a spec, with `SAVESPHERE_SCRUBBED_TABLES` beside `backup/snapshot.ts`. The Hub process is still the only writer of both files.
- **PD-147 — The queue runs Hub-internal work only; workers are isolated; vector search is proved, not built.** The durable queue (in `savesphere.db`) and its isolated workers run only Hub-internal work: blob verification, garbage collection, upload expiry, the restore drill, backup runs and later SaveSphere processors. Owner- or device-initiated privileged execution, a run-now for arbitrary jobs and a user-visible job framework remain Phase 88; `HUB_JOB_IDS` is extended with the internal jobs and stays read-only to clients. Workers are the Hub executable re-spawned in an internal worker mode (the single-executable application cannot run workers from a path), with a Node-process fallback chosen by `sea.isSea()`. SS1 provisions the schema slot for a vector index and proves that a pinned, hash-verified `sqlite-vec` library loads through `node:sqlite` `loadExtension` inside the single-executable application (an `allowExtension` option on `packages/sqlite-store/src/open.ts`); if it does not, or on Docker, the provisioning status reports "vector unavailable". FTS5 availability is proved in the same milestone. Milestone 830 is a go/no-go for both, and a failed proof is recorded here rather than worked around silently.
- **PD-148 — Blobs and uploads.** The local `BlobStore` is content-addressed by SHA-256 with refcounts, a verify job and mark-and-sweep garbage collection with a grace period; pruning or collecting unreferenced blobs is a two-step confirm (a `ConsequenceClass`-tagged preview and a single-use apply, with a confirmation-boundary spec). Uploads are a resumable route family with its own non-JSON body parser (the 64 KiB `HUB_BODY_LIMIT` is untouched elsewhere): sessions in `savesphere.db`, idempotent 8 MiB chunks by offset (below Cloudflare's request-body limit), a SHA-256 check before commit, no fixed size cap, a free-disk guard and an expiry job. An S3 blob mirror or tier is **deferred** (open item of PD-118 stays open after SS1); S3 is a backup destination only.
- **PD-149 — Ingest is a scaffold only.** SS1 adds `/api/v1/ingest/*` with the scoped, hashed ingest-token class (resolver, rate-limit bucket, audit events, gate-allowlist entry) and one `ping` route. Real capture channels are 32-SS3. Ingest tokens are **scrubbed on restore and must be reissued**, which resolves the open question recorded in the SaveSphere architecture ("whether ingest tokens survive a restore") now: a restored Hub never carries a capture credential from before the restore.
- **PD-150 — Backup v2: destinations, sequencing, retention and verification.** `@dude/hub-backup` gains a v2 format: a repository header with a wrapped master key (a passphrase change does not re-encrypt), an encrypted pack stream, a manifest, an HMAC-of-blob-hash dedupe key, `formatVersion` and `minReader` in the header and every manifest, and v1 files still restore. The engine snapshots both databases (with the scrub lists) first and takes the blob set from that snapshot under a GC lease; every backup is verified when written (verify-on-write) and counts only after that. Retention defaults to **7 daily, 4 weekly and 6 monthly**, pruned only by a two-step confirm, with mark-and-sweep blob garbage collection afterwards. A restore drill runs **monthly** as a job; a backup is **overdue at 2x its interval**, and overdue, failed and drill-failed backups raise notifications through the closed producer list (PD-109). Destinations are built in this order behind one streaming interface: local, S3-compatible (minimal SigV4 and multipart, tested against MinIO), warm standby (PD-151), then Google Drive and OneDrive (owner-supplied OAuth clients, separate `drive.file` consent). **The cut line:** the first three plus the interface close the 32-SS1 gate; Google Drive (Milestone 856) and OneDrive (Milestone 857) may slip to a named follow-up without blocking the gate and without renumbering earlier milestones. Restore stays the offline elevated command under the 31G rules and also restores the databases and blobs.
- **PD-151 — Warm standby is a pull, behind a per-device grant.** A paired desktop device pulls encrypted backup chunks over a device-token streaming route; the Hub never pushes to a device. The route is open only to a device holding a per-device, owner-set, step-up-gated, audited standby grant (the `notifications_access` pattern, with its own audit event and confirmation-boundary spec), revocable at any time. The puller lives in desktop main. Promotion with the old Hub dead uses the offline restore with `--old-hub-gone` and the 31G transfer rules; a promotion guide documents it. The standby holds only ciphertext it cannot decrypt without the backup passphrase.
- **PD-152 — Power policy: detect, then a two-step elevated change.** The Hub detects the sleep and hibernate settings of the active power plan with `powercfg` and reports them in provisioning status. Changing them is an elevated admin-pipe action with a preview, a single-use confirm, a `ConsequenceClass`, a confirmation-boundary spec registered in the high-consequence gate and a printed revert command. The Hub re-checks on start and raises a notification when the policy regresses. No owner-session route changes power settings.
- **PD-153 — Provisioning: an idempotent engine, a desktop wizard and a read-only Hub-web status.** An idempotent `dude-hub provision` engine (CLI and admin-pipe methods) creates and verifies each component and answers `GET /api/v1/provisioning` with per-component status, including "needs re-provision" and "secrets re-entry" after a restore. The Electron desktop wizard is chained after `setupLocalHub` and drives that engine; the token and passphrase reach one elevated `provision` run over stdin, never argv, never logs. Hub-web Settings shows per-component status and copyable commands only; it cannot create or change a backup, a schedule, the tunnel, the power policy or any exposure. Backup creation and scheduling therefore stay on the elevated admin pipe, and the owner UI on the Hub web stays view-only for backups.
- **PD-154 — Closure: an automated gate, a guided owner script and owed passes.** The exit gate is automated: a fake OIDC identity provider, a stub `cloudflared`, a generated backup larger than 512 MiB that streams with bounded memory and restores under the 31G rules, and MinIO for S3 in CI, plus the route-gating enumerate-and-probe spec, crash-injection suites (mid-commit, mid-blob-rename, mid-lease), upload resume, duplicate, wrong-hash and disk-full cases, and fake-IdP wrong `sub`, `nonce`, `aud` and `exp` cases. Live checks are a guided owner script in `PHASE32SS1_ACCEPTANCE.md` (real Cloudflare tunnel, Google sign-in including Google unreachable, direct Public mode, a second-machine restore, standby promotion, Drive and OneDrive). SS1 is declared complete with those passes owed, as 31E–31J were; 32-SS2 is not gated on them. Android is part of SS1: the public-CA trust mode ships in the Kotlin Hub client with emulator acceptance on the sharded Android CI.

## Deviations and implementation notes

### 2026-10-27, Milestone 829: decisions recorded and program wording amended

This milestone changes documentation only. The program decisions were reworded in place where the SS1 decisions above make their earlier wording wrong, and the dated scope entry required by PD-140 was added to the [program decisions](PHASE32SS_PLAN.md#dated-scope-entries-pd-140) and the [decision log](../history/DECISION_LOG.md#phase-32-ss1-implementation-decisions):

- **PD-064** still stands; the clarification is that the Hub holds no Cloudflare API token, only the tunnel connector token (PD-142).
- **PD-120** no longer says the tunnel uses "proxy pins": the tunnel is remotely managed, devices trust the public CA chain for the tunnel domain and only the loopback hop is pinned (PD-142, PD-143).
- **PD-122** is restated as the gating rule of PD-144 (static assets public; API, websocket and admin gated; the SPA guard keeps tool pages behind sign-in).
- **PD-123** now says the power policy change is a two-step elevated action (PD-152) and the standby device pulls backups (PD-151).
- **PD-124** gains the retention defaults, verify-on-write, the monthly drill, the 2x overdue rule, the standby pull and the Google Drive and OneDrive cut line (PD-150).
- The as-built constraints that 32-SS1 resolves (job queue, backup ceilings, tunnel readiness and pinning, the secret store, the upload parser) now cite the resolving decision, and the "ingest tokens across a restore" question is closed (PD-149).
- The [Hub scope ceilings](../../apps/hub/AGENTS.md) that said "no job queue", "no streaming backups", "no standby replication" and "no UI that creates or schedules a backup" are reworded to the 32-SS1 allowance and its boundaries: the queue runs Hub-internal work only, the standby is a device pull behind a grant, backup v2 streams, and the Hub-web backup UI stays view-only with creation and scheduling on the elevated admin pipe.

Planner judgment calls made at this milestone and reversible only by a dated amendment here: tunnel mode skips Cloudflare edge-certificate pins (PD-143); `savesphere.db` is separate with no `ATTACH` and an outbox (PD-146); an S3 blob tier is deferred (PD-148); the OIDC callback is a narrow GET exemption (PD-144); no new workspace packages (PD-141).

### 2026-10-27, Milestone 830: feasibility go/no-go (GO on all three)

Evidence from `npm run check:hub-capabilities` (`scripts/check-hub-sea-capabilities.mjs`) against the real single-executable Hub built with `npm run hub:compile` and `npm run hub:sea` (Node 24.21.0, SQLite 3.53.4, Windows 11 x64), and again against the CJS bundle under `node`:

- **FTS5: GO.** The `node:sqlite` build inside the SEA creates an `fts5` virtual table with the `porter unicode61` tokenizer and answers `MATCH` with `rank` ordering.
- **sqlite-vec: GO on Windows x64.** `scripts/fetch-sqlite-vec.mjs` (`npm run hub:sqlite-vec`) downloads sqlite-vec 0.1.9 `loadable-windows-x86_64` from the official release, pins the archive (`51581189...8165983`, equal to the release's own `checksums.txt`) and the extracted `vec0.dll` (`fcf98662...76476e6`) and writes it atomically to `build/vendor/sqlite-vec/` (untracked). The SEA verifies the DLL against the same pin (constants kept equal by `db/sqlite-vec.spec.ts`), opens an in-memory database with the new `allowExtension` option of `@dude/sqlite-store`, calls `loadExtension`, locks extension loading again (`lockExtensionLoading`) and reads `vec_version()` (`v0.1.9`). The default entry point works for `vec0.dll`. Extension loading stays off for every other connection.
- **Worker re-spawn: GO.** `apps/hub/src/workers/worker-mode.ts` re-spawns `process.execPath` with `--internal-worker <kind>` in the SEA and `node <bundle> --internal-worker <kind>` otherwise (`sea.isSea()` picks), one JSON line each way over stdio; `main.ts` runs the worker hook before the CLI. The SEA exchanged a message with a child process of itself.

Limitations and decisions recorded rather than worked around:

- The Hub only loads `vec0.dll` found beside the executable (SEA) or in `build/vendor/sqlite-vec/` (Node process), never from `PATH` or an unverified location. A missing, mismatching or unloadable library, a non-Windows or non-x64 host and the Alpine (musl) Docker image report `sqlite-vec` as **unavailable** (`state: 'unavailable'` with a reason, `ok` stays true) in `self-test`; the capability script fails on that only with `--require-vector`. `hub:stage` and the installer do not ship `vec0.dll` yet (a later milestone adds it to the copy list with provisioning status); until then a staged Hub reports vector search unavailable.
- The load is hash-check then `loadExtension` on the same path (no copy), so a local attacker who can write to the Hub's install directory could race it; that directory is already the trust root for the executable itself.
- `dude-hub run` keeps its fail-fast self-test but skips the vector and worker probes (`runSelfTest({ capabilities: false })`) so a start never spawns a child or reads the DLL; `dude-hub self-test` runs them all.
- FTS5 and worker re-spawn are hard requirements of the self-test (failure fails it); vector search is the only optional capability.
- The queue, the worker host and any non-`ping` worker kind are Milestone 834.

### 2026-10-27, Milestone 831: Hub secrets module

`apps/hub/src/secrets/` adds the `SecretStore` (closed `HUB_SECRET_PURPOSES`, one DPAPI entropy and one file per purpose under `<configDir>/secrets/`, `status()` presence only). Notes:

- It reuses `createDpapiProtector` and `createFileProtector` from `tls/ca-key-protector.ts` unchanged instead of extracting a `secrets/dpapi.ts`, so the CA, ACME and backup-schedule protectors and their specs are untouched.
- Limitation: the Linux/Docker fallback is a mode-0600 file in a mode-0700 directory (file-permission protection only), as for the CA and ACME keys.
- `HubPaths.secretsDir` was added; `ensureLayout` does not create it (the store creates it on first `put`). Backups hold only `dude.db` and `hub.json`, so the directory is never included (asserted in `secrets.spec.ts`); after a restore onto another machine DPAPI blobs are unreadable and every purpose needs re-entry. `status({ expected })` reports `needsReentry`; which purposes are expected comes from the provisioning config, which arrives at Milestone 835.
- The importer allowlist in `secrets.spec.ts` is empty until the first consumer (Milestone 832 onwards) adds itself.


### 2026-10-27, Milestone 832: `savesphere.db` content store foundation

`apps/hub/src/savesphere-db/` adds `openSaveSphereDb(paths, options?)`, its own migration sequence (`SAVESPHERE_MIGRATIONS`, `0001-platform`: `meta`, `schema_migrations`, `audit_outbox` only) and `audit-outbox.ts` (`appendAuditOutbox`, `drainAuditOutbox`, `drainAuditOutboxAtStart`). Notes:

- `HubPaths` gains `saveSphereDbPath` (`data/savesphere.db`) and `saveSpherePreMigrationDir` (`data/pre-migration/savesphere`, a subdirectory because the runner's backup pruning keeps the newest three `pre-v*.db` files of a directory and would otherwise count both databases together). `ensureLayout` does not create either; only `openSaveSphereDb` does, and nothing calls it yet except the start-up drain (provisioning is Milestone 835).
- The start-up drain in `cli/run.ts` runs only when `savesphere.db` already exists, opens it, drains and closes it, and swallows errors, so a Hub that never provisioned SaveSphere gets no file and an unreadable store never blocks start. The audit writer is the existing `audit()`; `HUB_AUDIT_EVENTS` is not widened (no first producer yet), so the specs use an existing event.
- Idempotence: the drain writes the row's `dedupe_key` into the audit detail as `outboxRef` and looks for it before writing, so a crash between the audit write and `drained_at` never duplicates the event. `appendAuditOutbox` refuses to run outside a transaction (`db.isTransaction`) and validates the event and detail (the Hub audit sanitizer) at append time so a bad event rolls the content back. Drained rows are pruned after 30 days.
- `backup/snapshot.ts` exports `HUB_KEPT_TABLES`, `SAVESPHERE_SCRUBBED_TABLES` (`audit_outbox`) and `SAVESPHERE_KEPT_TABLES`; `backup/classification.spec.ts` opens both real databases and fails on any unclassified table. Backup v1 behaviour is unchanged; the engine integrates `savesphere.db` at Milestone 847.
- `allowExtension` stays off unless the vector component asks; `SaveSphereDb.lockExtensions()` re-locks it.

### 2026-10-27, Milestone 833: content-addressed `BlobStore`

`apps/hub/src/blobs/` adds the `BlobStore` interface (`blob-store.ts`), the local-disk implementation (`local-blob-store.ts`), the catalogue and reference counts (`registry.ts`, migration `savesphere.db` 0002-blobs: `blobs`, `blob_refs`), the blob lease (`lease.ts`), `verifyBlobBatch` (`verify.ts`) and mark-and-sweep GC (`blob-gc.ts`, with `blob-gc.confirmation-boundary.spec.ts`, which the high-consequence gate's `confirmation-boundary` Hub filter already picks up). No job runner and no admin methods are registered: the queue arrives at Milestone 834 and the admin wiring at 835/847. Deviations from the architecture sketch:

- **Interface names and types.** `open` replaces the sketch's `get`, it returns a Node `Readable` (the Hub's stream type), and `put` accepts a buffer or any async-iterable of bytes (Node `Readable` or web `ReadableStream`). `has` and an optional `expectedSha256`/`maxBytes` on `put` were added; `list`, `delete`, `verify` and `stat` follow the sketch. `LocalBlobStore` also exposes `sweepStaging(maxAgeMs)`.
- **No overwrite without `rename`.** `put` hard-links the fsynced staging file to its final name and unlinks the staging name (`EEXIST` is the dedupe hit); `rename` is used only on a filesystem without hard links. `HubPaths` gains `blobsDir` (`storage/blobs`) and `stagingDir` (`storage/staging`); `ensureLayout` does not create them. `storage/staging/` is shared with the later import staging (PD-132): the sweeper only touches `*.part` files.
- **`blobs.unreferenced_since`** was added beside the sketched columns (`sha256`, `size`, `created_at`, `verified_at`, `state`) so the grace period counts from when the last reference went, not from the upload: it is set on record and on the last `removeBlobRef`, cleared by `addBlobRef`, and restarted by re-storing identical content. `state` is `ok`, `corrupt`, `missing` or `deleting`. `blob_refs` is `(blob_sha256, owner_kind, owner_id)` with the three as primary key and a foreign key to `blobs`. The migration floors the reader at 2.
- **GC.** `planBlobGc` is read-only (capped at 10 000 candidates, `truncated` flag); `previewBlobGc` stages a single-use 60-second token bound to the SHA-256 of the grace period and the exact candidate list (and the `cli` binding); `applyBlobGc` takes the `gc` lease first (a refused apply keeps the token), spends the token against the digest recomputed from the plan presented, then per blob re-checks references and the grace period in a transaction, marks `deleting`, removes the file, then the row. A failed file delete leaves the `deleting` row for the next GC. The grace period must be at least one hour (default seven days). Preview audits nothing (it must write nothing); apply appends one `blobs.gc-applied` outbox event.
- **Lease.** `meta` keys `blob_lease:gc` and `blob_lease:backup` (JSON `expiresAt`, 15-minute TTL, renewable) are mutually exclusive between holders; the backup engine (Milestone 847) takes `backup` while it reads the blob set from its snapshot. The keys are transient: Milestone 847 scrubs them from the snapshot (`SAVESPHERE_SCRUBBED_META_PREFIXES`) and the restore removes them again.
- **Audit events.** `HUB_AUDIT_EVENTS` gains `blobs.verify-failed` and `blobs.gc-applied` (written only through the outbox). `SAVESPHERE_KEPT_TABLES` gains `blobs` and `blob_refs`; the blob bytes are backup v2's concern. `0001-platform.spec.ts` now pins its own one-migration sequence instead of the full list.
- **Known narrow window.** If a re-upload of old unreferenced content dedupes against a file in the instant between GC's claim and its row delete, `recordBlob` refuses a `deleting` row and the caller re-puts; if GC finished completely in that gap the row would be recorded for a missing file, which the verify job flags as `missing`. The upload commit (Milestone 845) re-checks `has` after recording.

### 2026-10-27, Milestone 834: durable job queue and isolated workers

`apps/hub/src/queue/` and `apps/hub/src/workers/` add the queue, the runner and the worker host; `GET /api/v1/queue`, `HUB_JOB_IDS` growth and the `@dude/api-client` `queueStatus` method surface them. Deviations from the architecture sketch and decisions made here:

- **States.** `queued`, `running`, `succeeded`, `failed`, `dead` (not the sketch's `leased` and `canceled`; cancellation is not built, and there is no owner cancel or retry, which stays a later and separately decided scope). A failed retryable attempt returns to `queued` with a later `run_after`; `failed` is the terminal non-retryable state (a handler `PermanentJobError`, a worker out-of-memory abort, a kind with no handler) and `dead` means every attempt was used. Times are integer epoch milliseconds, unlike the ISO text of the older tables. `savesphere.db` migration 0003 floors the reader at 3; `jobs` is `SAVESPHERE_SCRUBBED_TABLES` (a restored Hub starts with an empty queue; the `queue_schedule:*` meta keys are kept and only make a schedule due early).
- **Idempotency** is unique among ACTIVE jobs (`queued` or `running`) through a partial unique index, so a scheduled job that is still waiting is never queued twice while a finished one can run again. Durable idempotency on (source hash, processor, version), which the processing pipeline needs, is that phase's check against content state.
- **Crash safety.** A claim counts as an attempt; a lease (60 s, renewed every third of it) that expires is recovered at runner start and every minute, with the same backoff as a failure and dead-lettering after `max_attempts` (default 5). A graceful stop `release`s running jobs without costing an attempt. Every holder-side change names the lease owner, so a stale holder gets `lost` instead of touching a re-claimed job.
- **Payload and error hygiene.** `enqueue` refuses a credential-looking key at any depth and a payload over 64 KiB; `last_error` is passed through `redactJobError` (paths, bearer tokens, secret-looking `key=value` pairs and long token-like runs removed, 300 characters) before it is stored, and the status route redacts again on read.
- **Handlers.** `JOB_KINDS` is `noop.echo`, `blobs.verify`, `blobs.staging-sweep`, all `inline` because each needs the Hub's own database or blob store. `worker` isolation is built and tested but has no production kind yet; the extension point is `JOB_KINDS` plus the handler map (`queue/handlers.ts`) plus `workers/worker-job-handlers.ts` (empty), and a spec fails if a declared worker kind has no implementation. An inline handler is only signalled on timeout (keep it short); a worker is killed.
- **Worker host.** One child per job (the Hub executable re-spawned as `--internal-worker job`), at most `size` (default 2) at once, a per-job scratch directory under `storage/workers/` (`HubPaths.workersDir`, emptied at pool start) as the child's working directory and temp location, `NODE_OPTIONS=--max-old-space-size=<mb>` for the heap ceiling (the same route works for the single-executable application, whose `execArgvExtension` defaults to the environment; not yet exercised inside a built SEA, an owed check), an allowlisted environment (`SystemRoot`, `windir`, `TZ`, `LANG`, `LC_ALL`; nothing else of the Hub's, no `PATH`; Windows itself still adds its own baseline variables to any child), a wall-clock kill with `taskkill /T` on Windows, out-of-memory detected from the child's stderr, and a crash back-off before the next spawn. The child exits when its stdin closes. Limits recorded: the heap ceiling does not bound native allocations, Windows Job Objects are not reachable from Node, and an event loop blocked inside a worker cannot notice a dead Hub until it yields. The pool size is an option of `createWorkerPool` and `createQueueRuntime`, not yet a `hub.json` field (provisioning, Milestone 835, decides the surface).
- **Wiring.** `run` creates the runtime only when `savesphere.db` already exists (a Hub that never provisioned gets no runner, pool or file), starts it after the other timers and stops it first at shutdown. `HUB_JOB_IDS` gains `queue-runner` (recovery, pruning and scheduling; reported only when it changed something, plus once at start), `blobs-verify` (every 6 h, 25 blobs) and `blobs-staging-sweep` (every 24 h, files older than 24 h); both are scheduled by the runner through idempotent enqueues and tracked in the job registry around each attempt, and a verify that finds a corrupt or missing blob shows as failed there. On a Hub without `savesphere.db` the three ids show as never run with no timer, so the bundle spec asserts a zero interval for them. The web Hub-jobs panel gained their display names (a type-checked map, not a behaviour change).
- **Read route.** `GET /api/v1/queue` is owner cookie or bearer, read-only (no CSRF, no audit, like `GET /api/v1/jobs`), `available: false` with zero counts when there is no store. There is no enqueue route.
- **Not done here.** Progress is passed to the pool's `onProgress` but not persisted or shown; no per-kind concurrency caps, cancellation or priority aging; the GC and upload-expiry jobs are registered by their own milestones; no real worker kind exists to prove SEA execution of a worker job beyond the M830 `ping` proof.

### 2026-10-27, Milestone 835: provisioning engine

`apps/hub/src/provisioning/` adds the engine (`engine.ts`: `provision`, `checkProvisioning`), the component registry (`registry.ts`, `registerProvisioningComponent`), the eight built-in components (`components/`), the cache helper (`cache.ts`) and a status service (`service.ts`); `dude-hub provision [status] [--json]` (`service/provision.ts`), the admin methods `provision.run` and `provision.status` (`admin/provisioning-methods.ts`), `GET /api/v1/provisioning` with `HubProvisioningResponse` in `@dude/contracts/hub`, `provisioningStatus` in `@dude/api-client` and the `provisioning.run` audit event. Deviations from the architecture sketch and decisions made here:

- **Statuses.** Components report `ready`, `degraded`, `unavailable`, `not-configured` or `needs-attention` (not the sketch's `not provisioned`/`failed`); `unavailable` is a by-design answer (vector search on Docker) and never lowers the overall state. The overall state is `not-provisioned`, `needs-provisioning`, `needs-attention`, `degraded` or `ready` (`deriveOverall`). A component that is not built (`tunnel` 836-837, `backup` 847 on, `oidc` 841, `power` 851) is absent from the report; its id is already reserved in the closed `HUB_PROVISIONING_COMPONENT_IDS`, so adding it edits only its own module and one line in `components/index.ts`.
- **Needs re-provision after a restore** is derived, not stored as a flag: no recorded run, a run recorded by another Hub identity (a restore creates a new one; the run record lives in `savesphere.db` `meta`, a kept table), a core directory missing, or a secret expected but absent. The expected secret purposes are also a `meta` key (`provisioning_expected_secrets`, names only), recorded by a provision run for every purpose present, so a restored Hub (machine-bound secrets never travel) reports `needsReentry` per purpose. Later milestones record a purpose with `setSecretExpected` when the owner stores a secret. A restored `hub.json` that keeps only the port and names holds no provisioning state, so the spec simulates the restore by copying `savesphere.db` into an otherwise empty data directory with a reduced `hub.json`.
- **No confirmation token.** A run only creates what is missing, so it is not destructive; it is still an owner-intent state change and writes `provisioning.run` through the outbox in the same `savesphere.db` transaction as the run record (credential class: the elevated admin pipe). It is single-flight per data directory (a concurrent caller joins the running run).
- **Cache location.** `HubPaths.cacheDir` is `storage/cache`, not the sketch's top-level `cache/`: `purge` already removes `storage/` (so the Destructive-Action Contract and its confirmation-boundary spec are untouched) and backups never hold it. The bound is the constant `DEFAULT_CACHE_MAX_BYTES` (1 GiB), swept oldest-first by every provision run; a `hub.json` field is later work.
- **Probes touch no live data.** The queue check runs a `noop.echo` job through the real queue and handler code against an in-memory database with the real migrations (a probe row in the live `jobs` table would race the runner and leave residue); the blob round trip uses a throwaway store under `storage/staging/.probe-*` and removes it. The FTS5 and worker re-spawn probes are the Milestone 830 code, now exported from `cli/self-test.ts`. The vector probe's reason (which names a path) is mapped to fixed sentences.
- **No `vec0` table yet.** SS1's "schema slot" for the vector index is the availability record only; a table that needs the extension at every open (and survives `VACUUM INTO` and the scrub) is SS5's decision.
- **A running Hub that started without `savesphere.db`** has no queue runner. A run that creates the store there returns `restartRequired` and the queue component reports `needs-attention` ("restart the Hub service") until it does; `run` passes `queueRunning` to the engine, the CLI engine and specs leave it unknown.
- **Wiring.** `run` creates one `ProvisioningService` (60 s cached read model for the route, invalidated after a run) and, only when `savesphere.db` exists, runs a read-only check after listening that logs the overall state and per-state counts, never a detail sentence. The route is owner cookie or bearer, `no-store`, no audit, and reports `not-provisioned` with the commands when no read model is wired or the check throws; the secret store is imported only by `provisioning/components/secrets.ts` (added to the `secrets.spec.ts` allowlist), never by a request handler.
- **CLI.** `dude-hub provision` needs the elevated terminal when the service is installed and the Hub running (it never opens a database itself; a stopped Hub exits 2); `provision status` is read-only. Exit codes: 0 ready or degraded, 1 needs attention, needs provisioning or a failed call, 2 usage or Hub not running. `provision.run` takes no parameters today and refuses any (the wizard's `secrets` parameter over standard input is Milestones 837 and 853, not built here).
- **Owed.** A real Windows service pass (elevated `dude-hub provision` against the installed Hub, the worker probe inside the SEA, `vec0.dll` beside the executable) belongs to the acceptance script; Docker is covered by the Linux secret-file fallback in the specs only.

### 2026-10-27, Milestone 836: pinned `cloudflared` and the process supervisor

`scripts/fetch-cloudflared.mjs` (`npm run hub:cloudflared`, part of `hub:stage`) pins **cloudflared 2026.10.4**, asset `cloudflared-windows-amd64.exe`, SHA-256 `411b16d40c8d872243efeb52c550053d00af0a8a97fbb32e730fb8aba429eaa8`. The value was computed from a real download and equals both the checksum in the release notes and the GitHub asset digest; the binary runs (`--version` reports 2026.10.4). It is written atomically to the gitignored `build/vendor/cloudflared/cloudflared.exe`, staged by `stage-hub.mjs` as `cloudflared.exe` (with its `SHA256SUMS` line), copied beside `dude-hub.exe` by `service install|update` (`CLOUDFLARED_EXE`, optional in a source directory so an older stage still installs), removed by `service uninstall` and the installer's uninstaller, and required by `build-hub-installer.mjs` and `check-hub-service.mjs` (which also asserts the update installed the staged copy). The image lookup uses CIM through PowerShell (about a second, only when a pid file exists).

- **Owed.** A real run of `cloudflared.exe` against a Cloudflare tunnel (the readiness probe's `/ready` contract is the documented one and is exercised only against the stub), the installed-service orphan sweep after a killed Hub, and `hub:stage`/`check:hub-service` inside the elevated CI job (staging was run locally; the service check needs elevation).

### 2026-10-27, Milestone 837: managed Cloudflare Tunnel mode and the tunnel-aware readiness gate

`dude-hub network tunnel on|off|status` (admin methods `network.tunnel.preview|apply|status`, `admin/tunnel-methods.ts`, CLI `service/tunnel.ts`), `exposure.tunnel` in `hub.json`, `tunnel/tunnel-runtime.ts`, `GET /api/v1/tunnel` (`HubTunnelStatusResponse`, api-client `tunnelStatus`), `evaluateTunnelReadiness`, the `www` redirect in the Host guard, the `tunnel` provisioning component, the `HUB_TUNNEL_DISCLOSURE` and `HUB_TUNNEL_PHRASE` constants and the audit events `tunnel.enabled|disabled|token-set|degraded`. The security contract is in [SECURITY_ARCHITECTURE](../architecture/SECURITY_ARCHITECTURE.md#as-built-in-32-ss1-managed-cloudflare-tunnel-milestone-837) and the Hub rules in `apps/hub/AGENTS.md`. Decisions and deviations:

- **The hop to the Hub is HTTPS on loopback with the Hub's own certificate (no plain-HTTP listener).** Proxy mode already expects TLS to the Hub, and a second, plain-HTTP listener only for the tunnel would be a new always-open surface and a new Host/cookie code path for no gain on a loopback-only hop. The owner enters in the dashboard: service type `HTTPS`, URL `https://127.0.0.1:<hub port>`, "No TLS Verify" on (the Hub's certificate is private and the hop never leaves the machine; verifying it needs a CA file path that a remotely managed tunnel cannot receive) and no "HTTP Host Header" override. `network tunnel on` prints these and `GET /api/v1/tunnel` returns them as `dashboard`.
- **`hub.json` carries `exposure.tunnel: { enabled, hostname }` only; there is no `metricsPort`.** Milestone 836 chose a fresh free loopback metrics port per launch, so a configured one would be dead state. The block is valid only with the proxy block it implies (`trusted` exactly `127.0.0.1` and `::1`, `publicOrigin` `https://<hostname>`); `off` removes both and returns a `public` mode that could no longer accept traffic to `private`. An operator's own reverse proxy is never replaced (`conflict`). `enabled` is always true when the block exists today; it is kept so a later pause without losing the hostname does not need a schema change.
- **Two steps, with the connector started inside the apply.** The readiness gate includes the connector, so `apply` stores the token, starts the supervised connector, waits for it to be ready (45 s) and then evaluates the gate with the diagnostics override `{ mode: 'public', tunnel: { hostname } }` (the engine reports as if the change were written: loopback bind, loopback hop, tunnel facts from the live connector); only a pass writes `hub.json`. A refusal stops a connector that call started and writes nothing, but a token supplied in that call stays stored (the owner pasted it; `network tunnel off --forget-token` deletes it). The preview checks everything except the connector (`checkedAtApply`) and issues no confirmation when anything else blocks. The phrase is checked before the confirmation is spent, so a typo does not burn it. `off` also needs a confirmation but no phrase (it narrows exposure).
- **`external-reachability` stays a blocker, so the first `on` needs `--accept-unverified-reachability`.** The Hub cannot observe a public client through a name it does not serve yet, and Host-guard and proxy trust are read at start, so verification can only follow the restart. The flag is audited in `tunnel.enabled` and downgrades the blocker to a warning; later runs of the gate (including `network mode public` with the tunnel on, which uses the same tunnel blocker set) need a fresh verification.
- **`tunnel.degraded` and the status are not in the job registry.** `HUB_JOB_IDS` is timer-shaped and read-only, so the tunnel reports through `GET /api/v1/tunnel` (state, restarts, last ready time, a log tail of at most 20 redacted lines), the diagnostics `tunnel` facts and the provisioning component instead. The provisioning component maps `connecting` and a stopped connector to `degraded` because the contract's component states have no `connecting`; the route's own `state` is exact.
- **The `www` redirect applies in tunnel mode only.** The guard accepts exactly the bare domain, `www.<domain>` (with and without `:443`) and loopback names through the connector; the OS host name and other configured names are not served there. A peer that is not `127.0.0.1` or `::1` gets loopback names only and is never redirected. A reverse proxy that is not the tunnel keeps its previous behavior.
- **Redaction and audit.** The connector token is in the secret store and the child's environment only. The audit sanitizer refuses credential-looking keys, so `tunnel.disabled` records `forgotten` (a boolean) rather than a token-named field; `tunnel.token-set` has an empty detail. A new `readSecretLine` in `cli/passphrase.ts` reads the token from a piped standard input or a no-echo prompt and never from the environment (the passphrase environment variable is deliberately not consulted).
- **SECURITY.md** is generated: the Hub row of the Network Listeners table (hand-maintained in `scripts/generate-security-doc.mjs`) now says the Hub supervises `cloudflared` with outbound connections when the tunnel is on, and the generated file was regenerated. `docs/architecture/data-scope-inventory.json` gained one reviewed heuristic (`tunnel-runtime.ts`, a DPAPI secret write).
- **Tests.** `tunnel-methods.confirmation-boundary.spec.ts` (in the high-consequence gate), `tunnel-edge.spec.ts` (the stub cloudflared forwards to a real Hub test server as the edge does: forged `X-Forwarded-For`, `-Proto` and `-Host`, the `www` redirect, exact hosts, and an untrusted peer sourced from `127.0.0.2`), `readiness-tunnel.spec.ts` (each blocker pass and fail, the other modes unchanged), `host-guard-tunnel.spec.ts`, `tunnel-config.spec.ts`, `tunnel-runtime.spec.ts`, `tunnel-component.spec.ts`, `server/tunnel.spec.ts`, `service/tunnel.spec.ts` and the contract spec.
- **Owed.** A real tunnel on a real Windows service (the dashboard values, `cloudflared.exe` ready through Cloudflare, `www` through the real edge, the reachability verification after the restart, an elevated `network tunnel on` with the typed phrase, the service stop killing the connector tree, and that the edge's `X-Forwarded-For` reaches the Hub so rate limits and the reachability echo see the real client rather than loopback) belongs to the acceptance script. No Hub-web Settings control exists yet (Milestone 852 shows the read-only status; the desktop wizard is Milestone 853). `tunnel.degraded` raises no owner notification (the closed producer list is unchanged). Devices still pin the Hub certificate until Milestones 838 and 839 add public-CA trust for the tunnel domain.

### 2026-10-27, Milestone 849 (Hub side): the warm-standby grant and the device-token pull routes

The Hub half of PD-151: the per-device standby grant, its two-step admin methods and CLI, and the device-token routes a standby pulls the encrypted repository through. The desktop puller (desktop main) and the promotion guide are the second half of this milestone. Files: `apps/hub/src/standby/` (`grants.ts`, `repositories.ts`), `server/routes/standby.ts`, `admin/standby-methods.ts`, `service/standby.ts`, migration `0013-standby-grants`; contracts `@dude/contracts/hub` `standby.schema.ts`; client methods `standbyRepositories`, `listStandbyObjects`, `getStandbyObject`. Decisions and deviations:

- **The grant is its own table, not a `devices` column.** `standby_grants` (device id, the device's `registered_at` at grant time, grant time; migration 0013, additive, reader floor unchanged) is SCRUBBED from backups and cleared by a restore (`SCRUBBED_TABLES`, `classification.spec.ts`), so a restored Hub never opens its repository to a device the owner has not granted again. `notifications_access` is a kept column; a standby grant opens the backups, so it follows the stricter rule. A grant is effective only while the row is an active desktop that does not await re-pair AND still has the enrollment it was given to (`registered_at` unchanged): a revoked, unenrolled, re-enrolled or re-attached device holds none, re-read on every request.
- **Owner-set on the elevated admin pipe only, not by an owner HTTP route.** PD-151 says "owner-set, step-up-gated"; the notifications grant is an owner route with step-up, but backup operations stay on the elevated pipe (scope ceiling: no UI that creates or schedules a backup), and opening the repository to a device is backup-grade, so the elevated pipe (a local administrator on the Hub machine) is the gate. Admin methods `standby.list`, `standby.grant.preview|apply`, `standby.revoke.preview|apply`; CLI `dude-hub standby list | grant <deviceId> | revoke <deviceId> [--confirm <token>]`. Both changes are two-step (single-use 60-second ConfirmationStore token bound to the device, its `registered_at` and the grant row it saw; actions `STANDBY_GRANT_ACTION`, `STANDBY_REVOKE_ACTION`; classes `authentication` and `database-write`), audited `standby.granted` / `standby.revoked` (actor `cli`, device id only) and both are in `SECURITY_ALERT_EVENTS` (so they also reach the owner's alerts and the notification producers). Boundary spec `admin/standby-methods.confirmation-boundary.spec.ts` (picked up by the high-consequence gate by name) also proves no HTTP route grants or revokes and no `server/`, `auth/`, `realtime/`, `devices/`, `security/` or `sync/` module references the grant writers.
- **Routes (device token only, then the grant).** `GET /api/v1/standby/repositories` (the grant time and the servable repositories: id, `kind: 'local-folder'`, label, `lastSuccessAt`, `lastBackupId`; never a folder), `GET /api/v1/standby/repositories/:destinationId/objects?prefix=repo|manifests/|packs/&after=<name>&limit=<1..5000>` (committed objects ascending by name with sizes, `next` cursor; default page 1000) and `GET /api/v1/standby/repositories/:destinationId/object?name=<repo|packs/<id>|manifests/<backupId>>` (`application/octet-stream`, streamed through the destination's chunked reader, never buffered; one `Range: bytes=a-b|a-|-n` gives 206 with `Content-Range`; a multi-range, malformed or unsatisfiable range is 416 with `Content-Range: bytes */<size>`; no automatic HEAD). A device without the grant is 403 `forbidden` ("This device has not been granted standby access.", the notifications wording); an owner cookie or bearer is the device resolver's 403; an ingest token, an unknown, revoked or unenrolled device and anonymous are 401. The per-device bucket of `requireDevice` applies, plus at most `STANDBY_MAX_CONCURRENT_STREAMS` (4) open object streams per device (429). The object name in a query parameter (not a path wildcard) keeps the route template plain for the parity and gating specs.
- **Ciphertext only, local folders only, the engine untouched.** `standby/repositories.ts` reads the stored objects through `createLocalFolderDestination` (the location rule re-applied on every open) and never opens a repository, reads the master key or a passphrase, decrypts or writes; it does not import the engine. S3 destinations are not served (the data is already off the machine). Objects named in a destination's unrecorded-run journal (`backup_dest_journal:<id>`) are hidden from the listing and 404 on fetch, so a standby never mirrors an unverified manifest or the packs of a run that is about to delete them (`STANDBY_JOURNAL_PREFIX`, asserted equal to `BACKUP_JOURNAL_PREFIX`). `repo` is the one object that can change (a re-wrap replaces it): the contract tells the puller to re-fetch it whenever its listed size changes.
- **Audit.** `standby.denied` (outcome denied, a device without the grant, at most once an hour per device) and `standby.pulled` (the last byte of a manifest was delivered, once per device and backup: the manifest is the backup's commit point, so the puller fetches packs first and each manifest last) are the per-request events; listings and pack reads are not audited (they would drown the log), like notification reads. Both dedupe sets are in memory and bounded (1024), so a Hub restart may audit a pull again. Details carry ids only, never a path, a token or bytes. The four events are appended to `HUB_AUDIT_EVENTS`.
- **Client.** `HubRequest.responseType: 'bytes'` is new: a transport that supports it returns a 2xx body as a `Uint8Array` and still parses an error envelope; `getStandbyObject(auth, destinationId, name, range?)` returns `{ status, bytes, start, end, size }` and refuses an answer whose `Content-Range` does not match the bytes or the requested start. No existing transport implements `responseType` yet: the desktop puller's pinned transport (Device Agent or desktop main) must, and the web and mobile transports never need it.

### 2026-10-29, Milestone 849 (desktop half): the standby puller and the promotion guide

The second half of PD-151: the puller that mirrors the Hub's encrypted backup repositories into a folder the user chose, the desktop bridge that picks the folder, and the promotion guide ([WINDOWS_SETUP.md](../WINDOWS_SETUP.md#keeping-a-warm-standby-on-a-paired-desktop), "Keeping a warm standby" and "Promoting the standby after the Hub is lost"). - **The puller lives in the Device Agent, not in desktop main.** The plan said "puller in desktop main", but the device token and the pinned or public-CA transport exist only in the Agent (`apps/desktop/AGENTS.md`: owner sessions and pinned TLS live there), and the Agent keeps running with no window, so a standby keeps pulling while nobody is signed in to the app. Desktop main only shows the folder dialog and forwards three calls. It reuses `hub.manager.deviceCall(..., { authRetryOn403: false })` (a 403 is the grant refusal, not an auth failure) and gates on the connection state (`online` only; `standalone` is `not-enrolled`), so nothing is requested while the Hub is unreachable.
- **`responseType: 'bytes'` in the pinned transport.** A 2xx answer is returned as a `Uint8Array` of exactly the received bytes under its own cap (`HUB_MAX_BYTES_RESPONSE_BYTES`, 16 MiB; the puller asks for 8 MiB pieces), any content type; a non-2xx answer is still a JSON error envelope under the 1 MiB cap; the JSON path is unchanged. `pinned-transport.spec.ts` covers the bytes, error, cap and unchanged-JSON cases against a real TLS server.
- **The pull.** Per repository: list `manifests/` (L1), `packs/` (P), `manifests/` again (L2) and `repo` (cursor-validated, strictly ascending, kind-checked, sizes checked); prune manifests, then packs, then stale partials not in L2/P; fetch `repo` whole on every run (a passphrase re-wrap need not change its size); fetch each missing pack in 8 MiB `Range` pieces into `<folder>\.standby-partial\<id>\<kind>-<name>.part`, synced per piece, resumed from the partial's size, size-checked against the listing and each piece against its `Content-Range`, renamed into place; only when every pack arrived fetch the manifests of L1 and L2, last (a manifest only in L2 waits for the next run, because its packs may have been committed after P was listed). A wrong-size final file or partial is replaced, never resumed. A pack 404 after the listing means the Hub pruned it: no manifest that run (`changed-during-pull`). A destination whose listing shows no backups while the mirror holds some is left untouched (`listing-empty`): that is the case the standby exists for. The mirror layout equals the Hub's `local-folder` destination, so it restores with `backup restore --folder <folder>\<id>`.
- **Hostile names.** Repository ids, object names and every derived path are checked against the closed grammar and re-checked to be strictly inside their directory (`standby-mirror.ts`); a listing that violates it fails the run as `hostile-listing` before anything is fetched. Only ciphertext is written and no passphrase or key is ever requested.
- **Retry policy.** First run 2 minutes after the Agent starts, then hourly; 403 (`no-grant`, with the `dude-hub standby grant` hint) every hour; 401, 429 (floor 30 s) and other failures back off 1 minute doubling to 30 minutes with up to 25% jitter, reset by a success. State (folder, last attempt and success, error, repository summary) is the `standby-puller` device doc in the Device State Store, so no new JSON file and no schema migration.
- **Desktop bridge.** `dude:standby:status|pullNow|chooseFolder` (`window.dude.standby`), window-only sender check, exactly zero arguments (the renderer can never supply a path), the native folder dialog is shown in main and its result goes to the Agent's `standby.setFolder` (an existing absolute directory; null stops pulling and leaves the files). Errors carry a code and a path-free message.
- **Tests.** `standby-puller.spec.ts` (a fake Hub client over an in-memory repository and a real folder: byte-identical mirror, ranges and order, pagination, no-op and `repo` refetch, retention prune confined to the mirror, `listing-empty`, L2-only manifests, vanished packs, tampered files, resumed and discarded partials, hostile listings, size and piece mismatches, `not-configured`, `not-enrolled`, waiting for the Hub, `no-grant`, exponential and 429 back-off, removed folder, folder validation, persistence), `standby-mirror.spec.ts`, `rpc/standby-rpc.spec.ts`, `hub/pinned-transport.spec.ts`, `device-store/standby-bridge.spec.ts`.

### 2026-10-29, Milestone 853: the desktop Hub provisioning wizard

Locked decision 5, built: after `setupLocalHub` (or at any later time, idempotently) the desktop drives the Hub's platform set-up from Settings > Environment & Hub. One Windows administrator prompt opens ONE elevated `dude-hub provision` session that serves the wizard's steps: status, create storage, the Cloudflare tunnel, Google sign-in, backups, the power policy and the standby grant, then a restart. Decisions and deviations:

- **The secrets travel over a pipe, not standard input.** Windows starts an elevated process through the shell (`Start-Process -Verb RunAs`, the mechanism `local-hub.ts` already uses), which cannot redirect the new process's standard streams, so a literal "stdin" is not available to an unelevated parent. The desktop creates a random per-run named pipe (`\\.\pipe\dude-hub-provision-<24 random bytes, base64url>`, accepts exactly one connection, then stops listening), and the elevated process connects to it and treats it as its standard input and output, one JSON line per request. The pipe name is the only session value on the command line (with `--data-dir` and `--install-dir`); the connector token, the backup passphrase and the Google client secret each travel in one request line straight into the admin call that stores them, are not kept by main after it, and never reach an argument, an environment variable, a file, a log, an audit row or an error (main also redacts every secret of a request from any error text). The pipe has Windows' default security descriptor, so only the creating user and administrators can write to it; a process of the same user that learns the 192-bit name before the elevated process connects could still race it, which is the same trust the setup-token hand-off file already has (an owned limit, recorded in the security architecture).
- **The session is a closed set of named operations, not an admin proxy.** `PROVISION_SESSION_OPS` (`status`, `provision`, `tunnel-preview`, `tunnel-apply`, `oidc`, `power-preview`, `power-apply`, `backup`, `standby-preview`, `standby-apply`, `restart`) each has a strict parameter check (unknown keys refused without echoing them) and maps to fixed admin methods; there is no operation for `tunnel off`, `network mode`, purge, restore, uninstall or any other admin method. It reuses the CLI's own helpers so nothing differs from the terminal: the native-listener host facts for the tunnel gate, the LAN firewall rule removal after `tunnel on`, and `runServiceControl('restart')` (with its output discarded). Errors carry the Hub's own value-free code and message; anything else becomes one fixed sentence. It needs the elevated terminal and a running Hub, exits 2 otherwise without connecting, and ends when the pipe closes or after 20 minutes idle. No Hub route, sync credential or Hub-web control reaches it.
- **Status is read inside the session.** `provision status` over the admin pipe is not reachable unelevated (the pipe's DACL is admin-only), and an owner-bearer read through the Device Agent would be a new Agent method, channel and port for a read the Hub-web panel already shows; the wizard's first step is therefore "start" (the one prompt) and its status is the session's `status` operation (provisioning report plus the tunnel, power and backup summaries and this desktop's device id from the Agent). A non-elevated status on the desktop is not built.
- **Exposure and machine settings stay two steps, enforced in main as well.** `tunnel-preview` changes nothing and returns the dashboard values (`hubTunnelDashboardLines`, the single source), the disclosure, the readiness warnings, whether a connector token is needed and the exact phrase; main remembers the preview (host name, acceptance flag, token, time) and accepts `tunnel-apply` only for that confirmation, once, within 60 seconds. The typed phrase is supplied by the user (the apply button is disabled until the typed text equals it exactly); main refuses a wrong or missing phrase before anything is sent (the session and the Hub check it again) and keeps the preview for a retry, while a failure after the Hub spent the confirmation drops it. The first `on` needs the owner's explicit "reachability can only be verified after the restart" checkbox (`--accept-unverified-reachability`). Power and standby apply the same way, and the standby device id comes from the Agent, never from the renderer. Nothing is auto-confirmed. The desktop confirmation-boundary spec (`hub-provision.confirmation-boundary.spec.ts`) is in the high-consequence gate beside the Hub's (`provision-session.confirmation-boundary.spec.ts`, picked up by name) and the wizard's.
- **The renderer supplies no path, command or method.** `dude:hub:provisionStep` takes one object validated against a closed grammar (exact keys, bounded strings, a host-name pattern, the connector token's shape, an integer hour interval); the backup folder is picked in the native dialog in main (`dude:hub:provisionChooseBackupFolder`, like the standby folder of Milestone 849) and main puts it into the backup operation. The channels are sender-checked, argument-count checked and registered by `hub-bridge.spec.ts`' one-channel-per-method rule; `onProvisionProgress` carries the wait for the administrator prompt, each step's running/done/failed and a session that ended by itself. Results are rebuilt field by field in main before they cross.
- **New Hub admin method `oidc.configure` (and audit event `oidc.configured`).** The Milestone 841 owed item: the wizard step that enters the Google client secret and writes the `oidc` block. Admin pipe only; it validates the client id and redirect origin through the existing `parseOidcConfig` (the issuer is always Google's), stores the secret through the Hub's secret store (`oidc.clientSecret`, via `OidcSecretSource.put`, so `cli/run.ts` stays the only importer) and writes `hub.json`; the audit row records the redirect origin only. It is additive owner configuration of an extra sign-in that never replaces the password, so it needs no confirmation token. The Hub reads the block at start, so the wizard's finish step restarts the Hub. There is still no `dude-hub` CLI command for it (the terminal owner edits `hub.json` and stores the secret as before); `data-scope-inventory.mjs` gained one reviewed heuristic for the secret write.

A session that ends by itself (idle, a restart, the Hub stopping, the window closing) is reported and the wizard returns to its start; every step is safe to run again.

### 2026-10-29, Milestone 851: the power policy check and the elevated two-step change

PD-152, built: a Hub machine that sleeps or hibernates drops the tunnel and misses scheduled backups, so the policy is "never sleep and never hibernate on AC power". Files: `apps/hub/src/power/` (`powercfg.ts` detection and the fixed commands, `policy-state.ts`, `power-policy.ts` the service), `admin/power-methods.ts` (`power.status|preview|apply|revert`), `service/power.ts` (CLI `dude-hub power status|apply|revert [--confirm <token>]`), `provisioning/components/power.ts` (the `power` component, reserved since Milestone 835), the `power-policy` job, the audit events `power.changed|reverted|regressed`, `@dude/contracts/hub` `power.schema.ts`. Boundary spec: `admin/power-methods.confirmation-boundary.spec.ts` (the name is what `check-high-consequence-gate.mjs` runs through its `confirmation-boundary` filter on the Hub config; no gate script change). Decisions and deviations:

- **Detection is by GUID and by the shape of the output, never by a label.** `powercfg /query SCHEME_CURRENT SUB_SLEEP STANDBYIDLE` and `HIBERNATEIDLE` (fixed argument vectors, `%SystemRoot%\System32\powercfg.exe`, no shell, 15 s timeout): the output must contain the setting's GUID, and the AC value is the second to last line, the DC value the last, each `<anything>: 0x<hex>` (labels are localized, the two index lines and the GUIDs are not; a German sample is in the spec). Seconds become minutes rounded UP, so a nonzero timeout is never read as "never". `powercfg /a` contributes only the informational `sleepStates` (`S1`, `S2`, `S3`, `S0ix`, read from the first block of the output by their `(S?)` tokens); the verdict never depends on it. Verdicts: `ok` (neither AC timeout is set; a plan without a hibernate setting is ok), `needs-change`, `unsupported` (not Windows, or `powercfg` missing: Docker is by design), `unknown` (the sleep setting or an existing hibernate setting could not be read: never guessed as ok).
- **Two steps, bound to the observed state.** `power.preview {action: apply|revert}` returns the exact commands (`powercfg /change standby-timeout-ac 0`, `hibernate-timeout-ac 0`; only a setting that is set gets a command), the AC values before and after, the revert commands and a single-use 60 s ConfirmationStore token (actions `power.apply` and `power.revert`, binding `cli`, class `system-config`) whose digest covers the verdict, both timeouts, the command vectors and the recorded previous values. `power.apply|revert {confirmToken}` re-reads the settings, refuses (`conflict`) when they moved, runs only the previewed vectors, reads the settings back and fails as `power-failed` (`powercfg-failed`, `not-verified` for a change a group policy undid, `unavailable`) with no `powercfg` output in the message. Nothing is previewed (and no token issued) when there is nothing to change, off Windows, or when the output is not understood.
- **Revert restores the recorded values.** The replaced minutes are written to `meta` `power_policy_state` BEFORE the first command runs (a failure part-way is still revertable, and a re-run after a partial failure keeps the original values), and `power.revert` puts them back, audits `power.reverted`, clears the record and sets `optedOut` so a deliberate revert is never nagged about until the owner applies again. Pattern: per-machine state in `meta`, as `backup_dest_state:<id>` (Milestone 847), so no table and no migration; the `power_policy` meta prefix is added to the scrubbed list (`SCRUBBED_META_PREFIXES`, cleared by a restore): the settings belong to THIS computer and a restored Hub on another computer must not "revert" to them. The table classification spec is unchanged (no table).
- **Re-check on start and hourly; one notification per regression episode.** `run.ts` runs one check right after start and registers the `power-policy` job (hourly, `POWER_CHECK_MS`). A check that finds the policy ok stamps `lastOkAt`; a later `needs-change` (and not opted out) is a regression and writes ONE `power.regressed` audit row (`reason: regressed`) and opens an episode that the next ok check closes, so an ignored regression is not repeated every hour or at every start. A machine that was never ok is reported (`reason: not-applied`) only while a tunnel or a backup schedule is configured (`hub.json`), because only then does sleeping hurt. `unsupported` and `unknown` never report.
- **No new notification kind; no HTTP route.** The notification is built from the audit row like the Milestone 850 ones, and is delivered as `backup-overdue` (title "The Hub computer may go to sleep"): a sleeping Hub is what makes backups overdue, and a new kind would touch the desktop preferences, the Hub-web preferences panel and the Agent's event allowlist. The only cost is that the owner's "backup overdue" toggle also silences it. There is no `GET` route and no api-client method (so `api-client-parity.spec.ts` needed nothing): the read-only owner view is the `power` component of `GET /api/v1/provisioning` (`ready`, `degraded`, `needs-attention` after a regression, `unavailable` off Windows, `not-configured` before the first check), which reads the last check from memory and never spawns `powercfg`. The boundary spec asserts no route mentions `power` and that no code under `server/`, `auth/`, `realtime/`, `devices/`, `security/`, `collab/` or `notifications/` references the actions, the methods or `powercfg`.
- **`power-policy` joins `HUB_JOB_IDS`** after `restore-drill` (the Settings job card labels it "Power policy check"; the job label is the one web file this milestone touches). The job is `success` when ok, `failed` on a regression, `skipped` off Windows.
- **Who runs `powercfg`.** The Hub process does, through the injected `PowerRunner`; the CLI only needs the elevated terminal (as `network tunnel`). A foreground `dude-hub run` in an elevated terminal needs nothing more; the installed service runs as `NT SERVICE\DudeHub`, and whether that account may change the active plan's AC timeouts is the first thing the real run below must settle.
- **Scope.** AC (plugged in) timeouts of the active plan only: battery settings, the lid-close action, "Fast Startup", display and disk timeouts, other plans and Modern Standby network behaviour are not touched or reported.

### 2026-10-29, Milestone 850: the restore drill and the backup-health notifications

PD-150's two promises that a backup is worth having: every destination's newest VERIFIED backup is restored into a scratch directory every month and checked, and an overdue (2x the interval), failed or drill-failed backup raises an owner notification through the closed producer list (PD-109). Files: `apps/hub/src/backup/restore-drill.ts` (the engine, the per-destination service and the job timer), `hub/backup-health.ts` (the read model both the status route and the producers use), `notifications/producers.ts`, the credential option added to `backup/restore.ts`, per-destination drill state in `hub/backup-destination-state.ts`; contracts `HUB_JOB_IDS` (`restore-drill`), `HUB_AUDIT_EVENTS` (`backup.drill-passed`, `backup.drill-failed`) and the `BackupStatusResponse` fields. Decisions and deviations:

- **The drill is the real offline restore, pointed at scratch.** `previewRestore` and `applyRestore` gained a `masterKey` credential (exactly one of passphrase or key; a repository source only), so the drill opens the repository with the Hub's held master key and runs the same 31G staged restore into a fresh `backups/.tmp/restore-drill/drill-<random>/` Hub root (new identity, epoch + 1, devices to re-pair, scrubbed state), never the live data directory and never `replace`. The "old Hub is gone" acknowledgement is passed only because the scratch root is never started as a Hub. Before that, the chosen backup gets a full `verify({ scope: 'full' })` (every referenced pack end to end). After it: `PRAGMA integrity_check` on both restored databases, and the restored blob files must equal the manifest's blob count (each was streamed through its SHA-256 by the restore); catalogue rows the backup could not carry are counted as `missingBlobs`, not a failure (the engine already counts and marks them).
- **"Newest verified".** The newest manifest that no unrecorded-run journal names (a committed but unverified manifest never counts, as for the standby). A destination with none is `skipped` (`no-backup`) and records nothing; a destination another operation holds is `skipped` (`busy`): the drill takes the per-destination lock as `drill`, so a backup of that destination answers `busy` meanwhile and the scheduler retries it.
- **Monthly, with a one-day retry.** `nextDrillDueAt`: never drilled means now (once a backup succeeded), 30 days after a pass, one day after a failure. The `restore-drill` Hub job is an in-process timer like `backup-schedule` (not a queue job: it must run on a Hub that never provisioned SaveSphere), checking hourly; `HUB_JOB_IDS` gains `restore-drill` after `backup-schedule` and the Settings job panel labels it "Monthly restore drill". A failed drill shows as a failed job run; a skipped check shows as skipped.
- **Free-space guard.** The drill refuses (`insufficient-space`, recorded as a failed drill) when the scratch volume has less than 1.25x the backup's plaintext bytes plus 256 MiB free (`RestoreSummary.bytes`, new, from the walked manifest); an unknown free space does not block. Memory is bounded by the restore engine's streaming.
- **Scratch is always swept.** At Hub start, at the start of each drill (never a directory a drill of this process is using) and in a `finally` after it; a killed drill leaves one, which the next sweep removes. Nothing outside the scratch directory is written (a spec compares the file tree of the data directory before and after). The destination is seen through a read-only view whose writers throw.
- **Shutdown.** The job's `stop()` aborts a drill between pieces with reason `shutdown`; that records nothing (the drill reruns at the next start). Any other abort (a timeout) is a recorded failure with code `timeout`.
- **State and audit.** Per destination in `backup_dest_state:<id>`: `lastDrillAt`, `lastDrillOutcome`, `lastDrillSuccessAt`, `lastDrillBackupId`, `lastDrillError`, plus `lastVerifiedAt` on a pass. `backup.drill-passed` carries the destination, backup id, blob and missing-blob counts, bytes, packs and the trigger; `backup.drill-failed` carries the destination, backup id when known, a short code and the trigger. Codes come from `restoreDrillFailureCode` (closed engine codes; an unknown error falls back to the backup run's code mapping), never a message, which can name a folder.
- **Notifications reuse the closed kinds.** No new notification kind: adding one would touch the desktop preferences, the Hub-web preferences panel and the Agent's event allowlist. A failed run (`backup.v2-failed`, once per destination, reason and UTC day) and a failed drill (once per destination and day, titled "A restore drill failed") are `backup-failed`; the first success after a failed run of the same destination is `backup-recovered`; overdue is `backup-overdue`, once per destination and UTC day. The scheduler's `no-destination` record is not a failed-run notification (it is the overdue case below). Bodies echo the destination's owner label (looked up from `hub.json`, 64 printable characters), a validated short code and an age, never a path, a folder or a credential.
- **Overdue is per destination.** The clock starts at the newest of the destination's last success, the schedule being set (`backup.scheduled` with `action: set`, or a 31G row without one) and the destination being added (`backup.destination-added`), so re-enabling a schedule or adding a destination never reports an instantly overdue backup; exactly 2x the interval counts as overdue. A schedule set with no destination at all (an upgraded 31G schedule, or the last destination removed) is reported once a day from when the schedule was set. `NotificationProducers.checkBackupOverdue(intervalHours)` became `checkBackupHealth(input)`; `run` calls it after each scheduler check and after each drill verdict.
- **Status.** `GET /api/v1/backup/status` gains per destination `overdue`, `lastDrillAt`, `lastDrillOutcome`, `lastDrillBackupId`, `lastDrillError` (only after a failed drill) and `nextDrillDueAt`, and a Hub-wide `health` (`overdue`, `lastRunFailed`, `drillFailed`, `noDestinationSince`); all optional in the contract, so the typed `backupStatus` client method and the parity entry are unchanged. The admin `backup.schedule.status` adds `health` (the same evaluation with ages), and `backup.destination.list` already carries the whole destination state.
- **`dude-hub backup drill [--destination <id>]` (elevated, admin method `backup.drill`).** Runs the drill now, due or not, and exits 1 unless every drilled destination passed (a skipped one is not a pass). No confirmation token: the Destructive-Action Contract applies to actions that change existing data, and the drill only reads the destination and writes and removes a scratch directory it created itself (the same reasoning that leaves `backup run` and `backup destination verify` without a token). Audited as `cli`.
- **Tests.** `restore-drill.spec.ts` (a pass with the data-directory tree unchanged and no scratch left; a corrupted pack; no manifest and an unverified one; the free-space refusal; a crash-left scratch directory swept; a restored database that fails its check and a throwing step; the destination lock; a shutdown abort versus a timeout; the due, retry and master-key-missing paths of the service; the job timer), `hub/backup-health.spec.ts` (the exact 2x boundary, a never-succeeded destination, a destination added later, a schedule with no destination, the drill schedule), the producer specs in `notifications/notifications.spec.ts`, the status route, admin method, argument and contract specs.
- **Owed.** A drill on a real Windows service with a multi-GiB repository (disk and time), and on an S3 destination over a real network (the drill reads every pack once a month, which costs egress); the Hub-web Settings status does not show the drill fields yet (Milestone 852); Hub-web audit labels for the two new events.

### 2026-10-27, Milestone 847: the backup v2 engine, local destination, retention and restore

`apps/hub/src/backup/` gains the engine (`run-backup-v2.ts`), the single-file export (`create-export.ts`), the destination interface and the `local-folder` destination (`destinations/`), the master-key store (`master-key.ts`), GFS retention and the two-step prune (`retention-v2.ts`), the per-destination lock (`destination-lock.ts`) and a disk-backed temp index (`temp-index.ts`); `snapshot.ts` writes scrubbed snapshot FILES for both databases; the scheduler, the offline restore, the admin methods, the CLI and `GET /api/v1/backup/status` move to v2. `@dude/hub-backup` gains one option (`createRepository(..., { masterKey })`); the format is unchanged. The security contract is in [SECURITY_ARCHITECTURE](../architecture/SECURITY_ARCHITECTURE.md#as-built-in-32-ss1-backup-v2-engine-destinations-retention-and-restore-milestone-847) and the Hub rules in `apps/hub/AGENTS.md`. Decisions and deviations:

- **v2 is the only format the Hub writes; v1 creation is gone from every production path.** `backup create` (and `--for-transfer`) writes a single-file v2 export: its own repository and key under the given passphrase, both databases and every referenced blob, staged under `backups/.tmp`, written to `<name>.part`, re-opened WITH the passphrase and fully verified (every pack and entry, exactly the referenced packs), then renamed. The file name and the two-step admin flow, the token binding, the transfer retirement and their boundary specs are unchanged. `createBackupFile` (v1) stays only as the writer the v1-restore specs use; `backup verify --file` and the restore read both versions through `openBackupFile`.
- **Destination definitions live in `hub.json`, not in a database `meta` table** (the brief suggested meta). They are configuration written only by the elevated `backup destination add|remove`, read per tick like the schedule, and the restore's `hub.json` reduction already drops them, so a restored Hub never points at the old machine's folders. They hold no secret (a later kind's credential goes to the secret store). Per-destination state (last attempt, outcome, success, backup id, error code, verification, repository id and size) is `dude.db` meta `backup_dest_state:<id>` (`hub/backup-destination-state.ts`, so the status route reads it without importing `backup/`); the `backup_dest` meta prefix is scrubbed from snapshots and cleared by a restore.
- **One master key per Hub, created at the first `backup destination add`, not at `schedule set`.** Every destination repository wraps the same random key under the owner's passphrase (subkeys still differ per repository through the repository-id salt). The Hub keeps it as the new secret purpose `backup.masterKey` (DPAPI LocalMachine with its own entropy; a mode-0600 file on Linux and Docker), so scheduled AND manual runs need no passphrase. Adding a second destination must use the passphrase that opens the first (one passphrase per Hub); a folder that already holds this key's repository is adopted (the restore case: re-adding the old folder continues its chain), one with another key is refused. Removing the last destination deletes the key and the schedule. `backup rewrap` re-wraps every destination's `repo` (atomic replace) with the held key; packs and manifests are untouched. The 31G derived schedule key is no longer read; `schedule set|off` delete its file. `schedule-key.ts` stays (cleanup and its spec).
- **Schedule migration.** The schedule is now `{ intervalHours }`; the 31G `folder` and `retention` still parse (an upgraded `hub.json` keeps starting) and are ignored. `backup schedule set --folder` adds that folder as a destination first (with the passphrase), so the 31G call shape still works; `--keep` is accepted with a note and ignored. An upgraded Hub whose schedule was never set again has no destination and no key: each check records `no-destination` (and the overdue notification fires) until the owner sets it once more. Each destination is due on its own (`nextDueAt`: the interval after its last attempt, or the 31G 6-hour back-off after a failure), destinations run in turn, a failure is isolated to its destination, and `backup_last` keeps the overall outcome for the 31G read model.
- **No automatic prune.** PD-150 says pruning is a two-step confirm, so the scheduler never deletes anything (the 31G count prune after a verified run is gone). Retention is GFS 7 daily / 4 weekly / 6 monthly per destination with restic semantics (the newest backup of each distinct day, ISO week and month, counted over periods that have backups), computed from the UTC timestamp in each manifest name. The name is not authenticated; changing it can only change which backups are kept, never mark a referenced pack deletable, because the marks come from the authenticated retained manifests. A retained manifest that cannot be read stops the plan (`manifest-unreadable`).
- **Unreferenced and unreadable blobs.** The `savesphere.db` copy drops `blobs` rows with no reference (garbage the collector would remove; a restored row must have its bytes). A referenced blob whose file is missing or no longer matches its hash is skipped and counted (`skippedBlobs`) instead of failing every future backup; the restore marks such a row `missing`, so the verify job and the collector see the truth.
- **Crash safety by a journal, not by listing.** Every object a run commits is recorded in `dude.db` meta `backup_dest_journal:<id>` until the run is recorded; the next run (and a prune plan) deletes a killed run's objects, including a committed but never verified manifest, which therefore never counts. Partial `.part` uploads older than an hour are swept at the start of a run. A run that fails (verification included) deletes its own objects at once.
- **Verify on write** is `verify({ scope: 'new' })` (the new packs and entries end to end) plus a reservoir sample of up to four deduplicated blobs read in full; a full verify of a whole backup is `backup destination verify` (and Milestone 850's drill).
- **The dedupe index** is the newest readable manifest at the destination, streamed into a temp SQLite file under `backups/.tmp` (an unreadable newest manifest falls back to an older one or a full backup); nothing grows in memory with the number of blobs.
- **Locking.** One operation per destination at a time (backup, prune, re-wrap, remove) through an in-process lock: the Hub process is the only writer of its destinations. A prune or remove refused because a backup holds the destination keeps its confirmation token. Two Hubs writing one folder is not supported and not detected beyond write-once names.
- **Restore.** Sources are a `.dudebackup` file (v1 or v2) or a repository folder with `--backup <id>` (default the newest). The preview and the apply walk and authenticate the whole manifest; the staged apply streams every entry through its SHA-256 (blobs into a staged content-addressed store) and swaps nothing until all of it checked out; a full pack-level verify is not run first because every byte restored is checked on the way. Besides the 31G set, an existing `savesphere.db`, `storage/blobs` and `config/secrets` are moved aside to `backups/replaced-<stamp>/`: the machine-bound secrets belong to the old instance, so even a same-machine restore re-enters them (the provisioning engine derives `needs-provisioning` from the new identity). The 31G phrases, the transfer flag and `--old-hub-gone` are unchanged.
- **Notifications are Milestone 850** (built, see its entry above). The only change here: the overdue check also counts `backup.v2-created` as a success, so a working v2 schedule does not raise false overdue notices. A failed v2 run raises no notification yet.
- **Admin, CLI and read model.** New admin methods `backup.run`, `backup.destination.add|list|backups|verify|remove.preview|remove.apply`, `backup.prune.preview|apply`, `backup.rewrap.preview|apply`; CLI `dude-hub backup run|prune|rewrap|destination add|list|remove|verify` and `backup restore --folder`. `GET /api/v1/backup/status` gains `destinations`, `retention` and `nextScheduledAt` (optional in the contract; the existing `backupStatus` client method and parity entry are unchanged). The audit list gains `backup.v2-created`, `backup.v2-failed`, `backup.v2-verified`, `backup.v2-pruned`, `backup.destination-added`, `backup.destination-removed` and `backup.rewrapped`. `docs/architecture/data-scope-inventory.json` gained three reviewed heuristics (the master key, the restore's staged blob store, the spec fixture).
- **Tests.** `run-backup-v2.spec.ts` (three chained backups with changing blobs: only new blobs written, pack bytes asserted; the newest restored from the folder onto a fresh data directory with every row and blob byte-identical, the 31G fields, `needs_re_pair`, the scrubbed tables of both databases empty and `needs-provisioning` derived; the single-file export with blobs restored; GC refused under the lease and allowed after; snapshot-first consistency; crash injection between packs and manifest then a clean next run that sweeps the orphans; a pack corrupted before verify-on-write fails and is not recorded; busy, missing repository and foreign key; a missing blob marked on restore; a 100 MiB blob streamed with at most about two chunks in flight), `retention-v2.spec.ts` (a 400-day matrix, same-day, sparse and year-boundary cases; mark and sweep over chained incrementals with blobs living in a deleted backup's packs; an unfinished run never retained; an unreadable retained manifest refuses), `backup-v2.confirmation-boundary.spec.ts` (prune, re-wrap and destination remove; in the high-consequence gate), `admin/backup-v2-methods.spec.ts`, `destinations/local-folder.spec.ts` (write-once, `.part`, names, atomic `repo` replace, probe, stale-part sweep, the location rule), `master-key.spec.ts` (the Linux/Docker file fallback and the DPAPI path through a fake helper), the rewritten `scheduler.spec.ts`, and updates to the backup-methods, transfer, status-route, CLI, config, secrets, provisioning and contract specs. The v1 restore specs (`restore.spec.ts`, `restore-real.spec.ts`, `restore-repair.spec.ts`) pass unchanged.

### 2026-10-27, Milestone 846: the streaming Backup v2 format

`packages/hub-backup/src/backup-v2-{format,stream,repo,manifest,writer,reader,export,memory}.ts`, exported from the package index next to the unchanged v1 API, with `backup-v2.spec.ts` and `backup-v2-scale.spec.ts`. The format is the format half of PD-150 only: nothing in `apps/hub` writes or restores v2 yet (Milestone 847). The design is in [SECURITY_ARCHITECTURE](../architecture/SECURITY_ARCHITECTURE.md#as-built-in-32-ss1-backup-v2-format-milestone-846). Decisions and deviations:

- **One coherent layout: a repository of objects plus a single-file export.** Destinations store immutable, independently verifiable objects. `repo` is the header with the wrapped master key; it is the only object ever replaced, on a passphrase change. `packs/<32 hex>` are encrypted packs of about 64 MiB. `manifests/<YYYYMMDDTHHMMSSZ>-<32 hex>` is one manifest per backup, with the timestamp first so a destination listing sorts by time without a key. A `.dudebackup` v2 file is the export of one backup: an export header, the `repo` object, the manifest and every pack the manifest references, copied byte for byte, then a JSON index of offsets and a 12-byte tail. The export is what the 31G transfer flow moves.
- **No `index` object in the format.** Every manifest lists every blob with its extents, including blobs whose bytes sit in earlier backups' packs. The previous manifest is therefore a complete dedupe index (`dedupeId` to extents), and M847 can stream it into whatever cache it wants. Packs are never rewritten (no repacking): a pack becomes deletable only when no retained manifest references it, and the M847 retention and garbage collection follow that rule.
- **Same magic, new versions.** All v2 objects use the v1 magic `DUDEBKUP` with `formatVersion` 2 and `minReaderVersion` 2, so an existing v1 reader (and `readBackupHeader`) answers `unsupported-version` rather than `bad-magic`. The v1 constants, including `BACKUP_READER_VERSION` = 1, are untouched. v2 has its own `BACKUP_V2_READER_VERSION`.
- **Nonce rule, beyond the brief.** The brief's rule is a nonce derived from (pack id, counter). Each object additionally gets its own HKDF key bound to its object name. Because the sink contract is write-once (`create` must refuse an existing or in-flight name), a (key, nonce) pair cannot repeat even if two objects drew the same random id, and a renamed or substituted object never decrypts. The writer also refuses a repeated id from a broken random source.
- **Streaming manifest.** The manifest is NDJSON inside a sealed object (records up to 1 MiB) and is written while the packs are written, so the writer's memory does not grow with the number of entries. Its order is a `head` record, then `file`, `blob` and `pack` records, then an `end` record with totals. Packs are committed before the manifest; the manifest commit is the backup's commit point. Duplicate blob records in one manifest are not refused (detecting them would need memory proportional to the number of blobs), and the engine dedupes before writing.
- **Errors keep the v1 codes.** `BackupErrorCode` is unchanged. A missing object is `integrity`, as is an object substituted from another name or backup. A wrong passphrase and a tampered `repo` header are both `wrong-passphrase-or-corrupt`; distinguishing them would take an unauthenticated check.
- **Writer failure modes.** An input stream error or a blob whose hash or size does not match what the caller declared throws, and the writer stays usable. The bytes already written are left as unreferenced dead space in the pack. A sink or cipher error marks the writer failed; the caller can then only call `abort()`, which leaves committed packs as unreferenced objects for garbage collection and never writes a manifest.
- **`verify` scopes.** `full` (the default) decrypts every referenced pack end to end, checking trailers and tag chains, and hashes every entry, so it decrypts referenced packs twice. `new` does the same for the packs this backup created and the entries stored in them; a blob that only points into earlier packs gets only its dedupe identity checked. Milestone 847's verify-on-write can use `new` to avoid re-reading a whole remote repository on every run.
- **Streaming reads are staged.** `readEntry` and `readBlob` emit plaintext one authenticated chunk at a time and throw `integrity` at the end if the entry's size or SHA-256 does not match. The M847 restore must write to staging and commit only after the stream ends cleanly.
- **Master-key credential.** `{ masterKey }` opens a repository without the KDF (checked against the header's key-check value) and survives a passphrase change; `exportMasterKey()` hands out a copy. When a repository is opened this way, the `repo` header's KDF fields are not authenticated by the wrap, which is harmless because they are not used. Milestone 847 decided it: the Hub keeps one master key as the secret purpose `backup.masterKey` and no longer uses the 31G derived key.
- **Limits** (all constants are exported). Chunks are 1 KiB to 4 MiB (default 1 MiB, the v2 default the brief asked for). Packs are at most 4 GiB (default 64 MiB). A backup holds at most 2^24 entries and 4,096 named files. Names have up to 128 characters `[A-Za-z0-9._-]` and are unique without regard to case. An entry has at most 16,384 extents. An object has fewer than 2^32 chunks. The export index is at most 16 MiB. There is no total-size ceiling. `openBackupFile` loads a v1 file whole only within `V1_MAX_FILE_BYTES` (the v1 ceiling plus framing).
- **Portable.** No Node built-ins: streams are `AsyncIterable<Uint8Array>`, and the sink and source are the `ObjectSink`/`ObjectSource` contracts. Disk, S3, standby and drive adapters belong in `apps/hub` (Milestone 847 on). No new dependency was added (HKDF and HMAC come from the `@noble/hashes` already declared). `createMemoryBackupStore` is a portable write-once in-memory store for specs.
- **Tests.**
  - `backup-v2.spec.ts` (21 tests):
    - round trip with chunk and pack rollover; no plaintext leak of content, names, authority fields or blob hashes in any object;
    - writer input refusals and the busy guard; sink failure, then abort leaves no manifest;
    - dedupe identity is the HMAC, is not the plain or double SHA-256, and differs across repositories;
    - passphrase and master-key opens and wrong credentials; rewrap keeps every pack byte-identical, refuses the old passphrase and opens with the new one;
    - incremental references with both verify scopes, a foreign-repository reference refused and a missing earlier pack detected;
    - versioning: the v1 reader refuses every v2 object and the export with `unsupported-version` without deriving a key; v1 files read through the dispatcher; a future `minReaderVersion` in `repo`, pack and manifest headers and in the manifest head is refused; downgrades and KDF weakening are detected through the associated data; unknown fields and record types are ignored; a missing end record or wrong totals are refused;
    - tampering: every bit position of every object of a small backup, a dropped, cut, appended, duplicated, reordered or spliced chunk, a substituted pack or manifest, a truncated manifest, and the export's header, index and tail plus sampled object bytes;
    - nonces: a fast-check property that (id, counter) to nonce is injective, unique ids across three backups, and a repeating random source refused.
  - `backup-v2-scale.spec.ts`: a deterministic PRNG stream (no fixture files) written through a temp-directory write-once sink, verified, read back piece by piece against the regenerated stream, exported and re-verified through `openBackupFile`. Bounded memory is asserted deterministically from source and sink counters: the writer's input-not-yet-written never exceeds 2 chunks plus 2 pieces, and an entry read's pulled-not-delivered never exceeds 3 chunks plus one 64 KiB piece per stream it opens. The verify pass delivers nothing, so it is checked by sampled heap growth (under 200 MiB for 600 MiB of data). The normal package suite runs it at 64 MiB (about 5 s). `npm run test:backup-scale` (`scripts/test-backup-v2-scale.mjs`, `DUDE_TEST_BIG=1`) runs about 600 MiB in about 47 s on the development machine; the Milestone 854 exit suite must run that script.
  - The v1 specs (`backup.spec.ts`) and the Hub backup specs (`npx vitest run -c vitest.hub.config.mts apps/hub/src/backup`) pass unchanged.
- **Not done here (Milestone 847 on).** The engine (snapshots, blob set under the GC lease, verify-on-write), the local, S3, standby and drive adapters for `ObjectSink`/`ObjectSource`, the atomic replace of `repo` on a passphrase change, the scheduled-key choice, retention and pack garbage collection, the restore of databases and blobs, and the Hub admin methods.
- **Owed.** The 600 MiB run in CI (Milestone 854). Throughput is that of the JavaScript ciphers and hashes (`@noble`): the whole 600 MiB scenario (write, a full verify, reading both databases back, export and a second verify) takes about 47 s here. If large blob stores make that too slow, injecting the host's native SHA-256 is a later, compatible change.

### 2026-10-27, Milestone 845: resumable chunked uploads into the blob store

The upload route family of PD-148: `server/routes/uploads.ts` (five routes, contracts in `@dude/contracts/hub` `uploads.schema.ts`, five typed `@dude/api-client` methods with parity entries plus the pure `uploadFileResumable` helper), the credential-agnostic session core `uploads/upload-service.ts` with `disk-guard.ts` and `attach.ts`, migration `0005-uploads`, the `uploads.expire` queue kind and the `uploads-expire` job id. Decisions and deviations:

- **One non-JSON route, parsed raw.** `PUT /api/v1/uploads/:id/chunks/:index` lives in its own encapsulated Fastify context whose only addition is an `application/octet-stream` parser that returns the raw request stream (nothing is buffered). The 64 KiB `HUB_BODY_LIMIT` is untouched everywhere else (a spec posts an oversize JSON create). `security/request-guard.ts` admits that one content type on exactly that method and path; any other route with it is 415. `Content-Length` is required (411 otherwise, so no chunked transfer) and is the trusted limit: it must not exceed the session's chunk size (413, answered before a byte is read, with `Connection: close` so the body is dropped with the socket) and must equal the expected length of that index (400). The route-level `bodyLimit` is `UPLOAD_BODY_LIMIT` (32 MiB plus 1 KiB slack), the ceiling for any negotiable chunk. A 400, 409 or 507 leaves the (bounded) body to Node, which discards it, so a client sees the status instead of a reset; this deviates from the first design (close on every refusal) on purpose, because a browser writing 8 MiB into a closed socket reports a network error.
- **Credential: owner only.** Owner cookie (plus CSRF) or owner bearer on all five routes; a device token is 403, an ingest token and anonymous are 401 (matrix in `uploads.spec.ts`; `route-gating.spec.ts` still passes and the routes are NOT in the anonymous allowlist). No device or Android capture path needs it in SS1. The service takes an `UploadPrincipal` (`kind`, `id`), so 32-SS3 adds the ingest class by resolving a principal in the route, not by changing the core; a session is invisible (404) to any other principal.
- **Chunking.** 8 MiB default, negotiated into 1 to 32 MiB; every chunk is exactly the chunk size except the last; indexes are 0-based, in any order and idempotent (an identical re-PUT is a 200 `duplicate: true` no-op that still reads and compares the body; a different chunk for an arrived index is 409 and the original is kept). `X-Chunk-Sha256` is verified when sent. The status lists received chunks as inclusive RANGES (`[[0, 3], [5, 5]]`), not an index array, so a 1 TiB file stays small. The declared size is capped at 2^40 (a sanity ceiling, not a policy: there is no fixed attachment cap, the disk guard decides).
- **Storage.** `storage/uploads/<uuid>/<index>.part` (`HubPaths.uploadsDir`), each written to a unique `<index>.<random>.tmp` while hashing, fsynced, renamed, and only then its `upload_chunks` row is written; a crash in between leaves a file no row names (not counted, overwritten by the retry). Both tables are scrubbed from backups (`SAVESPHERE_SCRUBBED_TABLES`); the `upload` blob reference of a completed session is kept metadata, so the expiry job also releases any `upload` reference whose session row no longer exists (the restore case). The session id is a random UUID the Hub generates; names and media types are display data only (control and bidirectional characters stripped, directories dropped, 255 characters), never a path.
- **Completion.** `open` to `completing` to `complete` or `failed` (also `aborted` and `expired`). Chunks stream in order through a per-chunk re-hash into `BlobStore.put` (with `maxBytes` and the declared `expectedSha256`), then one transaction records the blob, adds the `upload:<id>` reference, marks the session complete, drops the chunk rows and writes `upload.completed` to the outbox; only then are the chunk files removed, after re-checking `has` (the narrow GC window of Milestone 833, answered by storing it again from the chunks). A wrong declared hash fails the session for good and keeps no blob. A chunk that vanished or rotted on the Hub is dropped from the received set and the answer is 409, so the client re-sends only it (`uploadFileResumable` does this on its own, up to three rounds). The assembly outlives the request: `complete` waits up to 50 s and then answers 202 with the session (state `completing`); calling it again joins the running assembly, and a Hub that restarts mid-assembly reopens the session (chunks intact). The response carries `blobRef` = `upload:<uploadId>`.
- **Attach hook.** `attachUploadBlob(db, uploadId, ownerKind, ownerId, now, principal?)` (`uploads/attach.ts`) adds the caller's reference and releases the upload's in one transaction (nested transactions join the caller's), marks the session attached so expiry never touches it, and refuses an open, failed, aborted or expired session. 32-SS3 calls it.
- **Guards.** The free-disk guard keeps the larger of 512 MiB and 5% of the volume free (`UPLOAD_MIN_FREE_BYTES`, `UPLOAD_MIN_FREE_FRACTION`, injectable): session creation (the new file plus everything open sessions still owe), every chunk, and `complete` (the chunk files and the blob coexist until the commit, so the assembly needs the file's size again; the Docker volume therefore needs about twice the largest upload) are refused with HTTP 507 and the NEW error code `storage-full` (`HUB_ERROR_CODES` is now 14; a volume `statfs` cannot measure does not refuse, and a real ENOSPC maps to the same answer). At most 8 open or completing sessions per principal and 2^41 declared bytes in flight (both 409, injectable). Idle sessions expire 24 hours after the last activity; a completed, unattached session keeps its reference 24 hours, then the job releases it and the bytes wait for the two-step collector. Final rows are pruned after 7 days.
- **Expiry job.** `uploads.expire` (inline, every 15 minutes; `HUB_JOB_IDS` gains `uploads-expire`; the Settings job panel shows "Expired upload cleanup") expires idle sessions, deletes their chunk files, releases references, removes chunk directories no live session owns (older than 10 minutes), releases orphan `upload` references and prunes old rows. `queue-run.spec.ts` and `cli.spec.ts` now expect four scheduled succeeded jobs and the extra id.
- **Audit.** `HUB_AUDIT_EVENTS` gains `upload.created`, `upload.completed`, `upload.aborted`, `upload.failed` and `upload.expired`, all through the outbox (appended inside the transaction that changes the session, then drained). Details: the upload id, sizes, the blob hash and a closed failure reason; never a name, a media type or bytes.
- **Abort is one audited step.** `DELETE /api/v1/uploads/:id` is not two-step: it removes only this session's own staged chunks and its own `upload` reference. It never deletes a committed blob (the blob store's only deleter stays the two-step mark-and-sweep), nothing it touches was referenced by content (an attached session is left alone), and it is idempotent and refused while assembling. Recorded against the Destructive-Action Contract in `SECURITY_ARCHITECTURE.md`; `uploads.spec.ts` pins that abort leaves a blob another owner references intact. There is therefore no `*.confirmation-boundary.spec.ts`.
- **Client.** `HubRequest` gained an optional `rawBody` (a `Uint8Array` sent as-is, with the caller's `content-type`); the web fetch transport and the Agent's pinned transport support it, the mobile bridge refuses it (its native request takes a string), so mobile uploads wait for 32-SS3. `uploadFileResumable(client, source, { sha256Hex, ... })` chunks at the negotiated size, resumes from the status, sends only missing chunks with their hashes, retries 408, 429, 5xx (not 507) and network errors with exponential backoff, polls a 202, repairs a 409 and reads one chunk at a time from an `UploadSource` (`bytesSource`, `blobSource`). The portable package may not touch `crypto`, so the host passes `sha256Hex` (`webCryptoSha256(crypto.subtle)`).
- **Limits to know.** Node's HTTP server applies its own request timeout (300 s by default), so a chunk needs at least about 28 KiB/s; a smaller negotiated chunk helps a slow link. The tunnel's own response time limit is why `complete` answers 202 rather than blocking.
- **Tests.** `server/uploads.spec.ts` (a generated 40 MiB payload in five chunks through the real Hub and through the typed client, resume after a mid-chunk disconnect, duplicate and conflicting chunks, wrong chunk hash, length and index, out-of-order, a 413 answered before the body is read and 411, the content-type carve-out, a wrong declared hash keeping no blob, the 202 path, crash injection between the chunk file and its row and mid-assembly, a lost and a rotted chunk, the disk guard on all three steps, the caps, expiry with attached, unattached and orphan references, abort, attach, the credential matrix and a 96-chunk memory bound), `disk-guard.spec.ts`, `0005-uploads.spec.ts`, the classification spec, `uploads.schema.spec.ts` and `upload-file.spec.ts`.
- **Owed.** A real browser upload through the Cloudflare tunnel (request timeout, the 100 MB limit, a slow link, an early 413 seen from `fetch`) and a multi-gigabyte run on a real volume belong to the acceptance script; the web UI that uses the helper is 32-SS3.

### 2026-10-27, Milestone 843: the token-only ingest scaffold

`ingest_tokens` in `savesphere.db` (migration `0004-ingest-tokens`), the `ingest-token` credential class (`dit_`), `createRequireIngest` and `INGEST_BEARER_RESOLVERS`, the ingest and failure buckets in `security/rate-limit.ts`, `GET /api/v1/ingest/ping`, the owner management routes under `/api/v1/admin/ingest-tokens`, contracts (`ingest.schema.ts`, `credentials.ts`), five `@dude/api-client` methods with parity entries, three audit events and the `security/route-gating-allowlist.ts` fixture. - **Owner management is under `/api/v1/admin/ingest-tokens`, not `/api/v1/ingest/tokens`.** `/api/v1/ingest/*` is the token-only namespace (PD-119): nothing in it may accept a session, so the owner's list, create and revoke routes could not live there. (`/api/v1/admin/` is an HTTP prefix here only; the admin named pipe is unrelated.) The ping route is the only route under `/api/v1/ingest/`, and a spec pins that set.
- **The credential is a plain bearer family, not an owner session kind.** `INGEST_BEARER_RESOLVERS` mirrors the shape of `OWNER_BEARER_RESOLVERS` but is consulted only by `createRequireIngest`, and `resolveOwner`, `requireDevice` and the WebSocket authenticators never see it, so an ingest token anywhere else is the existing "unknown credential" 401 without any new branch in the owner path. On an ingest route every other credential (owner cookie, owner bearer, device token, other schemes) is 401 rather than 403, so the response is no oracle for which credential families exist. A `Cookie` header on the ingest path is deleted before any handler and ignored, so a valid token plus a session cookie is the token alone; a cookie alone is 401.
- **Hashing.** The secret is 32 random bytes (`dit_` plus 43 base64url characters), so the stored value is the plain lower-case hex SHA-256 (like `ddt_` device tokens; no per-token salt or slow hash is needed at 256 bits). Lookup is by that hash and the hash comparison is `timingSafeEqual`. The row keeps a six-character display prefix (`dit_` plus six) that is too short to use.
- **Scrubbed on restore (PD-149).** `ingest_tokens` joins `SAVESPHERE_SCRUBBED_TABLES` and `classification.spec.ts` pins it. The backup engine that actually applies the scrub for `savesphere.db` is Milestone 847; until then the list is only exported and enforced by the classification spec, as for `jobs` and `audit_outbox`.
- **Audit through the outbox.** Token creation and revocation write `ingest.token-created` and `ingest.token-revoked` to `audit_outbox` in the same transaction as the row change and drain after the commit (the existing 832 mechanism), so the audit row has no address (the outbox carries none) and a crash between commit and drain loses nothing. `ingest.auth-failed` is written straight to `dude.db` (it has no content write to be atomic with) at most once a minute per address, plus once a minute per token for a scope refusal; the failure counters still see every attempt. Audit detail keys avoid the sanitizer's credential-looking names (`ingestId`, not `tokenId`).
- **Rate limits and the IP block.** A valid token is metered per token id (`INGEST_TOKEN_POLICY`, 60 a minute, burst 20); a refused presented credential takes a token from a per-address failure bucket (`INGEST_FAILURE_POLICY`, 10 a minute, burst 10) that is checked BEFORE a token is evaluated, and counts toward `ip-block.ts` exactly like a failed login (`noteCredentialFailure`, 25 in 15 minutes; loopback is exempt as everywhere). A request with no `Authorization` header at all is a plain 401 that costs nothing and counts for nothing (a scanner probing the path is not guessing). Both policies are exported constants and injectable through `RateLimiterOptions`. The numbers are provisional; SS3 sizes them against real capture clients.
- **Storage handle.** `run` passes the already open `savesphere.db` (`QueueRuntime.db`) as `createHubServer`'s `ingest: { db }`, so ingest exists only once SaveSphere storage does and no second connection is opened. Without it the owner routes answer 409 `conflict` with a "run dude-hub provision" sentence (not an empty list that looks like "no tokens"; a new error code was not worth the closed-list change) and every token is unknown. Hub `create-server` registers the routes unconditionally, so the api-client parity spec sees them.
- **Cap.** At most 25 unrevoked tokens (`INGEST_MAX_LIVE_TOKENS`; expired ones count until revoked). A label is 1 to 64 characters; expiry is optional, 1 to 365 days (`expiresInDays`, so a client clock never decides it).
- **Revoke is two-step** with the ConfirmationStore (single use, 60 seconds, token bound to the ingest token id, digest over the session hash, the id and its creation time, so a different session or a changed token is a 403 or 409 and revokes nothing), step-up, class `secret-management`. A mint is not two-step (it adds a credential and removes none) but needs the owner, step-up and CSRF; a token can neither mint nor revoke. `server/ingest.confirmation-boundary.spec.ts` is picked up by the Hub half of `test:high-consequence` by its file name.
- **No CORS, and a note for SS3.** The Hub sends no `Access-Control-*` header anywhere and the ingest path strips one if a handler ever added it. The request guard refuses a mutating bearer request with `Sec-Fetch-Mode: cors` and `Sec-Fetch-Site: cross-site`, which is what a browser extension's `fetch` may send, so SS3 must decide (a dated entry, not a convenience) how an ingest POST from an extension origin passes before any capture route that browsers call is added. `GET /ping` is not mutating and is unaffected.

### 2026-10-27, Milestone 842: Google sign-in, linking and unlinking

The OIDC core of Milestone 841 is now routes and a web surface: `server/routes/oidc.ts` (eight routes, contracts in `@dude/contracts/hub` `oidc.schema.ts`, seven typed `@dude/api-client` methods with parity entries), migration `0012-oidc-link`, the `oidc` throttle kind, `secrets/oidc-source.ts` (the one place `run` reads the client secret through), the sign-in page's "Continue with Google" and the Settings > Security & Sessions "Google accounts" panel. Decisions and deviations:

- **Routes (credential, then behaviour).** `GET /auth/oidc/status` (none; `{ configured, enabled }` only, from configuration and the secret, never a probe of Google), `POST /auth/oidc/start` (none, `authLimited`, `credentialless`, throttled per address), `GET /auth/oidc/callback` (none, session-less, always a redirect), `POST /auth/oidc/link/start` and `/link/complete` (owner COOKIE session, CSRF, step-up), `GET /auth/oidc/accounts` (owner cookie or bearer), `POST /auth/oidc/unlink/preview` and `/unlink` (owner cookie or bearer, step-up, two-step). Closed audit events added: `oidc.signin`, `oidc.signin-failed`, `oidc.refused-account`, `oidc.link-started`, `oidc.link`, `oidc.unlink`, `oidc.unreachable`; `oidc.refused-account`, `oidc.link` and `oidc.unlink` are also security alerts (so they become owner notifications through the existing alert producer, whose closed list is otherwise unchanged). New error code `oidc-unavailable` (HTTP 503).
- **Deviation: two start routes, not one with a `purpose`.** The sketch had `POST /auth/oidc/start { purpose }`. One route cannot be both credential-less (sign-in, no CSRF, because a stale cookie must not break it) and cookie-authenticated (link, which needs CSRF and step-up) under the request guard's per-route `credentialless` flag, so the link start is `POST /auth/oidc/link/start` and the body is `{ returnTo? }` for both. The status route offers the button for `unreachable` as well as `ready` (only a start attempt can find out Google is back); the click then lands on the password form with an explanation instead of hiding Google for good.
- **The callback.** It checks the per-address `oidc` throttle first (`?oidc=locked`), spends the flow, exchanges the code and verifies the ID token (the Milestone 841 client), then: sign-in looks up `(google, sub)` and, only for a `sub` linked to the owner, creates the session through the SAME `createSession`, cookie, absolute lifetime, user agent and address attribution as the password path and audits `owner.sign-in` (`via: 'google'` and `newAddress`, so new-address alerts keep working) plus `oidc.signin`; anything else (an unlinked `sub`, the same address under another `sub`, no owner) is the one generic refusal: a redirect to `/hub/sign-in?oidc=failed`, `recordFailureKeys` (the `oidc` per-address counter AND the automatic IP block, exactly like a wrong password) and `oidc.refused-account` with only a 12-character hash tag of the `sub` (never the `sub` or an address). Every other failure (bad, unknown, replayed or expired state, rejected code, any token verification failure) is `?oidc=failed` with `oidc.signin-failed` (a closed reason) and counted; a provider `error=` (the owner declined) spends the flow, is audited as `provider-error` and is NOT counted unless the state names no live flow; Google unreachable, a missing secret or no configuration is `?oidc=unavailable`, never counted, with `oidc.unreachable` audited at most once a minute per process. The redirect set is closed (`failed`, `unavailable`, `locked`), the target is `flow.returnTo` (sanitized at start) or `/hub/sign-in?...`, and nothing from the request is reflected.
- **A Google session is NOT stepped up.** `createSession` gained `steppedUp?: boolean` (default true); the Google path passes false, because Google is never a step-up factor (PD-121): the new session cannot link, unlink, create pairing codes or do anything else step-up gates until the owner enters the password (the existing step-up route, unchanged). The HTTP step-up route accepts the password only; the recovery-code alternative named in the sketch is not an existing step-up path and was not added.
- **Link, two legs.** Leg one: `link/start` (step-up; binds the flow to the owner and the session hash) returns the Google URL; the callback records the VERIFIED `(sub, email, issuer)` on the consumed flow row and answers a 302 to `<returnTo>?oidcLink=<one-time token>` (43 base64url characters, only its SHA-256 stored); no cookie is set and nothing is linked. Leg two: `link/complete` (cookie, CSRF, step-up) claims the token once: it must belong to the signed-in owner and to the session that started the link OR a session rotated from it (`sessionDescendsFrom` walks `rotated_to`, so a step-up between the legs, which rotates the cookie, does not break it), within 10 minutes of the callback. A refused claim (`wrong-session`, `wrong-owner`) does not spend the token; an expired, replayed or unknown one is 403; an already-linked `sub` is 409 and is refused, never duplicated. Binding is by `sub` only; the same address under another `sub` links as a different account. **Migration `0012-oidc-link`** (additive, reader floor unchanged) adds the verified-link columns to the transient `oidc_flows` table (already scrubbed from every backup), so no new table needed scrubbing or classification. ### 2026-10-27, Milestone 841: OIDC core, linked identities and a fake IdP

`apps/hub/src/auth/oidc/` (the relying-party core, no route), migration `0011-oidc` (`linked_identities`, `oidc_flows`), the `oidc` block of `hub.json`, `security/cross-site-get.ts`, the `oidc` provisioning component and the spec-only `fake-idp.ts`. The Hub contract for the code is in [apps/hub/AGENTS.md](../../apps/hub/AGENTS.md); the routes, step-up, audit events and the failed-callback counting into `ip-block.ts` are Milestone 842 (no `@dude/contracts` or `@dude/api-client` change here). Decisions and deviations:

- **Restore scrubs BOTH new tables.** `oidc_flows` is transient (in-flight attempts and PKCE verifiers). `linked_identities` is scrubbed too (added to `SCRUBBED_TABLES`, so the backup copy and the restore both empty it): a restored Hub is a NEW instance with a new identity, probably a new domain and a new OAuth redirect, and the machine-bound client secret never travels, so a restored link would point at an OAuth client that no longer exists and could mislead. Restore therefore needs the password or a recovery code, after which the owner configures Google again and re-links. `sanitizeRestoredConfig` already keeps only the port and names, so the `oidc` block is dropped as well, and the provisioning `oidc` component reports `needs-attention` when the secret was expected (`provisioning_expected_secrets`) but the block is gone. The scrub fixture, `snapshot.spec.ts`, `restore.spec.ts` and `classification.spec.ts` assert both.
- **Migration 0011 is additive (`minReaderVersion` 1).** A Hub without OIDC can open the database and keeps working with the password; this differs from 0010, which raised the floor. The table `CHECK`s encode the contract (provider `google` only, `sub` 1 to 255 bytes, `(provider, sub)` unique, a `link` flow needs owner and session hash, a `signin` flow neither). `oidc_flows.session_hash` carries no foreign key (sessions are scrubbed and pruned independently).
- **Bug fixed on the way, in `@dude/sqlite-store`.** `runMigrations` read the reader floor once before the loop, so a later pending migration with a LOWER floor overwrote the floor an earlier one in the same run had raised: a fresh database running 0001 to 0011 ended at floor 1 instead of 10, silently defeating the refusal of an older Hub (found by the existing 0010 specs failing once 0011 was added). The floor now only rises within a run; `migration-runner.spec.ts` covers it. Existing databases are unaffected (they already hold their floor), but a database created fresh on a build between 0010 and now would carry floor 1 until a later migration run raises it; no data is at risk.
- **The request guard did not refuse cross-site GETs before this milestone.** `registerRequestGuard` ran for mutating methods only, and the SameSite=Strict cookie is what kept a cross-site navigation anonymous. So the exemption is built together with its rule: `evaluateCrossSiteGet` refuses a cross-site top-level navigation (`Sec-Fetch-Site: cross-site` and `Sec-Fetch-Mode: navigate`) to anything under `/api` (new behaviour, defence in depth; `cors` fetches stay governed by CORS, the Hub sends no `Access-Control-Allow-Origin`, and same-site, same-origin and non-browser clients are unchanged) and admits exactly the `CROSS_SITE_GET_ALLOWLIST` entry `GET /api/v1/auth/oidc/callback`. Narrowing beyond the sketch: HEAD never; only while `oidc` is configured; a cross-site request must also be `Sec-Fetch-Dest: document`; each query parameter at most once, 4096 characters, no body (400 otherwise); and the request is made CREDENTIAL-LESS (`Cookie` and `Authorization` removed in the hook, for same-site visits too), so a session can never be the callback's authority.
- **Allowed query parameters are wider than `code`, `state`, `error`, `error_description`.** Google appends `scope`, `authuser`, `prompt` and (Workspace) `hd` to the redirect, RFC 9207 defines `iss`, and `error_uri` is part of the error response; refusing them would break a real sign-in. They are tolerated and unused; anything else (for example `session` or `access_token`) is a 400.
- **Config.** `oidc: { issuer?, clientId, redirectOrigin }` in `hub.json`, strict (`parseOidcConfig`): the issuer defaults to `https://accounts.google.com`, must be written canonically (https, no port, query, fragment or trailing slash, a public DNS name, never an IP or `localhost`); `redirectOrigin` is an origin only, https (plain http only for `localhost`, `127.0.0.1` or `[::1]`). No secret key can be placed in it. The callback URL the owner registers with Google is `<redirectOrigin>/api/v1/auth/oidc/callback` (`OidcClient.redirectUri()`).
- **Egress.** The allowlist is the three Google hosts for the Google issuer and exactly the issuer host for any other (a discovery document naming any other host is refused). GET redirects are followed only to the same host (two hops), a POST (the token exchange) never redirects, https and the default port only, one timeout (5 s) over every hop and the body, bounded bodies (discovery 64 KiB, JWKS 128 KiB, token 64 KiB), and every failure is a closed code with no URL, header or body. It is disclosed in `SECURITY.md` (the Hub row, via the generator) and in the provisioning `oidc` component detail.
- **Cache.** Discovery and JWKS honour `Cache-Control: max-age` clamped to 5 minutes to 24 hours (1 hour default); a stale copy serves for up to 24 hours while Google is down; a failed fetch is remembered for 30 seconds; concurrent callers share one fetch; an unknown `kid` forces one refresh and never more than one per 30 seconds, so forged `kid`s cost one fetch. Nothing throws into a request path: `unreachable` is a value and Milestone 842 turns it into the password fallback.
- **ID token.** RS256 only (an `alg` of `none`, `HS256`, `RS384`, `ES256` and every other is refused before any key is read; a token with no `kid` is refused), `iss`, `aud`, `exp`, `nbf` through `jose` with a 60 second skew, `iat` required, not in the future and at most 10 minutes old (not in the sketch: the Hub exchanges the code seconds after the redirect, so an old token is a replay), `azp` equal to the client when present and required when there are several audiences, the `nonce` compared in constant time against the stored hash, `sub` 1 to 255 characters. `email` is trimmed display text and `email_verified` is informational. A verification failure is one of 13 closed reasons; a Google outage after the exchange is `unreachable`, not a failure.
- **Flows.** A flow is spent by the first callback even when the provider then fails (the owner starts again); the verifier is cleared in the same transaction. `state` and `nonce` are stored only as SHA-256 hashes; the PKCE verifier stays in the row (it is needed at the exchange) and the table is scrubbed from every backup. At most 200 live flows exist (an unauthenticated `signin` start is bounded) and expired or spent rows are swept after a retention window. `return_to` is sanitized to a same-site path (never `//`, a backslash, a control character, a scheme or an `/api` path) and falls back to `/` silently. There is no browser-binding cookie: the cookie is SameSite=Strict and would not arrive on the callback, so a login-CSRF attempt is stopped by the rule that only an already-linked `sub` signs in, and a link flow is bound to the owner and session hash that started it (the completion in Milestone 842 must still check that the signed-in session at the follow-up page is that session).
- **Client secret.** Purpose `oidc.clientSecret`, read per call through a structural `getText` (`auth/oidc/client-secret.ts` imports nothing from `secrets/`; `run` supplies the store in Milestone 842). The wire form is `client_secret_post` unless discovery offers only `client_secret_basic`. Only the ID token is kept from the token response; the access token is dropped.
- **Provisioning.** The `oidc` component (registered after `tunnel`) reads only the `oidc` block of `hub.json` and the secret's presence, never the network: `not-configured`, `needs-attention` (invalid block, or the secret absent, which is also what a restore looks like) and `ready`, with `degraded` standing in for the sketch's `unreachable` (the contract has no such state) when `context.oidc?.()` reports it. `ProvisioningContext.oidc` and `ProvisioningOptions.oidc` were added; `run` does not pass it until Milestone 842 builds the client there. `provisioning/components/oidc.ts` joined the secret-store importer allowlist (`secrets.spec.ts`).
- **Dependencies.** `jose` (`^6.2.12`, already a root dependency) is now declared in `apps/hub/package.json` and the lockfile workspace entry; `npm run check:boundaries` and `check:dockerfiles` pass, and a one-off esbuild bundle of the client with the `build-hub.mjs` options loads under Node. `npm run hub:compile` does not exercise `jose` yet, because nothing reachable from `main.ts` imports the client until Milestone 842.
- **Inventory and SECURITY.md.** `scripts/data-scope-inventory.mjs` classifies both tables as `local-only` and the inventory was regenerated (no review heuristic was needed); the Hub row of the generated `SECURITY.md` now names the three outbound hosts.
- **Tests.** `pkce` (RFC 7636 vector, entropy, shape), `flows` (single use, expiry boundary, sweep, cap, `return_to` fuzz), `egress` (host, scheme, port, redirect, size, timeout, error hygiene), `provider` (cache, stale, backoff, cooldown, document validation, key filtering), `verify-id-token` (every claim, algorithm and `kid` case against the fake IdP), `client` (round trips, replay, every failure mode, secret handling through the real Linux file store, no secret, code, token or verifier in the database, the audit table, results or process output), `linked-identities`, `cross-site-get` (pure, and against a real test Hub), config, migration, classification and the provisioning component.
- **Not done here (Milestone 842 and later).** The routes, the session cookie, step-up, the audit events (the audit sanitizer refuses any detail key containing `code`, `token`, `key` or `secret`, so use `reason`), `ip-block` counting of failed callbacks, the `run` wiring of the client and the secret store, the sweep timer, the entry of the client secret (the wizard, Milestone 853) and the Hub-web sign-in page.
